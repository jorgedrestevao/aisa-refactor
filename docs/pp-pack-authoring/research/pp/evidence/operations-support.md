**The reading rule for this area.** Power Platform's operational story has a specific shape that must be understood before any individual feature matters:

1. **The platform operates itself well** — zone redundancy, continuous backups, automatic patching, service health (OP-01, OP-14, PF-40).
2. **The solution is not operated at all unless someone decides to operate it.** There is no default owner, no default monitoring, no default alert, no default runbook. Every operational capability in §2 must be *deliberately turned on*, and most of them require a licence tier the maker does not control (OP-21).
3. **Most of the observability that would explain a production problem is gated, delayed, aggregated or lossy** (OP-11, OP-12, OP-13). This is the single most consequential structural fact in the area and §3 is built on it.
4. **Microsoft's support scope is narrower than teams assume** — no RCAs, a four-hour cap on performance cases, no help with data corruption, and end users cannot raise tickets at all (OP-24, OP-25).

So the operational question in Discovery is never "does it have monitoring?" but "**which role notices, on which signal, acting as which identity, with what evidence, and what had to be bought for that evidence to exist?**" The nine organisational items of OE:01–OE:11 are real; what a technical decision consumes from them is the design consequence — role, identity, permission, mechanism, alert destination, recovery procedure — not a name, an acceptance or a maturity grade.

## 1. Operational maturity is a design input, not a post-deployment concern

Microsoft publishes the distinction this area turns on, as a table contrasting a **productivity workload** with a **mission-critical workload** (O-01, `ms.date` 2026-05-04):

| Productivity workload | Mission-critical workload |
|---|---|
| Built ad-hoc | Built to last |
| Built by one | Built and maintained by a team |
| Supports non-critical processes | Support business critical processes |
| No tests | Automated tests |
| **Development in production** | **Exercises application lifecycle management** |
| Users monitor quality | Monitored to improve |
| Improved in reaction to user complaints | Improved with recommendations |
| Short lifecycle | Long lifecycle |

And the definition: *"A mission-critical workload refers to a workload that is essential for the continuous operation of a business or organization. These workloads must be highly reliable, always available, and resilient to failures."* Microsoft names four design factors — reliability and availability, security, performance, and *"Operational Excellence: Continuous monitoring, logging, and alerting are essential to detect and respond to issues promptly"* — and three challenges: *"Creating a reliable application at scale is complex. It demands deep platform knowledge… In any complex distributed system, failures are inevitable. Solutions must be architected to handle failures with correlated or cascading impacts… Operationalizing mission-critical workloads necessitates a high level of engineering rigor, maturity throughout the entire engineering lifecycle, and the ability to learn from failures"* (O-01).

### 1.1 The four maturity classes and what actually changes

Extending Microsoft's two-column table to the four classes the brief asks about. The right-hand column is what makes this a **design** input rather than a process input: each row names the things that must change in the *architecture*, not only in the ways of working.

| Class | Operationally characterised by | What changes in the architecture |
|---|---|---|
| **Simple departmental** | One maker, users report problems, no formal support, short life | Nothing. Default environment or a team environment; non-solution artefacts acceptable; no telemetry. This is a legitimate class and over-engineering it is a real cost (LC-28) |
| **Business-critical** | Named owner, monitored, a support route exists, multi-year life | **Solution-aware artefacts** (required for capacity licences, pipelines, backup coverage — OP-15, OP-16); **service-principal or capacity-licensed ownership** (OP-04); telemetry export, which requires a **managed environment** (OP-11); an environment topology with dev/test separation (OP-20) |
| **Enterprise** | Platform team, ALM pipeline, change control, integrated with enterprise monitoring | All of the above plus **correlation identifiers across service boundaries** (OP-10), audit enabled (with its unfunded capacity cost, LC-11), **environment strategy with managed environments throughout the pipeline** (OP-16), and DLP/network policy which are themselves managed-environment features (OP-21) |
| **Mission-critical** | 24×7 expectation, RTO/RPO commitments, drills, incident command | All of the above plus **cross-region DR** (production + managed environment + double storage, and it degrades automation throughput — OP-18); **dependency-level failure-mode analysis** because the platform's own resilience says nothing about the ERP on the path (OP-19); a **premium support plan** (OP-24); and **documented, drilled runbooks** (OP-18) |

**The load-bearing consequence.** Moving from "business-critical" to "mission-critical" is not a process upgrade — it changes the licence footprint of every user in the environment (OP-21 / LC-23), the artefact structure (solutions, OP-15), the environment topology (OP-20) and the region strategy (OP-18). So **criticality must be established in Discovery**, because discovering it after the build means rework.

- **Classification:** DECISION CRITERION · **Origin:** MS (the two-column table and definitions) + INF (the four-class extension and the architecture column) · **Confidence:** MEDIUM · **Sources:** O-01, and the findings cited in the right-hand column

## 2. Findings

### 2.1 What Microsoft's operational-excellence guidance actually requires

#### OP-01 — Microsoft publishes an eleven-item operational-excellence checklist, and most of it is **about people and process, not tooling**
- **Classification:** RECOMMENDATION · **Origin:** MS
- **Evidence:** OE:01–OE:11 verbatim (O-02, `ms.date` 2025-08-15): **OE:01** *"Determine workload team members' specializations, and integrate them into a robust set of practices… Team members must have clarity in decision making and responsibilities, value continuous improvement and optimization, and adopt a blameless culture."* **OE:02** *"Formalize the way you run routine, as-needed, and emergency operational tasks by using documentation, checklists, or automation."* **OE:03** *"Formalize software ideation and planning processes."* **OE:04** *"Optimize software development and quality assurance processes… standardize practices across components such as tooling, source control, application design patterns, documentation, and style guides."* **OE:05** *"Build a workload supply chain that drives proposed changes through predictable, automated pipelines."* **OE:06** *"Design and implement a monitoring system to validate design choices and inform future design and business decisions."* **OE:07** *"Develop an effective emergency operations practice. Ensure that your workload emits meaningful health signals. Collect the resulting data and use it to generate actionable alerts… **Clearly define human responsibilities, such as on-call rotations, incident management, emergency resource access, and running postmortems.**"* **OE:08** *"Automate all tasks that don't benefit from the insight and adaptability of human intervention."* **OE:09** *"Design and implement automation up front… **Don't try to retrofit automation later.**"* **OE:10** *"Clearly define your workload's safe deployment practices. Emphasize the ideals of small, incremental, quality-gated release methods."* **OE:11** *"Implement a deployment failure mitigation strategy that addresses unexpected mid-rollout issues with rapid recovery. Combine multiple approaches, such as rollback, feature disablement, or using your deployment pattern's native capabilities."* Framing: *"Prioritize human intervention in areas that benefit from it, and incorporate automation in other areas… **If you don't consider tradeoffs and recommendations for operational excellence, your workload might be at risk**"* (O-02).
- **Why it matters:** Nine of the eleven items are organisational. Microsoft is saying, in its own words, that Power Platform operational excellence is mostly a **team, ownership and process** problem — which is exactly the part a low-code delivery model tends to skip, because the platform makes the build so cheap that no one budgets the operating model. OE:07's explicit list (on-call rotations, incident management, emergency access, postmortems) is the clearest statement anywhere in this corpus of what "supported in production" actually means.
- **Decision impact:** For any workload above the departmental class, the operating model is a **deliverable**, not an assumption — expressed as design objects, never as people: the **role** that intervenes and the **identity** it runs as, the escalation route and its **alert destination**, runbooks, the **mechanism** that detects the condition, postmortem practice, and a defined deployment and rollback method. Absence of any of them is a **requirement with a cost** carried by the option; it is never a verdict on the option's availability, and never a verdict on the organisation. OE:09's *"Don't try to retrofit automation later"* makes ALM an up-front architectural decision (→ OP-15, OP-16). Where the sponsor cannot name who will do these things, the workload is not ready for production regardless of the state of the build.
- **Confidence:** HIGH · **Sources:** O-02

#### OP-02 — The reliability checklist requires per-flow criticality rating and failure-mode analysis **before** monitoring design
- **Classification:** RECOMMENDATION · **Origin:** MS
- **Evidence:** RE:01–RE:08 (O-03, `ms.date` 2025-08-15), of which four are load-bearing here: **RE:02** *"Identify and rate user and system flows. Use a criticality scale based on your business requirements to prioritize the flows."* **RE:03** *"Use failure mode analysis (FMA) to identify and prioritize potential failures in your solution components. Perform FMA to help you assess the risk and effect of each failure mode. Determine how the workload responds and recovers."* **RE:04** *"Define reliability and recovery targets for the components, the flows, and the overall solution. Visualize the targets to negotiate, gain consensus, set expectations, and drive actions… **Use the defined targets to build the health model. The health model defines what healthy, degraded, and unhealthy states look like.**"* **RE:08** *"Measure and publish the solution's health indicators. Continuously capture uptime and other reliability data from across the workload and also from individual components and key flows."* And the sequencing is explicit: *"Before you create a monitoring and alerting strategy, perform the following tasks for your workload as part of your reliability planning: Identify critical and noncritical flows. Perform failure mode analysis (FMA) for your flows. Identify reliability targets. Design a robust testing strategy"* (O-04, `ms.date` 2025-08-18).
- **Why it matters:** It inverts the usual order. Teams reach for Application Insights first; Microsoft says you cannot design monitoring until you know which flows are critical, how each fails, and what "degraded" means for each. Without a health model, alerts have no thresholds and monitoring produces noise instead of signal — which is how monitoring gets switched off.
- **Decision impact:** Encode the order: rate the business flows → analyse failure modes per flow → set reliability targets per flow → define healthy/degraded/unhealthy → *then* choose instrumentation. This also makes the analysis **per business flow across dependencies**, not per platform component — which is the only way to reach an honest availability answer (→ OP-19, PF-43). Practically: the output is a short table of critical flows, each with its failure modes, its target, its health definition and its owner.
- **Confidence:** HIGH · **Sources:** O-03, O-04

#### OP-03 — Microsoft prescribes correlation across service boundaries, separation of audit from diagnostics, and both black-box and white-box monitoring
- **Classification:** RECOMMENDATION · **Origin:** MS
- **Evidence:** *"Log events at service boundaries. **Include a correlation ID that flows across service boundaries.** If a transaction flows through multiple services and one of them fails, the correlation ID helps you track requests across your application and pinpoint why the transaction failed."* *"**Separate application and agent logging from auditing.** Audit records are commonly maintained for compliance or regulatory requirements and must be complete. To avoid dropped transactions, maintain audit logs separate from diagnostic logs."* *"Use **white box** monitoring to instrument the application or agent with semantic logs and metrics… Use **black box** monitoring to measure platform services and the resulting customer experience. Black box monitoring tests externally visible application or agent behavior without knowledge of the internals of the system. This approach is common for measuring customer-centric service-level indicators (SLIs), service-level objectives (SLOs), and service-level agreements (SLAs)."* Also: *"Forward all diagnostic logs to a centralized data sink and analytics platform… If you have regional data sovereignty requirements, you must use local data sinks in the regions that are subject to those requirements."* *"Configure alerts to trigger when values pass critical thresholds that correlate to a health model state change… **Threshold configuration is a practice of continuous improvement.**"* *"Implement backup and recovery monitoring to capture: The data replication status to ensure that your workload achieves recovery within the target recovery point objective (RPO). Successful and failed backups and recoveries. The recovery duration"* (O-04).
**Cross-Block V2 implementation boundary.** A correlation ID across a broker/API seam is **not assumed to be automatic**. The solution must generate/accept an identifier at the first boundary, put it in message/API metadata and the status/audit record, propagate it through worker/backend calls, and emit it into the telemetry sink. This work has schema, storage, privacy and operational cost; see `integration-architecture.md` §15.6 and AP-03/AP-04/AP-05.

- **Why it matters:** Three of these are architecturally consequential rather than procedural. (1) **Correlation across boundaries** is the only way to diagnose a multi-hop Power Platform solution (app → flow → connector → external system), and it must be designed in — Power Platform's own correlation capability is experimental and limited to custom connectors (OP-11). (2) **Separating audit from diagnostics** matters because in Dataverse they are physically different things with different funding: audit consumes log capacity that no licence provides (LC-11), while diagnostics go to Application Insights. (3) **Black-box monitoring** is the only route to a customer-facing SLI, and Power Platform provides no built-in synthetic monitoring — so an external availability check is required, which has its own cost trap on Power Pages (OP-07 / LC-20).
- **Decision impact:** Requirement "we must be able to explain a failed transaction end to end" → correlation identifiers must be part of the design, propagated through custom connectors, and the receiving service must also emit to the same sink. Requirement "audit for compliance" → separate store, separate retention, separate capacity budget. Requirement "an SLA to the business" → an external black-box check, configured to avoid billing itself (OP-07).
- **Confidence:** HIGH · **Sources:** O-04

### 2.2 Ownership — the constraint that changes the architecture

#### OP-04 — Power Platform artefacts have a **runtime-significant owner**, and the consequences of an unowned artefact are automatic and severe
- **Classification:** CONSTRAINT + RISK · **Origin:** MS
- **Evidence:** Ownership sets throughput: *"A cloud flow uses the plan of its owner… **If the original owner leaves the organization, the flow reverts to the Low performance profile**"* (O-05, `ms.date` 2026-07-17). Ownership sets suspension exposure: *"Flows without trigger activity | 90 days | A cloud flow that isn't triggered within a 90 day period might be turned off. **Flows owned by users with premium licenses or assigned capacity licenses (Power Automate Process, per flow) aren't subject to this suspension.** Flow owners and co-owners are notified 30 days prior to suspension"*; *"Flows with errors | 14 days | A cloud flow that has a trigger or actions that fail continuously is turned off"*; *"Consistently throttled flows | 14 days"* (O-05). Notification goes to individuals: *"Be sure to monitor email for notifications about such flows"* (O-05). Deployment ownership: *"**Who owns deployed solution objects?** The deploying identity. For standard deployments, the owner is the requesting maker. For delegated deployments, the owner is the delegated service principal or user"* (O-06, `ms.date` 2026-01-12). Visibility is ownership-scoped: in the automation centre, *"Visibility of flows and their run history… requires you to be the **owner** (coownership isn't sufficient) of the flows or to have environment wide access"*, and *"Co-owned or shared flows aren't supported yet (runs of flows that are shared with them don't display)"*; admins with broad access *"might see **Unknown flow** as flow names"* (O-07, `ms.date` 2026-03-06). In PPAC Monitor, *"Makers can view data only for resources that they have edit privileges for in the runtime environment"* (O-08, `ms.date` 2025-11-20).
- **Why it matters:** This is the most under-appreciated operational fact about the platform. Ownership is not metadata — it is a **runtime dependency on an individual's employment status and licence**. A leaver silently degrades throughput by up to 50× (LC-26). A quarterly business-critical flow owned by a non-premium user is switched off between runs. Suspension warnings go to a personal mailbox, so an unowned or orphaned artefact receives its 30-day warning into a disabled account. And the monitoring surfaces are *ownership-scoped*, so a platform team can see aggregate health but may not be able to see the specific flow's history — the exact evidence needed during an incident.
- **Decision impact:** For any workload above the departmental class, ownership is an **architectural decision with a named outcome**: own business-critical automation with a service principal, or assign a capacity licence to the flow (which requires the flow to be in a solution, OP-15). Route suspension and failure notifications to a **shared mailbox or Teams channel**, not an individual. Establish environment-wide read access for whoever will be on call, because owner-scoped visibility will otherwise block diagnosis. Record the owner of every critical artefact as a reviewable fact, not an incidental property.
- **Confidence:** HIGH · **Sources:** O-05, O-06, O-07, O-08

#### OP-05 — Unclear ownership has a documented cascade, and the platform provides no default owner
- **Classification:** RISK · **Origin:** INF over MS facts
- **Evidence:** Assembling the mechanisms: no Microsoft page assigns a default owner to an app, flow or site; ownership is whoever created or deployed it (O-06). The consequences of that owner being absent or under-licensed are automatic: performance profile reversion, 90-day suspension, 14-day error suspension, 14-day throttling suspension (O-05). Notifications are individual (O-05). Monitoring visibility is owner-scoped (O-07, O-08). Support tickets can only be raised by admins: *"**End users can't open support requests** and must have their permissions elevated within the tenant to do this. There's no alternative to this experience"* (O-09, `ms.date` 2025-07-31). And restore breaks ownership-adjacent configuration: after a restore, *"Connection references require new connections"*, *"Review custom connectors and, as required, delete and reinstall them"*, and *"apps shared with Everyone aren't shared with Everyone in the restored environment"* (O-10, `ms.date` 2026-06-23).
- **Why it matters:** The failure chain is fully documented even though no single page states it: **no owner → no one receives the warning → the artefact is switched off → the business notices → the affected user cannot raise a ticket → an admin who does not know the solution must diagnose it → the monitoring surface shows "Unknown flow" because the owner is gone.** Every link in that chain is MS-sourced. It is the archetypal Power Platform production failure and it is entirely an ownership failure, not a technical one.
- **Decision impact:** Ownership must be *assigned and recorded*, at three levels that are genuinely distinct: **business owner** (decides whether the process still matters and accepts risk), **application owner** (accountable for the artefact's health, receives alerts, authorises change), **platform/operations** (holds environment-wide access, admin rights and the support-plan relationship). The first two are frequently the same person in a departmental solution and must not be in an enterprise one. Where no name can be given for the application owner, that is a gate condition, not a documentation gap.
- **Confidence:** MEDIUM (every link is MS-sourced; the cascade framing is INF) · **Sources:** O-05, O-06, O-07, O-08, O-09, O-10

#### OP-06 — Makers and operators see **different, partially non-overlapping** monitoring surfaces, and some products have no maker surface at all
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** *"The Monitor experience is available to both makers (in experiences such as Power Apps) and admins (in experiences such as the Power Platform admin center). Makers use the data to improve their resources. Admins use it to understand aggregate operational health in the tenant or in specific environments."* But coverage differs by product: *"**Power Automate and Copilot Studio don't have a monitoring page in their respective maker portals.** However, users can use the Power Automate Automation center and Copilot Studio Analytics tab for similar experiences."* The availability matrix: canvas apps and model-driven apps generally available in both admin and maker experiences; cloud flows and desktop flows *"Generally available"* in the admin centre but *"Not available"* in the maker experience; work queues public preview (admin only); **Dataverse "Not yet available"** in both; Copilot Studio agents public preview; Dynamics 365 apps *"Not yet available"* (O-08).
- **Why it matters:** Two operational gaps. (1) A **flow maker has no monitoring page in Power Automate** — they must use the automation centre, which has its own ownership restrictions (OP-04). (2) **Dataverse has no Monitor coverage at all**, so the component that most often causes a slowdown (service protection, PF-22) is the one with no health surface in the admin centre; its telemetry route is Application Insights, which requires a managed environment (OP-11). So the operational picture is assembled from four or five different places with different licence gates and different retention.
- **Decision impact:** A support model must name **which surface each role uses for which question**, because no single surface answers all of them: PPAC Monitor for aggregate app/flow health, Automation Center for automation run detail, Live Monitor for a specific session, Application Insights for correlated and retained telemetry, Purview for audit, PPAC Service Health for platform incidents. Requirement "one pane of glass" → only Application Insights approximates it, and it requires a managed environment plus an Azure subscription (OP-11).
- **Confidence:** HIGH · **Sources:** O-08

### 2.3 Monitoring and observability — what is actually available, and its limits

#### OP-07 — Service health and platform incidents are visible, and this is the one operational capability that needs nothing bought or enabled
- **Classification:** FACT · **Origin:** MS
- **Evidence:** *"You can view service health information for Dynamics 365 and Power Platform products in the Power Platform admin center"* via **Support → Service health**, filterable by product category, issue type (*"all issues, advisory issues, or incident issues"*) and status (*"all issues, active issues, or resolved issues"*) (O-11, `ms.date` 2025-06-25). In the support flow: *"Service health alerts notify you of active and recently resolved disruptions affecting your products and tenant… You can also view active and recently resolved alerts on the Support/Service Health page of the Power Platform admin center, and **in the Microsoft admin center (where you can subscribe for email updates)**"*, and *"**Known issues** represent bugs or product problems that product engineering teams identify and share. The details of the issue and any workarounds are provided"* (O-12, `ms.date` 2026-05-15). The reliability guidance says to use it: *"Incorporate cloud platform monitoring and alerting services, including platform-level health"* (O-04).
- **Why it matters:** It cleanly separates "the platform is broken" from "our solution is broken", which is the first question in any incident and the one most likely to be answered wrongly under pressure. Email subscription is available — but through the Microsoft 365 admin centre, not PPAC, so it is easily missed. The Known Issues register is materially useful and under-used: it is where a "our solution suddenly broke" incident is often already explained.
- **Decision impact:** Every support model, at every maturity class including departmental, should include: service-health email subscription to a **shared** mailbox, and "check Service Health and Known Issues" as the first triage step in the runbook. This is the cheapest operational capability available and requires no licence.
- **Confidence:** HIGH · **Sources:** O-11, O-12, O-04

#### OP-08 — Telemetry export to Application Insights is the real observability story, and it is **gated, lossy and per-artefact**
- **Classification:** CONSTRAINT + RISK · **Origin:** MS
- **Evidence:** **Dataverse and model-driven telemetry:** *"Data that has already been collected from a specific tenant or environment is pushed to your own Application Insights environment… The support, developer, and admin personas can use this feature to triage and resolve issues."* Correlation fields are provided: *"**operation_Id**: This links together all the operations in a single interaction"*, *"**session_Id**: This uniquely identifies all activities in a single user session"*. Privacy behaviour: *"**client_IP**: This field is always populated with 0.0.0.0 for compliance with privacy laws"* (O-13, `ms.date` 2024-08-13). The Dataverse stream scope: *"The Application Insights for Dataverse data stream currently provides performance data related to Dataverse API incoming calls, Dataverse plug-in execution calls, and Dataverse SDK calls"* (O-14, `ms.date` 2025-08-15). **Flow telemetry:** *"Power Automate telemetry flows into two tables on Application Insights – **Requests** (contains cloud flow runs) and **Dependencies** (contains cloud flow triggers and cloud flow actions)."* Gate: *"**This feature is turned on and supported for managed environments only.**"* Loss: *"**The logs powering the Power Automate telemetry in Application Insights aren't transactional data and hence are not 100% lossless. Small data losses on this telemetry data might happen due to temporary, non-repeating service issues.** Flow execution history available within the flow details in the Power Automate portal is transactional, and therefore provides full view of events, in case of transient missing log data on Application Insights."* Sovereignty: *"Export of Power Automate and Dynamics 365 Customer Service data isn't available in sovereign clouds, such as Government Community Cloud (GCC), Government Community Cloud - High (GCC High), and Department of Defense (DoD), currently"* (O-15, `ms.date` 2025-01-16). **Canvas app telemetry:** requires a tenant setting (*"your tenant admin needs to enable Canvas app insights"*), a **per-app connection string**, and *"**Play the published app to send events to Application Insights. Events don't send to Application Insights when you preview the app in Power Apps Studio.**"* Cross-tenant hazard: *"When you specify a connection string, remember that **data can be sent across tenants.** Trace events are sent to the App Insights resource that corresponds to the connection string you set for your app, even if the target App Insights instance is in a different tenant than the app."* And an import hazard: *"**Be cautious when importing existing .msapp files because connection strings for App Insights might be present.** Manually open the app after import to check that the correct App Insights connection string is used."* Unsupported: *"Offline player events aren't recorded. Events from mobile apps (iOS and Android) aren't recorded when the app is suspended."* Session-level performance telemetry exists (`timeToAppInteractive`, `timeToAppFullLoad`, `appLoadResult`, `appLoadNonOptimalReason`) but *"These events are accurate for canvas apps running in a web browser. **They aren't available for apps running in Power Apps mobile**, and their values might not always be available or accurate for custom pages"* (O-16, `ms.date` 2025-04-08).
- **Why it matters:** Four independent limitations, each of which changes what can be promised. (1) Flow telemetry requires a **managed environment**, so observability is licence-gated (→ LC-23) — an organisation that declined managed environments cannot export flow telemetry at all. (2) It is **explicitly not lossless**, so it cannot be the system of record; run history can, and expires at 30 days (OP-09). (3) Canvas telemetry is configured **per app via a connection string** that can point at another tenant and survives `.msapp` import — a data-exfiltration and misconfiguration surface, and one that is silently lost or wrong after a migration. (4) Mobile and offline are **not covered**, so an offline-first field solution is largely unobservable.
- **Decision impact:** Requirement "we must be able to diagnose production problems" → this is a managed-environment requirement and therefore a licensing decision taken in Options (→ LC-23). Requirement "audit-grade record of what the automation did" → **not** Application Insights (lossy); use run history within 30 days plus a business record (OP-09). Requirement "sovereign cloud" → flow telemetry export is unavailable; the operating model must be designed without it. Requirement "offline mobile solution" → telemetry gaps must be accepted and compensated with in-app logging to a business table. Treat the canvas connection string as a controlled configuration item, verified after every import and deployment.
- **Confidence:** HIGH · **Sources:** O-13, O-14, O-15, O-16

#### OP-09 — Run history is the only transactional record of automation, and it **expires in 30 days**
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** *"Run duration | 30 days"*; *"**Run retention in storage | 30 days** | Run retention is calculated using a run's start time"* (O-05). Microsoft names it as the authoritative source when telemetry is missing: *"Flow execution history available within the flow details in the Power Automate portal **is transactional, and therefore provides full view of events**, in case of transient missing log data on Application Insights"* (O-15). Meanwhile the automation centre's copy is separately governed: *"Older cloud flow run history might be missing for the selected date range filter. Missing run history might be due to your current environment's **time to live (TTL) configuration**, which is set to retain cloud flow runs for n-days only"*, and *"Cloud flow run history shown on the Overview and Runs tabs **might take up to an hour** to be available in Dataverse and the automation center"* (O-07).
- **Why it matters:** A three-way asymmetry that is easy to get wrong. The **authoritative** record (run history) is short-lived. The **retained** record (Application Insights) is lossy. The **queryable** record (automation centre / Dataverse `flowrun`) has a configurable TTL and up to an hour of lag. So there is no single store that is simultaneously complete, retained and prompt.
- **Decision impact:** Requirement "prove what the automation did N months ago" → the evidence must be written to a **business record** as part of the process, not left in run history or telemetry. This is a functional requirement on the automation design, discoverable in Discovery ("will anyone need to reconstruct this later, and how far back?"). Requirement "near-real-time operational dashboard" → the automation centre's up-to-an-hour lag rules it out; use Application Insights, accepting the loss.
- **Confidence:** HIGH · **Sources:** O-05, O-15, O-07

#### OP-10 — Purview activity logging is comprehensive but explicitly **not for real-time monitoring**
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** *"Power Platform resources log activities in the Microsoft Purview compliance portal. **Most events are available within 24 hours of the activity. Don't use this information for real-time monitoring.**"* Coverage spans Power Apps, Power Automate, Copilot Studio, Power Pages, Power Platform connectors, data policy activity logging, Power Platform administrative logs and Dataverse auditing (O-04). Dataverse auditing consumes **log capacity**, which no Power Apps or Power Automate licence accrues (→ LC-05, LC-11), and restoring audit logs *"can significantly increase the time it takes to restore an environment. Therefore, audit logs are excluded by default"* (O-10).
- **Why it matters:** It draws the line between two things routinely conflated. **Audit** answers "who did what, provably, for compliance" — complete, retained, 24-hour latency, capacity-consuming. **Monitoring** answers "is it healthy right now" — prompt, lossy, disposable. Microsoft's guidance to keep them separate (OP-03) is not stylistic; they have different completeness guarantees, different latencies, different funding and different restore behaviour.
- **Decision impact:** Requirement "compliance audit trail" → Dataverse auditing plus Purview, with the log-capacity cost budgeted (→ LC-11) and retention agreed. Requirement "operational alerting" → never Purview; use Application Insights alerts or PPAC Monitor alerts. Note the restore interaction: audit logs are excluded from restore by default and including them makes restore materially slower, so an audit-completeness requirement conflicts with a fast-recovery requirement and needs an explicit decision (→ OP-14).
- **Confidence:** HIGH · **Sources:** O-04, O-10

#### OP-11 — PPAC Monitor is aggregated, delayed, short-retention, percentile-only and partially licence-gated
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** Purpose: *"to bring attention to resources that have degraded operational health and highlight resources that have opportunities for improvement."* Prerequisites: *"**Tenant-level analytics must be turned on** to make data available for Monitor experiences"*; *"You must be assigned to the system administrator role of the environment to view the name of resources that belong to the environment"*; *"**Optional**: A **managed environment** is required to view Monitor recommendations."* The matrix confirms recommendations are unavailable without a managed environment, and that with tenant analytics off, *"health metrics, logs, recommendations"* are all unavailable. Nature of the data: *"**Metrics are calculated by aggregating daily event logs from runtime activity; they're not real-time.**"* Retention and precision, verbatim: *"Metrics are aggregated at a point in time, according to their aggregation rate. For example, the App open success rate metric is calculated daily and has only one value per day."* *"**Event logs in the monitoring experiences are available for only up to seven days.**"* *"**Metrics are available for only up to 28 days.**"* *"**Time-based metrics report out only the 75th percentile.**"* *"Only logs that are associated with metric recommendations are available."* And: *"To produce health metrics and generate recommendations, Power Platform Monitor experiences require runtime activity. **Unused resources don't appear in Monitor experiences.**"* Microsoft's own comparison with Application Insights: *"Power Platform Monitor includes recommendations for improving a metric. Application Insights doesn't automatically derive recommendations. Power Platform Monitor doesn't require Azure subscriptions. **Application Insights contains a superset of runtime event logs**… It allows for customer-defined data retention… It allows for custom traces… Event logs can be correlated and joined across resources"* (O-08).
- **Why it matters:** PPAC Monitor is a **trend and advisory** tool, not an operational one. Daily aggregation means it cannot detect an incident. Seven-day log retention means a post-incident investigation a week later has no logs. 75th-percentile-only reporting means the tail — where user complaints come from — is invisible. And recommendations, its distinctive value, require a managed environment. Microsoft states plainly that Application Insights is the superset.
- **Decision impact:** Do not present PPAC Monitor as the monitoring solution for a business-critical workload. Use it for periodic health review and for its recommendations; use Application Insights for incident detection, correlation and retention (accepting OP-08's gates). Requirement "investigate an incident from last month" → Application Insights with customer-defined retention is the only route. Requirement "alert on p95/p99 latency" → not available in PPAC Monitor.
- **Confidence:** HIGH · **Sources:** O-08

#### OP-12 — Live Monitor and the Automation Center cover the diagnostic middle ground, each with named blind spots
- **Classification:** FACT · **Origin:** MS
- **Evidence:** **Live Monitor:** *"Live monitor is a tool that offers makers the ability to view a stream of events from a user's session to diagnose and troubleshoot problems. Makers of canvas apps can use Live monitor either to view events while building a new app in Power Apps Studio or **to monitor published apps during runtime**. Makers of model-driven apps can monitor page navigation, command executions, form-related issues, and other major actions."* It answers concrete operational questions Microsoft lists: *"A high number of network calls… Retrieve data from the same data source… The response data size… The duration of the request… **Errors — Have you configured the required permissions to run the app correctly? Are your requests throttled by the platform?**"* Per-event detail includes HTTP status, duration, data source, control, property, response size, and the request/response bodies. Access requires *"Environment Admin or Environment Maker"* (canvas) or *"System Administrator or System Customizer"* (model-driven). It has a documented unsupported-scenarios list (O-17, `ms.date` 2024-11-14). **Automation Center:** covers *"cloud and desktop flow execution data"*, work queue SLA health, machine status, error trends, AI Builder activity, savings and capacity utilisation. Gates: *"Data under the **Work queues** tab is a premium feature, which requires a Power Automate Premium license"*; *"*Recommendations* is a premium feature, which requires a **Managed Environment**"*. Blind spots: *"Cloud flow-based filtering **only lists cloud flows that exist within a solution** in the current environment"*; *"**Only runs for solution-based cloud flows are available** in the automation center"*; *"Top-level desktop flow runs aren't supported yet"*; *"Co-owned or shared flows aren't supported yet"*; ownership (not co-ownership) or environment-wide access is required; *"Users with broader access to run data might encounter increased latency during data load because of high cloud flow run volumes"*; and *"There's a limit of 40 connection statuses displayed at one time"* (O-07).
- **Why it matters:** Live Monitor is the strongest diagnostic tool in the platform for a *reproducible* problem — it shows the actual HTTP traffic, including throttling, on a live published session. Its limitation is that someone must be watching while the problem happens. The Automation Center is the operational console for automation, and its **solution-only** restriction is the operationally decisive detail: a flow built outside a solution is invisible to it. That converts an ALM choice into an observability outcome (→ OP-15).
- **Decision impact:** Include Live Monitor in the runbook as the standard tool for reproducible user-reported problems, and pre-provision the required security roles to whoever is on call (this is an access decision to make before the incident). For automation, **build in solutions** or accept that the Automation Center cannot see the runs. Requirement "work queue SLA monitoring" → Power Automate Premium. Requirement "automation recommendations" → managed environment.
- **Confidence:** HIGH · **Sources:** O-17, O-07

#### OP-13 — Alerting is available but must be constructed, and Microsoft flags its cost
- **Classification:** PATTERN + TRADE-OFF · **Origin:** MS
- **Evidence:** The mapping for flow alerts is explicit: *"**Cloud flow runs** are mapped to **Requests** table, and fall into **Server Requests** signal name. Therefore, any alerts that refer to **Failed requests** directly map to cloud flow run error. **Cloud flow triggers** and **cloud flow actions** are mapped to the **Dependency calls** signal name. Hence, any alerts that refer to **Dependency call failures** map to action or trigger errors."* Environment- or flow-scoped alerting needs KQL: *"When you want to restrict alerting for a specific environment, or a specific set of flows or actions, consider **Custom log search**"*, with worked queries filtering on `customDimensions['environmentId']` and `customDimensions['resourceId']`. Action groups can *"use a webhook to trigger a Power Automate flow to do more advanced notifications using Microsoft Teams or other communication channels"* (O-15). PPAC Monitor has its own alerts: *"The cards on the Overview page highlight the state of your triggered custom and predefined alerts"* (O-08). Canvas apps can emit unhandled Power Fx errors, with two warnings: *"**Warning: Enabling the Pass errors to Azure Application Insights setting might incur additional costs for storing Application Insights logs**"*, and the feature is *"an experimental feature… not meant for production use"*; correlation tracing carries the same cost warning and *"works only with custom connectors. Other connector types aren't supported"* (O-16). Microsoft's cost callouts: *"**Tradeoff**: There are cost implications for storing and querying logs. Notice how your log analysis and retention affects your budget"* (O-04) and *"**Tradeoff**: Logic monitoring tools are likely to increase costs"* (O-14).
- **Why it matters:** Everything needed for real alerting exists — but as an **assembly job** in Azure, requiring KQL for anything scoped, and priced. Two of the most valuable canvas capabilities (unhandled-error reporting and correlation tracing) are **experimental** and therefore unsuitable for the production workloads that most need them, and correlation tracing only works with custom connectors, which is precisely the boundary where multi-hop diagnosis matters most.
- **Decision impact:** Requirement "we must be alerted when the automation fails" → Application Insights alert rules on Failed requests / Dependency call failures, with an action group; and for anything scoped to an environment or flow set, a KQL custom log search. Budget log ingestion and retention as an operating cost (→ LC-21). Do not design a production operating model that depends on the experimental canvas features; instead emit deliberate `Trace()` events for the errors that matter. Route alerts to a shared destination (OP-04).
- **Confidence:** HIGH · **Sources:** O-15, O-08, O-16, O-04, O-14

### 2.4 Production operations

#### OP-14 — Backup is continuous and automatic, but restore is **constrained, destructive to configuration, and blocked by capacity**
- **Classification:** CONSTRAINT + RISK · **Origin:** MS
- **Evidence:** Backup: *"The system automatically creates backups for environments that have a database. By default, the system retains backups of all production and nonproduction environments for **seven days**. However, for production **managed environments**, you can extend the retention period up to **28 days**."* *"System backups occur continuously. The underlying technology is Azure SQL Database."* Retention by type: production, sandbox, developer, Teams and default all 7 days; **Trial: "Not backed up"** and manual backups *"Not supported"*. Restore constraints: *"**You can't directly restore backups to production environments.** To restore a backup to a production environment, first change the environment type to sandbox, perform the restore, and then switch the environment type back to production."* *"**You must restore an environment in the same region where it was backed up.**"* *"You can restore a **managed environment only to another managed environment.** You can't restore a non-managed environment to a managed environment."* CMK and enterprise policies must match; VNet-enabled environments must share the enterprise policy. Capacity: *"To restore an environment, you need **1 gigabyte (GB) of free capacity**"*, and being over capacity blocks restore entirely (→ LC-10). Coverage: *"**Backup and restore operations include only apps (created by using Power Apps) and flows (created by using Power Automate) in a Dataverse solution.**"* Duration: *"Copying and restoring data might take **more than one day**, depending on the size of the data, especially if you must copy audit data."* No export: *"Downloading a copy of a database backup for offline use isn't supported"* and *"You can't get a copy of your database backup."* Post-restore state: *"The newly restored environment is put in **administration mode**."* And the configuration damage, verbatim: *"**Flows** – In the target environment, existing solution flows are deleted, but existing nonsolution flows remain… **Solution flows are turned off.** Therefore, enable flows as required. **Connection references** – Connection references **require new connections**. Create and set connections on connection references. **Custom connectors** – Review custom connectors and, as required, **delete and reinstall** them."* Also *"apps shared with Everyone aren't shared with Everyone in the restored environment"* and *"**Not for canvas apps.** The app ID for a canvas app in a restored environment differs from the app ID when an environment was backed up."* Deleted environments are recoverable *"within seven days of deletion"*, or *"up to 28 days"* for production environments with Dynamics 365 applications. Failure handling: *"If the restore operation fails, the target environment is disabled… Wait 30 minutes and retry"* (O-10, `ms.date` 2026-06-23).
- **Why it matters:** This is the most operationally consequential finding in the file, because almost every assumption a team makes about restore is wrong. **Restore is not a rollback.** It cannot target production directly; it does not restore non-solution artefacts; it deletes solution flows in the target and leaves non-solution ones; it breaks every connection reference; it changes canvas app IDs (breaking every bookmark and deep link); it silently un-shares apps shared with Everyone; it may take over a day; it requires free capacity; and it must stay in-region and match managed/CMK/VNet state. A restore is therefore a **project**, not a button, and the environment comes back in administration mode with automation switched off.
- **Decision impact:** Recovery must be **designed and rehearsed**, not assumed, and the recovery runbook must include: reconnecting connection references, re-enabling solution flows, reinstalling custom connectors, re-sharing apps, and publishing new canvas app links. Requirement "the solution must be recoverable" → the artefacts must be **in solutions** (OP-15), because that is the boundary of backup coverage. Requirement "retain more than 7 days of restore points" → production managed environment, i.e. a licensing decision (→ LC-23). Requirement "recovery within N hours" → restore duration is data-dependent and can exceed a day; test it and measure, because no figure is published. And never put a business-critical workload in a **trial** environment: it is not backed up at all.
- **Confidence:** HIGH · **Sources:** O-10

#### OP-15 — Being **in a solution** is the operational boundary for almost everything
- **Classification:** DECISION CRITERION · **Origin:** MS
- **Evidence:** Backup coverage: *"Backup and restore operations include **only** apps… and flows… **in a Dataverse solution**"* (O-10). Capacity licensing: *"**Flows must be in a solution for a Process license to be assigned**"* (O-18, `ms.date` 2026-07-20). Automation Center visibility: *"**Only runs for solution-based cloud flows are available** in the automation center"* and *"Cloud flow-based filtering only lists cloud flows that exist within a solution"* (O-07). Pipelines: *"Pipelines deploy **solutions** as well as configuration for the target environment such as connections, connection references, and environment variables"*, and *"Pipelines can't be viewed or run from the **default solution**, managed solutions, or in target environments"* (O-06). Per-user artefact ceiling: *"Number of flows owned by a single user | 600 | **Use flows under solutions if you need more than 600**"* (O-05). Restore asymmetry: *"existing solution flows are deleted, but existing **nonsolution flows remain**"* (O-10).
- **Why it matters:** "Put it in a solution" is normally presented as an ALM best practice — a matter of tidiness. It is not. It is the **precondition for being backed up, being licensable by capacity, being monitorable, and being deployable**. A flow outside a solution is: invisible to the Automation Center, ineligible for a Process licence (so stuck on the owner's performance profile, LC-26), outside backup coverage, and undeployable by pipeline. That is four independent operational failures caused by one apparently cosmetic choice.
- **Decision impact:** For anything above the departmental class, **solution-aware artefacts are a hard requirement**, decided at the start, because retrofitting is rework. This is the cleanest example of an operational requirement changing the build: it dictates how artefacts are created on day one. Note the restore asymmetry as a trap — a mixed environment restores inconsistently, deleting the managed half and keeping the unmanaged half.
- **Confidence:** HIGH · **Sources:** O-10, O-18, O-07, O-06, O-05

#### OP-16 — Pipelines make governed deployment achievable, and every non-development environment in the pipeline must be a **managed environment**
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** Licensing: *"Developer environments aren't required to be managed environments. They can be used for development and testing with the developer plan. The pipelines host should be a production environment, but the pipelines host doesn't have to be a managed environment. **All other environments used in pipelines must be enabled as managed environments. Licenses granting premium use rights are required for all managed environments.**"* Coming change: *"**Starting February 2026, Microsoft will start enabling managed environments for any pipeline target environments that aren't already enabled.** Customers will be notified via Microsoft 365 Message center."* Integrity: *"Solutions are exported as soon as a deployment request is submitted… and the same solution artifact will be deployed. Similarly, the system doesn't re-export a solution for deployments to subsequent stages… **The system also prevents any tampering or modification to the exported solution artifact. This ensures customization can't bypass QA environments or your approval processes.**"* Backups: *"**Does pipelines automatically store solution backups?** Yes. Both managed and unmanaged solutions are automatically exported and stored in the pipelines host for every deployment."* Approvals and identity: delegated deployments support approvals and service principals; *"Who owns deployed solution objects? The deploying identity."* Documented limitations: *"**Can pipelines deploy to a different tenant?** No. We recommend using Azure DevOps or GitHub for this scenario."* *"**Can I deploy multiple solutions at once?** Not currently. You'll need to submit a different deployment for each solution."* *"**Can I specify advanced solution import behaviors such as update versus upgrade?** Not currently. Pipelines default import behavior is **Upgrade without Overwrite customizations**."* *"**Can I roll back to a previous version?** Yes. **If the pipeline setting is enabled**, you can redeploy previous solution versions… If the setting is disabled, only higher solution versions can be deployed."* *"**Why can't I update existing connection references?** Currently, connection references without a value in the solution or targeted environment can't be updated during deployment."* *"Power BI Dashboards (preview) and Power BI Datasets (preview) are not currently supported in pipelines."* *"The current implementation uses a **single development environment for a given solution**"* — so isolated multi-developer environments are not supported. Cross-geo deployment requires an explicit setting; otherwise all environments must share a geography. *"Do pipelines publish unmanaged customizations before exporting the solution? **Not currently.**"* (O-06, `ms.date` 2026-01-12).
- **Why it matters:** Pipelines genuinely deliver what OE:05 and OE:10 ask for — predictable, quality-gated, tamper-proof promotion with automatic artefact retention and optional approvals — and they do it without Azure DevOps. But the licence gate is absolute (**premium use rights for every managed environment in the pipeline**), and the February 2026 auto-enablement means organisations using pipelines will acquire managed environments whether they planned for them or not, with the licence consequences that follow (→ LC-23). The rollback caveat is the operational trap: **rollback is off unless enabled**, and without it only higher solution versions can be deployed — so the OE:11 "deployment failure mitigation strategy" is a setting someone must have turned on before the incident.
- **Decision impact:** Requirement "governed, auditable deployment" → pipelines, budgeted with premium licences for every managed environment (a cost consequence of an operational requirement). **Enable the previous-version redeployment setting before go-live**, or accept that rollback means a manual artefact download, a version increment in `solution.xml` and a manual import — Microsoft's documented workaround. Requirement "cross-tenant deployment" or "multi-developer isolated environments" → pipelines do not support it; Azure DevOps or GitHub. Requirement "publish before export" → publish individual objects as they are saved, because the pipeline will not do it.
- **Confidence:** HIGH · **Sources:** O-06

#### OP-17 — Connections, connection references and service accounts are the fragile part of every deployment and every recovery
- **Classification:** RISK · **Origin:** MS
- **Evidence:** After restore: *"**Connection references require new connections.** Create and set connections on connection references"* and *"Review custom connectors and, as required, delete and reinstall them"* (O-10). In pipelines: connection references *"without a value in the solution or targeted environment can't be updated during deployment. If a value was deployed previously, it can be updated"*; *"makers running pipelines can either provide their own connections or connections they have access to. **Service principal connections can also be used** for connectors that support service principal authentication, including custom connectors"*; and *"Admins can even preconfigure certain connections that will be used"* (O-06). Ownership determines the identity that runs: for automated and scheduled flows the owner's entitlements apply; for instant and app-triggered flows the invoking user's do (→ LC-19). Licensing depends on an invisible link: an automated flow is covered by the app's Power Apps entitlement only if *"linked to the app using a PowerShell script"* (→ LC-06). And the connection identity model itself is carried in `automation-architecture.md` (AT2-48: embedded credentials versus "Provided by run-only user", and secret exposure via run history).
- **Why it matters:** Connections are the seam where identity, licensing, deployment and recovery all meet, and they are **not** carried by the artefact. Every restore breaks them. Every deployment must supply them. The identity behind them determines both what the automation can do and whose entitlement it consumes. And the app-flow link that preserves licensing is a PowerShell-set property invisible in the maker experience — so it is silently lost when a solution is redeployed by someone who does not know it exists.
- **Decision impact:** Treat connections and connection references as **first-class configuration items** with a documented inventory: which reference, which connector, which identity, which credential store, who owns it, and what it costs if it is wrong. Prefer **service principals** for connectors that support them, so the connection does not depend on an individual (reinforcing OP-04). Include connection reconnection as an explicit, timed step in the recovery runbook (OP-14). Record any PowerShell-set app-flow links as configuration that must be re-applied after deployment.
- **Confidence:** HIGH · **Sources:** O-10, O-06, AT2-48

#### OP-18 — Disaster recovery is a customer-operated capability, and Microsoft publishes **no prescriptive test plan**
- **Classification:** CONSTRAINT + RECOMMENDATION · **Origin:** MS
- **Evidence:** The self-service model, its gates and its cost are in PF-41 and LC-24. The operational half: *"A disaster recovery drill lets you do self-service disaster recovery without losing any data. The duration of the failover action can be slightly longer while all remaining data is replicated… **Run drills on a copy of a production environment, since this process involves downtime when failing over to remote region that can last for minutes.** For example, you might want to copy a production environment to a sandbox environment and then change the type from sandbox to production."* Emergency failover: *"When you start an emergency response, you see the **amount of data loss shown in time**. Compare this data loss to your recovery point objective to check if it's acceptable before you continue."* Replication lag is observable on demand: *"To check data replication latency at any time, select Disaster Recovery, and then select Emergency response as the disaster recovery reason. This action opens a confirmation dialog that shows the last replication time."* And the gap, verbatim: *"**Microsoft doesn't currently publish a prescriptive disaster recovery test checklist that all customers must follow.** However, you should validate both the Dataverse platform failover and your broader application ecosystem as part of your business continuity plan."* Microsoft's suggested validation set covers platform (drill failover/failback, user access, security roles, app functionality, verify RTO/RPO), **integration** (*"Validate all Azure integrations and external APIs. Test custom plugins, custom code, and middleware dependencies. Verify Power Automate flows function as expected… Validate all third-party plugins and mission-critical connectors"*, and *"Validate failover readiness: Confirm the environment can use the corresponding subnet in the disaster recovery (DR) region after SSDR failover"*), **reporting** (refresh Synapse Link and data lake connections), and **operational readiness** (*"Validate monitoring, alerting, and incident response procedures. Confirm runbooks and escalation processes. **Ensure application owners understand failover and failback processes.** Conduct periodic compliance disaster recovery drills (**for example, quarterly recommended**)"*). Also: *"Perform disaster recovery drills or an emergency response before a real disaster strikes, so you can document all steps required for any integration points that are external to Power Platform."* And the known gap in drills: *"The DR drill validates the SSDR platform capability and operational readiness, but **it can't perfectly replicate a real regional outage because the primary production region stays healthy during testing.** You should validate any connectors that use hard-coded to primary region endpoints for failover and failback"* (O-19, `ms.date` 2026-08-20).
- **Why it matters:** Microsoft has moved both the *trigger* and the *test* to the customer. There is no published RTO commitment (PF-41) and no prescribed test plan — so a DR capability exists only to the extent the customer builds, drills and documents it. The named limitation of drills (the primary region stays healthy) is honest and important: a passing drill does not prove a real failover works, particularly for connectors with region-pinned endpoints. And the explicit call-out that **application owners must understand failover and failback** ties DR back to OP-04: without named owners there is no one to run it.
- **Decision impact:** Requirement "region-loss resilience" → the deliverable is a **documented, drilled runbook** covering the platform failover *and* every external integration, with a named owner and a periodic (quarterly-recommended) drill on a copy of production. Verify replication lag against the RPO regularly, since the figure is observable on demand. Audit connectors for hard-coded region endpoints as a specific pre-DR task. Where the customer cannot commit to drills, do not represent the solution as regionally resilient (→ OP-AP-09).
- **Confidence:** HIGH · **Sources:** O-19

#### OP-19 — A solution's real availability is set by its **weakest dependency**, and Microsoft says its commitments stop at the platform boundary
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** *"when Power Platform solutions connect to external systems—such as SQL Server, REST APIs, or other third-party services—**the RPO of those integrations are governed by the availability and recovery capabilities of the respective target systems, and fall outside the scope of Power Platform's resiliency commitments.**"* Named coverage gaps in the DR model: Business Events endpoints *"stop delivering events"* after failover and must be recreated; Fabric link *"doesn't currently provide a service level objective (SLO) for recovery time objective (RTO) or recovery point objective (RPO) during SSDR failover"*; *"Synapse Link isn't automatically recovered as part of the SSDR process"*; *"Copilot Studio conversation runtime requests fail until Microsoft restores the service in the primary region"*; Customer Insights – Data *"doesn't support self-service disaster recovery today"*; Project Operations *"aren't yet supported"*; *"Connectors might have recovery problems when dependent on external systems, like SharePoint, SQL server, or third-party applications"*; and *"You can't perform servicing actions, such as code deployments… while the environment is operating from the secondary region"* (O-19). The reliability pillar requires exactly this analysis: RE:02 flow rating and RE:03 failure-mode analysis (O-03).
- **Why it matters:** Power Platform's in-region numbers are strong (RPO ≈ 0, RTO < 5 min, PF-40) and they are **not the solution's numbers** when anything external is on the path. The named gaps are not edge cases: analytical replication, event publishing, agent runtime and every on-premises integration. And the servicing restriction means that while running from the secondary region the organisation **cannot deploy fixes** — so a regional outage freezes change control at the moment change is most likely to be needed.
- **Decision impact:** Availability must be stated **per business flow, across dependencies**, with the weakest link named. Never quote platform RTO/RPO as the solution's. For each critical flow, record: the dependency with the weakest recovery capability, whether it is covered by SSDR, and what the manual recovery step is (recreate Business Events endpoints, relink Synapse/Fabric, re-establish connectors). Include "no deployments while failed over" in the incident-command assumptions.
- **Confidence:** HIGH · **Sources:** O-19, O-03

#### OP-20 — Environment strategy is an operational control, and the environment **type** carries hard operational consequences
- **Classification:** DECISION CRITERION · **Origin:** MS
- **Evidence:** Production-type is required for the platform's own resilience: *"This in-region capability is for production environments that host business-critical application processes and data. **To avoid disruption, don't deploy production processes and data in nonproduction types like sandbox, developer, or trial environments**"* (O-19). Backup differs by type, and **trial environments are not backed up** (O-10). Restore targets are constrained by type: *"The target environment can be a sandbox, developer, or Teams environment. If the source is a default environment, the target must be a developer environment"*, and managed↔managed only (O-10). Cross-region DR is *"available only for production environments"* (O-19). Pipelines require managed environments for every non-development stage (O-06). Service protection headroom differs: *"**Trial environments allocate only a single web server**"* (→ PF-22). Capacity differs: every environment consumes 1 GB, while trial, preview, support and developer *"don't count"* (→ LC-25). And a testing constraint: PE:05 asks the test environment to *"Mirror your production environment"* including *"environment settings and region, network settings, security settings, data sources, and integrations"* (O-20, `ms.date` 2026-07-17) — which a non-managed sandbox cannot fully do against a managed production environment.
- **Why it matters:** Environment type is usually chosen for cost or convenience and is in fact an **operational capability selector**: it determines whether the workload is zone-redundant, whether it is backed up, how long backups are kept, whether it can be a DR source, whether it can be a pipeline target, how much service-protection headroom it has, and whether it counts against capacity. The trial environment is the standout hazard — no backup, single web server, and no restore support.
- **Decision impact:** Encode the topology decision with these consequences visible: production-type for anything business-critical (non-negotiable for zone redundancy and DR); developer-plan environments for development, where they are free of both capacity cost and managed obligations (O-06 endorses this); managed environments where the operational feature set is required, accepting the licence consequence; and never trial for anything that matters. Note the honest limitation on test fidelity: a non-managed test environment cannot faithfully emulate managed production, so some managed-environment behaviour is only testable in a managed environment — which has a cost (→ LC-25, §4 CO:08).
- **Confidence:** HIGH · **Sources:** O-19, O-10, O-06, O-20, PF-22

#### OP-21 — Nearly the entire operational feature set sits behind **managed environments**, and therefore behind premium licensing
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** *"Managed environments are a suite of **premium capabilities** that allow admins to manage Power Platform at scale with more control, less effort, and more insights."* The list includes, operationally: *"Environment groups; Limit sharing; Weekly usage insights; Data policies; **Pipelines in Power Platform**; Solution checker; **IP Firewall**; IP cookie binding; **Customer Managed Key (CMK)**; **Lockbox**; **Extended backup**; Data policies for desktop flow; **Export data to Azure Application Insights**; Administer the catalog; Default environment routing; **Virtual Network support**; Conditional access on individual apps; Control which apps are allowed in your environment; Create and manage masking rules."* Entitlement: *"included as an entitlement with standalone Power Apps, Power Automate, Microsoft Copilot Studio, Power Pages, and Dynamics 365 licenses"*, but *"**Managed environment isn't included as an entitlement in the Developer Plan** when users run their assets"* (O-21, `ms.date` 2026-02-23). Corroborated at each point of use: extended backup to 28 days for production managed environments (O-10); flow telemetry export *"for managed environments only"* (O-15); PPAC Monitor recommendations require a managed environment (O-08); Automation Center recommendations require a managed environment (O-07); pipelines require premium use rights for all managed environments (O-06); SSDR requires *"a managed environment… premium license tier"* (O-19).
- **Why it matters:** Every capability required to *operate* a solution responsibly — telemetry export, extended backup, DR, governed deployment, network isolation, customer-managed keys, DLP for desktop flows, sharing limits, app allow-listing — is on one side of a single licence boundary. So **operational maturity is bought, not configured**, and buying it changes the licence footprint of every user in the environment. The Developer Plan carve-out closes the obvious workaround.
- **Decision impact:** This is the pivotal decision in the whole area, and it belongs in Options, not in a post-deployment operations review: *criticality → operational requirements → managed environment → premium licences for that environment's users* (→ LC-23). Practical consequence: an organisation whose users are licensed only through Microsoft 365 seeded rights **cannot** have telemetry export, extended backup, DR or pipelines. If the workload needs those, the licence model must change — and that changes the option's economics, not merely its runbook.
- **Confidence:** HIGH · **Sources:** O-21, O-10, O-15, O-08, O-07, O-06, O-19

#### OP-22 — Capacity overage is an **operational** failure, not just a bill
- **Classification:** RISK · **Origin:** MS
- **Evidence:** *"The following administrative environment lifecycle operations aren't available when the required storage capacity isn't available to support the operation: Create a new environment (requires minimum 1-GB capacity available); **Copy an environment; Restore an environment;** Convert a trial environment to paid; **Recover an environment**; Add Dataverse database to an environment."* Notifications at 15% and 5% remaining, then over. And the commercial backstop: *"If your storage consumption exceeds the documented entitlements or usage limits, **Microsoft might suspend use of the online service.** Microsoft provides reasonable notice before suspending your online service"* (O-22, `ms.date` 2026-08-17). Restore explicitly requires *"1 GB of available capacity"* (O-10).
- **Why it matters:** Being over capacity does not degrade the running solution — it disables **restore, copy, recover and environment creation**. So the failure is discovered at the worst possible moment: during an incident, or when trying to stand up a test environment to reproduce one. And the documented right of suspension makes a finance oversight into an availability risk.
- **Decision impact:** Capacity headroom is a **recoverability requirement** owned by operations, not a finance metric owned by procurement. Encode: monitor database, file and log independently; treat the 5% notification as an incident-readiness alarm; maintain ≥ 1 GB free as a standing restore precondition; and give the tenant capacity pool a **named owner**, because it is shared across projects and no project-level view exists (→ LC-10, OP-U-05).
- **Confidence:** HIGH · **Sources:** O-22, O-10

#### OP-23 — Administrative and deployment operations are **load events on production**
- **Classification:** CONSTRAINT · **Origin:** MS-A
- **Evidence:** *"Microsoft recommends that you don't execute operations that require concurrent database transactions. Also, don't execute operations that require intensive database transactions **during normal business hours**, when users are most likely to access the system. Example operations… include: Enable one or more language packs; **Solution import, upgrade, delete, or export**; Install or upgrade apps from Microsoft Marketplace…; **Publish customizations**; Large bulk record operations, such as business unit changes"* (O-23, `ms.date` 2020-09-08 — **aged**). Corroborated by the current service-protection page: *"Batch operations, **importing solutions**, and highly complex queries can be very demanding"* (O-24, `ms.date` 2026-01-09). Restore duration: *"might take more than one day"* (O-10). Manual backup timing: *"Manual backups might take up to 10 minutes to process before they're available for restoration. Wait at least 10 to 15 minutes before attempting to restore"* (O-10).
- **Why it matters:** The mechanisms that make change safe — solution import, publishing, pre-change manual backups — are themselves load and time events. A team deploying during business hours to have people available is trading one risk for another, and a team that takes a manual backup and immediately restores it will find it is not yet available.
- **Decision impact:** Release windows are an **operational requirement with a performance basis** (→ PF-44). Bulk security-model changes (business-unit reassignment) belong in a maintenance window. Build the 10–15 minute manual-backup latency into the pre-change runbook. Where "frequent releases" and "no business-hours degradation" are both required, the resolution is a release calendar, not a configuration change.
- **Conditions:** The primary source is six years old; the *direction* is corroborated by the current O-24, but the specific list should be spot-checked (OP-U-02).
- **Confidence:** MEDIUM (aged, partially corroborated) · **Sources:** O-23, O-24, O-10

### 2.5 Support model — what Microsoft will and will not do

#### OP-24 — Microsoft support is tiered, ticket-gated, and **narrower than teams assume**
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** Access: *"You can access self-help resources in the Support experience without a support plan. **However, to create a support request, you must have an active support plan**"* — Subscription, Professional Direct, or Unified (O-12). Who may raise: *"Any users with the Power Platform admin roles… can submit a support request. **End users can't open support requests** and must have their permissions elevated within the tenant to do this. There's no alternative to this experience"* (O-09). Response times: Severity A *"Less than one hour"* on all tiers, 24×7; Severity B *"Standard: Less than four hours; ProDirect: Less than two hours; Unified enterprise: Less than two hours"*; Severity C *"Standard: Less than eight hours; ProDirect: Less than four hours; Unified enterprise: Less than four hours"*, business hours only. Scope by tier: *"Support for billing, subscription management issues, and technical break-fix issues is available at all support levels. **Advisory, escalation, and account management services are available at the Professional Direct and Microsoft Unified Support levels.**"* Severity discipline: *"Selecting **Severity A** for a low priority issue results in automatic downgrade"*; *"Microsoft might downgrade the severity level if the customer can't provide adequate resources or responses… Other situations where Microsoft might downgrade severity include **requests for RCA**, issues with **customized processes or code**, and tickets with proposed resolutions pending customer action."* Scope boundaries, all verbatim: *"**Technical support doesn't conduct RCAs as part of any support experience.**… RCAs are only provided to published service-related incidents when multiple customers or services aren't available… **Any other request for an RCA to a specific scenario impacting your tenant, won't be honored by the engineering team.**"* *"**Microsoft doesn't help correct damaged data.** Per the Service Provider License Agreement (SPLA), Microsoft doesn't have a legal obligation to change or correct data being corrupted due to malfunctioning software."* On performance: *"**The Microsoft Dynamics support team invests up to four hours of time on a break-fix case to assist. If after four hours the issue isn't resolved, consult a partner or the community forums for further investigation. The technical support incident is then closed.**… If, at any point it's determined that the cause points to custom code, partner or ISV software, something environmental, or anything else outside of core Microsoft code, the Microsoft Dynamics Support team provides evidence that supports this."* Non-reproducible or customised: *"the Microsoft Dynamics support team invests best effort support **up to four hours**… If after four hours, we haven't yet identified the repro steps of an issue, consulting a partner or the community forums is recommended… and the technical support incident is closed."* Diagnostics consent: *"**Microsoft can't access or run diagnostics on data in your tenant or environment without consent.**"* Preview features: *"Preview services and features are provided *as-is*, *with all faults*, and *as available*. **They are excluded from the Service SLAs**… Any technical support for a public preview service or feature is limited to break-fix scenarios and is available only in English with no around the clock support"* (O-09).
- **Why it matters:** Four expectations that are commonly wrong. (1) **No RCAs.** A business demanding a root-cause report after an incident will not get one from Microsoft; the customer must produce it, from telemetry they must have chosen to collect (OP-08). (2) **Four hours on performance**, then the case closes — so the four-hour investment is not going to resolve a design-level performance problem, and the design has to be right (→ PF-15, which also removes load testing). (3) **No help with corrupted data** — data-integrity recovery is entirely the customer's, which makes the restore constraints of OP-14 the whole recovery story. (4) **End users cannot raise tickets**, so an internal triage tier is mandatory, not optional.
- **Decision impact:** The support model must include an **internal first line** (because end users cannot escalate to Microsoft), an internal **RCA capability** with the telemetry to support it, and a **partner or internal engineering** capability for anything customised or performance-related. Support-plan tier follows from the criticality requirement and is a cost line (→ LC-22). Requirement "vendor-provided RCA after every Sev 1" → cannot be met; renegotiate or resource it internally. Never place a preview feature on a critical path: it is outside the SLA with English-only, business-hours break-fix support.
- **Confidence:** HIGH · **Sources:** O-09, O-12

#### OP-25 — Diagnosis requires customer **consent**, and support environments have a product-selection quirk
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** *"Set your contact preferences and advanced diagnostic consent… **Microsoft can't access or run diagnostics on data in your tenant or environment without consent. If you don't provide consent when it's required, a Microsoft support representative will contact you to update the consent before proceeding**"* (O-12). And: *"For some support requests, you're asked to request a support environment. **Currently, you can't create support environments for the Power Apps or Power Automate product options** in the 'What product were you using when the issue occurred?' field. To create a support request that includes a support environment for Power Platform issues, **select the Microsoft Dataverse product** for that field"* (O-12). Also a routing warning: *"Selecting 'Dynamics 365 Customer Service' for customer service with another product **misroutes and delays a request**"*, and *"Selecting **Technical** in order to submit an **Advisory** request results in closure of your request."*
- **Why it matters:** Small operational details with real incident-time cost. Consent is a **decision someone must be authorised to make under pressure**, and withholding it stalls the case. The support-environment quirk means a correctly-categorised Power Apps or Power Automate ticket cannot get the diagnostic environment it needs — the person raising it must know to select Dataverse instead. These are exactly the things that are learned during the first Sev 1 rather than before it.
- **Decision impact:** The runbook must pre-authorise (or name who authorises) advanced diagnostic consent, and record the product-selection guidance: Dataverse for Power Platform issues needing a support environment; Power Platform Administration for admin-centre issues; never Dynamics 365 Customer Service unless that is the product; Advisory versus Technical chosen correctly or the request is closed.
- **Confidence:** HIGH · **Sources:** O-12

### 2.6 Lifecycle after deployment

#### OP-26 — Deprecation is a **continuous, dated, externally-imposed** workstream
- **Classification:** RISK · **Origin:** MS
- **Evidence:** From the important-changes register (O-25, `ms.date` 2026-05-22, page updated 2026-08-14), a representative sample of recent and near-term items with their dates: **Power Automate mobile app deprecated 31 August 2026** — *"App removed from App Store and Google Play; no updates or support; push notifications cease"*, with approvals moving to Teams and notifications requiring replacement of the *"Send me a mobile notification"* action. **Editable Grid and Power Apps Read-Only Grid controls, March 2026** — *"will continue to function until further notice, after which they are no longer supported. These controls will receive critical security fixes only and no new features."* **Test Engine, April 2026** — *"Documentation and GitHub repository no longer maintained"*, replaced by Power Platform Playwright samples. **BYOK for Dataverse, 6 January 2026** — *"If your migration to CMK isn't completed by January 6, 2026, your environment will automatically revert to Microsoft-managed keys."* **Classic look for model-driven apps, April 2026** — *"All apps will use the modern, refreshed look by default… This timing applies to all release channels, including the semi-annual channel."* **Cards for Power Apps, 29 August 2025** — *"any Cards for Power Apps that have been built and shared in Microsoft Teams won't function."* **SQL Server connector V1 actions, 30 June 2025** — *"the applications using the V1 actions of SQL server will be impacted and might no longer function as expected."* **Personal Microsoft service accounts in Power Automate, 26 July 2025** — *"Access to any cloud flows associated with Microsoft service accounts are permanently removed, and these cloud flows are deleted."* **Viva Engage connector OAuth 2.0** — new connections blocked 1 September 2025, existing connections stop working 15 November 2025. **Create app from image or Figma, 21 October 2025.** Historic examples show the same pattern applied to authentication and runtime: WS-Trust/Office365 authentication retired progressively to April 2022; `jQuery 2.1.1` removed October 2023 (*"If custom code in web resources had a dependency on this library, it stopped working when this library was removed"*); Internet Explorer 11 blocked 31 October 2022; app-only tokens without a service principal unsupported from October 2024.
- **Why it matters:** Three properties make this a design consideration rather than a maintenance chore. (1) It is **continuous** — the register is never empty. (2) The dates are **Microsoft's**, not the customer's, so remediation competes with the roadmap on someone else's schedule. (3) Several items **delete or break things silently**: personal-account flows *deleted*; BYOK environments *auto-reverted*; jQuery removal breaking dependent custom code; connector OAuth connections ceasing to work. The failure mode is a working solution stopping on a published date that nobody was tracking.
- **Decision impact:** Encode deprecation monitoring as a standing operational duty with a named owner: the important-changes register plus the Microsoft 365 Message Center (which is also how the February 2026 managed-environment auto-enablement will be announced, OP-16). Provision for remediation as a **recurring cost line** (→ LC-29). Two design consequences: prefer supported, first-party, non-preview components on critical paths (deprecation risk is concentrated in preview, community and legacy components), and treat any dependency on a specific connector *version*, a bundled JavaScript library, or an authentication mode as a dated liability.
- **Confidence:** HIGH · **Sources:** O-25

#### OP-27 — The **CoE Starter Kit is no longer maintained**, and governance tooling has moved into the admin centre
- **Classification:** FACT + RISK · **Origin:** MS
- **Evidence:** ***"The Power Platform CoE Starter Kit is no longer actively maintained.** Its core capabilities are part of the Power Platform admin center. **Issues are no longer reviewed or addressed.** If you identify a potential security issue, please report it to the Microsoft Security Response Center."* And: *"The CoE Starter Kit remains available for existing and new deployments, but **it will not be enhanced with new capabilities.** Issues are no longer reviewed or addressed."* The replacement mapping: *"Use the **Inventory** experience to view and govern all apps, flows, and agents created across your tenant. Use the **Usage** experience to track adoption and identify top resources and their owners. Use the **Monitor** experience to track the operational health of heavily used resources. Use **Actions** to identify risks, enforce best practices, and take action on governance insights across your tenant."* Programmatic routes: *"Microsoft Power Platform CLI… Microsoft Power Platform API… Power Platform inventory API… Power Platform for Admins V2 connector"* (O-26, `ms.date` 2026-05-07).
- **Why it matters:** A significant discontinuity in the operational landscape. Any organisation whose Power Platform governance rests on the CoE Starter Kit is running **unmaintained software with no issue triage** — and, because the kit is itself built from Power Apps and Power Automate, it is subject to the same deprecation stream as everything else (OP-26) with nobody fixing it. The successor capabilities are admin-centre features, several of which are gated behind managed environments (OP-11, OP-21), so the migration path from a free kit leads to a licensed feature set.
- **Decision impact:** Do not recommend or assume the CoE Starter Kit for new work. Where a customer already runs it, record it as **technical debt with a migration path** to Inventory / Usage / Monitor / Actions, plus the CLI and inventory APIs for anything bespoke — and note the licence consequence of the parts that need managed environments (→ LC-21). Any prior operational guidance in this corpus that assumed the kit should be revisited.
- **Confidence:** HIGH · **Sources:** O-26

#### OP-28 — Retirement is an operational duty with no platform support, and orphaned artefacts have documented consequences
- **Classification:** RISK · **Origin:** INF over MS facts
- **Evidence:** No fetched page describes a retirement process for a Power Platform solution. The observable consequences of *not* retiring are documented: flows without trigger activity are turned off after 90 days unless owned by a premium or capacity licence, with owners notified 30 days in advance (O-05) — so an orphaned flow is disabled rather than removed, and the warning goes to a possibly-inactive mailbox (OP-04). Every environment consumes 1 GB regardless of content, and unused data continues to consume capacity (O-22). PPAC Monitor cannot see unused resources at all: *"Unused resources don't appear in Monitor experiences"* (O-08). Manual backups accumulate without limit: *"There's no limit on the number of manual backups that you can create"* (O-10). Azure's cost pillar names the discipline that Power Platform's does not: *"Regularly remove or optimize legacy, unneeded, and underutilized workload components"* (CO:07). The successor to the CoE kit provides the inventory: *"Use the Inventory experience to view and govern all apps, flows, and agents created across your tenant"* and *"Use the Usage experience to track adoption and identify top resources and their owners"* (O-26).
- **Why it matters:** The platform's response to abandonment is **silent disablement**, not cleanup. So an estate accumulates disabled flows, unused apps, orphaned connections and consumed capacity, none of which appears in the monitoring surfaces (which only show *active* resources) and all of which contributes to the capacity ceiling that blocks restore (OP-22). The absence of a retirement process is a real gap, and it compounds: nobody can tell whether a disabled flow was retired deliberately or died of neglect.
- **Decision impact:** Retirement should be an explicit lifecycle stage with a named owner and a checklist: confirm the business process has ended; export or archive the data per retention policy; remove connections and connection references (releasing the identities); delete the artefacts; reclaim capacity; retire the environment where it was single-purpose; and record the decision so a disabled artefact can be distinguished from an abandoned one. Use the Inventory and Usage experiences as the periodic review input. This is an area where aisa can add real value, because Microsoft supplies inventory but no process.
- **Confidence:** MEDIUM (the consequences are MS-sourced; the absence of a retirement process and the recommended practice are INF) · **Sources:** O-05, O-22, O-08, O-10, O-26, CO:07 via `licensing-cost.md` §4

## 4. Support-model reference

Not a Microsoft artefact — an INF synthesis of the ownership, tooling and support findings, offered as a checklist for what must exist rather than as a prescribed structure.

| Role | Answers the question | Needs | Sourced from |
|---|---|---|---|
| **Business owner** | "Does this process still matter, and do we accept this risk?" | Authority to accept risk, approve change and authorise retirement | OP-05, OP-28 |
| **Application owner** | "Is this solution healthy, and what changed?" | Named individual or team; receives alerts and suspension notices at a **shared** destination; edit privileges for maker monitoring surfaces; understands failover and failback | OP-04, OP-05, OP-08, OP-18 |

## 5. Support and operations anti-patterns

| # | Anti-pattern | Mechanism and documented consequence | Origin | Sources |

## 7. Conflicts (CONFLICTED)

**OP-C-01 — Managed environments described as an included entitlement, yet requiring premium licences.** O-21 says managed environments *"are included as an entitlement with standalone Power Apps, Power Automate, Microsoft Copilot Studio, Power Pages, and Dynamics 365 licenses"*; O-06 says *"Licenses granting premium use rights are required for all managed environments."* **Resolution:** consistent at different scopes — the *feature* costs nothing extra, but every user of the environment must hold a qualifying standalone/premium licence. Recorded because "included as an entitlement" is routinely read as "free", which it is not for a population licensed only through Microsoft 365. **Sources:** O-21, O-06.

**OP-C-02 — "Backups occur continuously" versus "create manual backups before major changes".** O-10 states both that *"system backups occur continuously"* and *"Because Azure SQL Database continuously makes backups, you don't need to make other backups"*, and that makers should *"Create manual backups before major customizations, applying a version update, or making significant changes."* **Resolution:** Microsoft explains it — a manual backup is *"just a timestamp and a label that reflects that timestamp"*, i.e. a named restore point over the continuous backup, not an additional copy. Recorded because the practice is valuable while the mental model behind it ("we have our own copy") is wrong: the label cannot be downloaded, exported, or kept beyond the retention window. **Sources:** O-10.

**OP-C-03 — Test environments should mirror production, yet non-managed environments cannot.** PE:05 requires *"Mirror your production environment… environment settings and region, network settings, security settings, data sources, and integrations"* (O-20). But managed-environment behaviour (DLP, sharing limits, IP firewall, telemetry export) exists only in managed environments, and pipelines explicitly permit development on non-managed developer-plan environments (O-06). **Resolution:** unresolved. Faithful mirroring requires a managed test environment, which has a licence cost; the documented pipeline pattern accepts a non-managed development environment. So some production behaviour is only testable at extra cost. Recorded as a genuine tension between the performance/reliability guidance and the ALM guidance. **Sources:** O-20, O-06, O-21.

**OP-C-04 — Support "invests up to four hours" versus 24×7 commitment to Severity A resolution.** O-09 says Severity A means *"you commit to continuous, 24x7 operation, every day with the Microsoft team until resolution"*, and separately that performance and non-reproducible cases receive *"up to four hours"* before the incident is closed. **Resolution:** partially reconcilable — the four-hour cap is described for break-fix performance and repro-identification cases rather than for confirmed platform outages. But the boundary is not defined, and a Severity A performance incident could plausibly fall under either. Marked CONFLICTED because the practical expectation a customer should hold is ambiguous. **Sources:** O-09.

**OP-C-05 — Aged deployment-window guidance versus the current platform.** O-23 (2020) names solution import and publish customisations as intensive database operations to avoid during business hours, describing a platform that has since moved to availability-zone replication and continuous Azure SQL backups. O-24 (2026) still lists solution import among demanding operations. **Resolution:** direction corroborated, specifics not vouched for. CONFLICTED by age rather than content. **Sources:** O-23, O-24.

## 11. Implications for the aisa knowledge model (pointers, not pack content)

- **Discovery-safe signals** implied by §3, all technology-neutral: `criticality_class`, `who_notices_failure`, `acceptable_time_to_detect`, `acceptable_time_to_recover`, `evidence_reconstruction_horizon`, `compliance_audit_required`, `named_application_owner_exists`, `internal_first_line_exists`, `on_call_arrangement_exists`, `change_frequency`, `change_window_constraints`, `rollback_expectation`, `region_loss_tolerance`, `dr_drill_commitment`, `external_dependency_recovery_capability`, `existing_support_plan_tier`, `existing_governance_tooling`, `expected_solution_lifetime`, `retirement_trigger`.
- **Signals that must not be collapsed:** *audit* and *monitoring* are different requirements with different completeness, latency, funding and restore behaviour (OP-10, OP-03). *Platform availability* and *business-flow availability* are different quantities (OP-19). *Backup exists* and *recovery is possible* are different claims (OP-14). *An owner is recorded* and *an owner will act* are different facts (OP-04, OP-05).
- **The pack's central operational question** should be the one from §0: not "does it have monitoring?" but "**who will notice, who will act, with what evidence, and what have they bought that lets them?**" All four parts are needed; three out of four is not an operating model.
- **Knowledge-state guidance.** `named_application_owner_exists` should be **Confirmed only with a name**, never assumed. `recovery_is_possible` should be **Risky** until a restore has been rehearsed, because OP-14 shows restore is a procedure rather than a button. `regional_resilience` should be **Risky** until a drill has been run, per Microsoft's own framing (OP-18). `dataverse_service_sla` can be sourced as 99.9% on the current Dataverse page; `end_to_end_availability_sla` remains **Unknown** (`OP-U-01`) until the applicable contractual services/dependencies are reconciled.
- **Natural revalidation triggers:** application owner leaving or changing role; support-plan renewal; any item on the deprecation register reaching its date; the February 2026 managed-environment auto-enablement; crossing the 15% capacity notification threshold; a DR drill result; the CoE Starter Kit's continued use becoming a security exposure.
- **The pack must be able to conclude that Power Platform is operationally inappropriate** for a given workload — most defensibly where the customer cannot supply an owner, cannot fund managed environments while requiring telemetry or DR, cannot accept the restore constraints for a recovery-critical workload, or requires vendor-provided RCAs that Microsoft does not offer.

## 13. Cross-Block V2 reconciliation

### 13.1 Architecture ↔ Operations — external estate
AP-02/AP-04/AP-05/AP-08/AP-10 introduce operational responsibilities outside Power Platform. Azure Well-Architected guidance for API Management and Functions explicitly requires monitoring, skills, safe deployment and incident-ready operations. For queue-based designs include dead-letter/replay ownership, backlog/oldest-message alerts and DR administration. A pattern with no operator remains **unavailable**, not merely high-cost (`architecture-patterns.md` Y-13).

Minimum operational contract for a cross-boundary pattern:
1. named service owner and on-call/escalation route;
2. end-to-end health model across Power Platform and external dependencies;
3. correlation identifier propagated across every seam (OP-03);
4. alert ownership for API error/latency, queue backlog/dead-letter, worker failures and Power Platform failures;
5. deployment/change route for both supply chains;
6. recovery order and reconciliation after restore;
7. telemetry retention/cost owner;
8. dependency/SLA inventory and known exclusions.

### 13.2 Availability — corrected boundary
Dataverse documents **99.9% uptime SLA**. The Microsoft licensing SLA repository confirms formal online-service SLA documents exist for covered Microsoft Online Services, but Cross-Block V2 could not reliably parse the currently applicable service document end-to-end. Therefore:
- cite 99.9% only for Dataverse and with date/scope;
- do not transform Power Platform RTO/RPO into an uptime commitment;
- do not multiply/average service percentages into a business-flow SLA without contractual scope and dependency modelling;
- retain OP-19: the weakest dependency governs the real flow objective.

Sources: `https://learn.microsoft.com/en-us/power-apps/maker/data-platform/why-dataverse-overview`; `https://www.microsoft.com/licensing/docs/view/Service-Level-Agreements-SLA-for-Online-Services`.

### 13.3 Security/Governance ↔ Operations
Advanced security controls add operational preconditions: key ownership/revocation for CMK, network policy and allowlists, privileged identities and audit/telemetry retention. Governance must name who operates those controls; licensing must fund the population and telemetry (`security.md` SEC-XB-01, `governance.md` GOV-XB-01, `licensing-cost.md` LC-30).

### 13.4 Recovery ↔ Integration/ALM
A restore is not the end of recovery for an integrated system. If one participant is restored to an earlier point while peers, queues or replicas retain later state, the solution is divergent. Runbook sequence: pause writers → identify restore boundary → replay/re-seed/reconcile → validate authoritative fields/invariants → resume. The reconciliation identity and manual disposition rights are security/governance concerns; the rules and schemas are versioned ALM artefacts.

### 13.5 Validation and testing
Operational readiness uses the shared V1–V4 model in `integration-architecture.md` §15.8. A load/pilot test can validate runtime behaviour; a pro-dev harness can validate regression; a managed test environment is required where production behaviour depends on managed/network/security controls. None of these claims that Power Platform supplies a native functional-test framework.
