## 2. The four automation shapes — a classification test, not a product list

v1 had no typology, so the same requirement could be read into two different architectures by two readers (review C-5). The four shapes below are distinguished by **what holds the state** and **what the unit of failure is**, which is what actually decides the technology.

| Shape | Defining question | State lives in | Unit of failure | Natural technologies |
|---|---|---|---|---|
| **WORKFLOW AUTOMATION** | Does a *business event* need a bounded sequence of steps, usually involving people or documents? | The run instance (ephemeral) plus the business record | The whole run | Power Automate cloud flow; BPF for the human-guidance part |
| **PROCESS ORCHESTRATION** | Does a *long-lived business process* need to survive waits, restarts, versioning and partial completion, with a durable notion of "where am I"? | An explicit, queryable process record outside the run | A step, individually resumable | Durable Functions; Logic Apps Standard (stateful); a Dataverse process table plus a re-triggering flow |
| **INTEGRATION ORCHESTRATION** | Does a *message* have to move between systems with delivery, ordering, dedup and poison-message guarantees? | The broker | The message | Service Bus / Event Grid plus an idempotent consumer (flow, Function or Logic App) |
| **DISTRIBUTED PROCESSING** | Does *volume or computation* have to be split across workers and recombined? | The job/partition ledger | The partition or item | Durable Functions fan-out/fan-in; dataflows; ADF; Dataverse bulk APIs |

**Classification test** (apply in order; the first "yes" fixes the shape):

1. Is the primary artefact a **message that must not be lost, duplicated or reordered**? → INTEGRATION ORCHESTRATION.
2. Does the work have to be **split and recombined**, or does one step need real computation rather than calls? → DISTRIBUTED PROCESSING.
3. Must the process **outlive a single run** — survive 30+ days, a deployment, a version change, or resume mid-way after failure? → PROCESS ORCHESTRATION.
4. Otherwise → WORKFLOW AUTOMATION.

**Why this matters architecturally.** Power Automate is a first-class WORKFLOW AUTOMATION engine and a competent *front door* to the other three shapes. It is not a state store (AT2-21), not a broker (AT2-18), and not a compute host (AT2-32). Most failed Power Automate architectures are a shape-2/3/4 requirement implemented as shape 1 — the anti-patterns in §7 are almost all instances of that single error.

- **Classification:** DECISION CRITERION. **Origin:** INF (the taxonomy is this file's synthesis; every capability fact behind it is MS-sourced in §5). **Confidence:** MEDIUM. **Sources:** synthesis over AT2-01…AT2-53.

## 4. Decision boundaries — POWER AUTOMATE / HYBRID / OTHER

The central output of this file. Each boundary is REQUIREMENT → CONSTRAINT → ARCHITECTURAL CONSEQUENCE, with origin.

### 4.1 Boundaries that keep the work in Power Automate

- **A human must decide, delegate, escalate, reject or cancel, within 30 days** → approvals are a first-class Dataverse-backed construct with five response models including sequential, reachable from Outlook, Teams and the action centre, on a **standard (non-premium) connector** → **POWER AUTOMATE**. Moving this leg to Logic Apps or Durable Functions means hand-building a task store, a notification surface and a response UI that Power Automate already ships (MS, AT2-23, AT2-24).
- **The trigger is an M365 / Dataverse / SaaS business event and the work is a bounded sequence of connector calls** → 1,400+ connectors on both platforms, business-user ownership, licence usually already paid → **POWER AUTOMATE**; the alternatives' technical advantage here is nil and their operating cost is not (MS, AT2-30, AT2-31).
- **Volume is high but the *processing* can be delegated** → Microsoft's own remedy for bulk work is `CreateMultiple` / batch / dataflows, not a different orchestrator → **POWER AUTOMATE as initiator and orchestrator, plus a bulk API or dataflow as the workhorse**. The flow stays inside its envelope because it issues one request instead of N (MS, AT2-05, AT2-08).
- **The organisation has no Azure operating model** — no subscription ownership, no on-call for Azure resources, no IaC pipeline → introducing Logic Apps Standard, Functions or Service Bus adds a second ALM pipeline, a second billing model, a second support rota and a cross-boundary correlation problem the requirement never asked for → **POWER AUTOMATE**, with the constraint documented and an explicit tripwire on the metric that would force the move (INF over MS facts, AT2-53).

### 4.2 Boundaries that force HYBRID

- **A step needs real computation** (algorithm, iteration to convergence, a library, document or image processing) → cloud-flow expressions are not a general-purpose imperative language (PS-08) and plug-ins cap at 2 minutes (PS-09) → **HYBRID: flow as the business-facing front door, Azure Function as the compute step** — Microsoft's own "no-cliffs" extension model. The Functions **plan** is part of this decision, not a later detail (MS, AT2-32).
- **Messages must not be lost, duplicated or reordered** → Service Bus provides sessions, duplicate detection, peek-lock and dead-lettering, and the Power Automate Service Bus connector exposes all of them (peek-lock triggers, `Session id: Next Available`, `MessageId`, an explicit Dead-letter action) → **HYBRID: Service Bus in front, flow as an idempotent consumer**. The claim that cloud flows have no equivalent native mechanism is inferred from its absence in the reference documentation — **treat as unsupported until verified** (MS for the mechanisms, INF for the absence; AT2-18, AT2-28).
- **A producer bursts faster than the consumer or downstream system can absorb** → the documented remedy is queue-based load levelling and competing consumers at the broker layer, not larger retry counts inside the automation tool; it also converts a whole-flow failure into a per-message failure → **HYBRID: broker between producer and flow**, except where the caller needs a synchronous answer, which is the documented exclusion (MS, AT2-26, AT2-27).
- **One business operation must succeed-or-fail atomically across Dataverse and anything else** → no cross-connector transaction construct exists; atomicity is available only inside Dataverse → **HYBRID: saga with per-step idempotency keys, compensating actions, a persisted in-doubt state, irreversible steps last, and a human fallback** — never a flow that "just retries", and never presented to the business as transactional (MS, AT2-16, AT2-17, AT2-19).
- **The process must outlive 30 days, or resume mid-way after a failure or a deployment** → the flow run duration is a 30-day hard ceiling *including pending approvals*, and run state is not addressable once the run ends → **HYBRID: state in a Dataverse process table (or Durable orchestrator state / Service Bus session state) with a scheduled flow resuming it** (MS, AT2-13, AT2-14).
- **Enterprise-grade observability is required** → native surfaces give a 30-day rolling run history and a per-flow view; Application Insights export adds queryable telemetry and alerting but is **Managed-Environments-only**, explicitly **not lossless**, and unavailable in sovereign clouds → **HYBRID: Application Insights for alerting and trends, run history or `FlowRun` as the transactional record**, with an explicit correlation id propagated across the boundary (MS, AT2-41, AT2-42, AT2-44, §6.4).

### 4.3 Boundaries that force OTHER

- **Logic must run inside the Dataverse transaction, or be immediate and unbypassable** → a cloud flow executes asynchronously, after the triggering operation has committed, so it can neither veto the operation nor guarantee that its own effect is visible to the next reader; a synchronous plug-in stage runs "within the database transaction" and its exception "causes the entire transaction to roll back" → **PLUG-IN / CUSTOM API** (MS for the plug-in semantics at PS-45; INF for the flow-side consequence, which follows from asynchronous execution; AT2-35).
- **Sustained high-volume Dataverse-internal automation** → a flow consumes the owner's daily entitlement *and* per-user service-protection budget, whereas "Service protection limits don't apply to data operations that originate from plug-ins and custom workflow activities" → **PLUG-IN / CUSTOM API** for the data-heavy leg (MS, AT2-04, AT2-35).
- **The definition genuinely needs more than 500 actions or 8 nesting levels** → Logic Apps Consumption **and** Standard carry the identical ceiling and prescribe the same remedy (nested workflows) → **child-flow decomposition, or DURABLE FUNCTIONS / a custom service** if the decomposition is itself the problem. "Move to Logic Apps because the flow is too big" is **not supported by evidence** (MS, AT2-30).
- **Fan-out/fan-in, sub-orchestrations, aggregator/monitor patterns, or control flow with mutable state** → the declarative designer does not express these; Durable Functions is the documented purpose-built answer → **DURABLE FUNCTIONS**, accepting determinism constraints, the in-flight versioning hazard and the November 2026 in-process migration as its price (MS, AT2-33, AT2-34).
- **Private-network-only runtime, managed identity, or RBAC that survives the author leaving** → Power Automate RBAC "works at the user level" and a flow reverts to the Low performance profile when its owner leaves; Logic Apps Standard offers VNet integration, private endpoints, managed identity and resource-level RBAC → **LOGIC APPS STANDARD / FUNCTIONS / CUSTOM** (MS-V framing over MS facts; AT2-31, AT2-44, AT2-49).
- **Continuous event streams** → Event Hubs is the documented technology for streams; a flow run per event is the wrong unit (MS, AT2-26; envelope not yet fetched — U-13).
- **An enterprise workflow/BPM engine or integration estate already owns this process class** → an organisational-fit criterion, not a technical limit; adding Power Automate duplicates the operating model rather than reducing it → **EXISTING ENGINE** (INF over PS-24/PS-41, AT2-52).
- **A stable API exists for the target system** → RPA automates a UI contract the target's owner never committed to keeping stable → **API > RPA**. RPA is justified only where no programmatic access exists, the system's remaining lifetime does not justify building one, and the volume fits the queue model (MS for the API-preference statement at PS-21; MEDIUM for the fragility framing; AT2-40).

## 5. Findings

### 5.1 The metering model — three independent limit systems (review C-2, C-3)

#### AT2-01 — A cloud flow's throughput class is a property of its **owner's licence**, not of its design, and it silently degrades when the owner changes
- **Classification:** CONSTRAINT + RISK · **Origin:** MS
- **Evidence:** "A flow's *performance profile* determines its Power Platform request limits." Profile membership: "Low | - Free - Microsoft 365 plans - Power Apps Plan 1, Per App plans - Power Automate Plan 1 - All license trials - Dynamics 365 Team Member - Microsoft Power Apps for Developer"; "High | Power Automate Process license, Power Automate per flow plan"; "Unlimited Extended | Pay-as-you-go flows, Dynamics in context flows running under service principal". "A cloud flow uses the plan of its owner. If a cloud flow is shared with multiple people, then generally the owner is the flow's creator… **If the original owner leaves the organization, the flow reverts to the Low performance profile.**" "If a user has multiple plans… the flow has the performance profile of the higher of the plans" (V-01, `ms.date` 2026-07-17).
- **Why it matters:** The same flow definition can lose 98% of its daily request ceiling (500,000 → 10,000) through an HR event, with no change to the flow and no design-time warning.
- **Decision impact:** Business-critical automation → assign a Process or capacity licence to the flow deliberately, or own it with a service principal; never let throughput depend on an individual's personal licence. Document the owner as an architectural decision.
- **Conditions:** The **Medium** profile's plan membership was not captured verbatim in this pass (the row was elided in the fetched extract); v1 recorded it from the same page as Power Apps Plan 2/per-user, Power Automate Plan 2/Premium and Dynamics 365 Enterprise/Professional — spot-check before encoding (U-01).
- **Confidence:** HIGH (owner-dependency, Low/High/Unlimited membership) / MEDIUM (Medium membership) · **Sources:** V-01

#### AT2-02 — Three different meters govern the same flow, they are evaluated separately, and the one that bites first is usually **not** the one people plan against
- **Classification:** DECISION CRITERION · **Origin:** MS
- **Evidence:** (1) **Power Platform requests (PPR)** — a per-owner or per-flow daily and 5-minute entitlement; "Both successful and failed actions count toward these limits. Retries and requests from pagination also count as action executions" (V-02, 2026-08-14). (2) **Dataverse service protection API limits** — per authenticated user, per web server, on a 300-second sliding window (V-03, 2026-01-09). (3) **Per-connector throttles** — published per connector, e.g. Service Bus "API calls per connection | 6000 | 60 seconds" (V-08), custom connectors "500 requests per minute per connection" (V-01), and for the SQL connector "Logic Apps & Power Automate | Shared Environment | CRUD | API calls per connection | 100 | 10 [seconds]" with "Concurrent calls per connection | 125" (DA, quoting the connector reference). Microsoft states the independence explicitly: "**Batch operations aren't a valid strategy to bypass entitlement limits. Service protection API limits and entitlement limits are evaluated separately**" (V-03).
- **Why it matters:** v1 answered "throughput" with the PPR table alone. A flow comfortably inside 500,000 requests/day will still fail with HTTP 429 after 6,000 Dataverse requests in five minutes by one identity, or after 100 SQL calls in ten seconds on one connection. Capacity planning that uses only the daily number is planning against the wrong meter.
- **Decision impact:** Any throughput requirement must be expressed in **three** units before a verdict: actions/day (entitlement), requests per 5 minutes per identity (service protection), and calls per connection per window (connector). The binding constraint is the smallest of the three, and it is normally the connector or service-protection one.
- **Confidence:** HIGH · **Sources:** V-01, V-02, V-03, V-08, DA-10

#### AT2-03 — The two published PPR number sets are not a contradiction: the licence page states the **official** limits, the flow limits page states the **higher transition-period** approximations, and Microsoft says so on the page

#### AT2-04 — Dataverse service protection limits are the real throughput wall for Dataverse-heavy automation, they scale with **licences purchased** rather than with design, and plug-in-originated operations are exempt
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** "Two of the service protection API limits use a five-minute (300 second) sliding window." Per web server: "Number of requests | 6,000 within the five-minute sliding window"; "Execution time | 20 minutes (1,200 seconds) within the five-minute sliding window"; "Number of concurrent requests | 52 or higher". "The system evaluates service protection API limits for each user. Each authenticated user has an independent limit." "Each web server that your environment makes available enforces these limits independently. Most environments have more than one web server. Trial environments allocate only a single web server… **One of the factors is how many user licenses you purchase**." Errors are 429 with a `Retry-After` header; "the more demanding the requests are, the longer it takes for the server to recover". Exemption: "**Service protection limits don't apply to data operations that originate from plug-ins and custom workflow activities.** Plug-ins and custom workflow activities run within the isolated sandbox service. Dataverse operations invoked on the sandbox service don't use the public API endpoints" — but "the extra computation time that these operations contribute is added to the initial request that triggered them" (V-03, 2026-01-09).
- **Why it matters:** Three consequences v1 missed. First, effective Dataverse throughput is *not* a published number for a given environment — it is 6,000 × (undisclosed web-server count) per user per 5 minutes, and that count moves with licensing. Second, a service-principal-driven or portal-driven flow concentrates all traffic on **one identity** and therefore one limit set; distributing across identities is a documented mitigation ("Distribute loads across service principles rather than a single user" — DA). Third, the exemption is a genuine architectural lever: the same data work costs service-protection budget in a flow and none in a plug-in.
- **Decision impact:** Requirement "high-volume Dataverse writes" → do not plan against the daily entitlement; plan against 6,000 requests / 1,200 s execution / 52 concurrent per identity per 5 minutes, then choose: spread across identities, batch (accepting that batching trades the request limit for the execution-time limit), or move the data leg to a plug-in / Custom API where the limit does not apply. Microsoft's own throughput advice is explicitly empirical: "Don't try to calculate how many requests to send at a time. Each environment can be different. Gradually increase the rate… and then depend on the service protection API limit `Retry-After` value to tell you when to send more."
- **Conditions:** "These limits can change and might vary between different environments. These numbers represent default values." Dataverse search is separately metered: "there's a throttling limit of one request per second for each user" (V-03).
- **Confidence:** HIGH · **Sources:** V-03, DA-10

#### AT2-05 — Microsoft's own bulk-write guidance contradicts the intuitive "batch everything" reflex, because batching moves the load from one meter to another
- **Classification:** RECOMMENDATION · **Origin:** MS
- **Evidence:** "**Avoid large batches.**… Most scenarios are fastest sending single requests with a high degree of parallelism. If you feel batch size might improve performance, start with a small batch size of 10 and increase concurrency until you start getting service protection API limit errors that you retry." "With the SDK for .NET, this approach means using `ExecuteMultipleRequest`, which typically allows sending up to 1,000 operations in a request. The main benefit… is that it reduces the total amount of XML payload… For service protection limits, it increases the total execution time per request. **Larger sized batches increase the chance you encounter execution time limits rather than limits on the number of requests.**" "When using the Web API, the smaller JSON payload sent over the wire for individual requests means that network latency isn't an issue" (V-03, 2026-01-09).
- **Why it matters:** The corpus already says "don't loop per record, use batch/bulk" (AT2-08). This finding bounds that advice: bulk operations reduce *action count* and *entitlement* consumption, but they concentrate execution time, which is a separate limit with its own error code. A 1,000-operation batch can pass the request meter and fail the execution-time meter.
- **Decision impact:** Bulk write design → prefer `CreateMultiple`/bulk for entitlement efficiency and atomic intent; prefer moderate batches (order of 10) with parallelism for raw throughput; instrument for both `0x80072322` (request count) and `0x80072321` (execution time) and treat a shift from one to the other as the signal that the batch size is now the problem.
- **Confidence:** HIGH · **Sources:** V-03

### 5.2 Throughput and concurrency (review checklist 1, 2, 3, 6)

#### AT2-06 — Trigger concurrency control is an irreversible one-way door that also **caps and can drop** incoming triggers; Microsoft's guidance is to leave it off
- **Classification:** TRADE-OFF + RISK · **Origin:** MS
- **Evidence:** "Concurrent runs | - Unlimited for flows with Concurrency Control turned off - 1 to 100 when Concurrency Control is turned on (defaults to 25) | … **Turning on Concurrency Control can't be undone without deleting and re-adding the trigger.**" "Waiting runs | - Not applicable when Concurrency Control is off - 10 plus the degree of parallelism (1-100) when Concurrency Control is on | … **Additional triggers that arrive while the waiting runs limit is met might be re-tried by the connector. However, the retry attempts might not succeed if the maximum waiting limit continues to be met for an extended period of time. To ensure all triggers result in flow runs, leave the Concurrency Control setting off in the flow's trigger.**" "Split on items | - 5,000 for Low without trigger concurrency - 100,000 for all others without trigger concurrency - **100 with trigger concurrency**" (V-01, 2026-07-17). v1's cited guidance stands: concurrency control exists to prevent "dirty reads", and "As a best practice, leave the concurrency control at its default setting. If you need to apply concurrency control, consider doing so on a flow with the least number of actions… organize actions that require concurrency control into a dedicated child flow" (V-21).
- **Why it matters:** This is the sharpest reliability trade-off in the product and v1 stated only half of it. Turning concurrency on to get ordering **introduces trigger loss** under sustained load, and shrinks `SplitOn` debatching by three orders of magnitude. It cannot be reverted without recreating the trigger.
- **Decision impact:** Ordering requirement → do **not** reach for trigger concurrency = 1 as the primary answer at any meaningful volume; that trade is "ordered but lossy". Put an ordered broker in front (Service Bus sessions) and keep concurrency off. Use concurrency = 1 only for low-volume, order-sensitive, loss-tolerant single-record processing, isolated in a small child flow.
- **Confidence:** HIGH · **Sources:** V-01, V-21

#### AT2-07 — In-run parallelism is bounded at 50 and defaults to 1; the array a loop can process is bounded by profile
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** "Apply to each array item | 5,000 for Low, 100,000 for all others"; "Apply to each concurrency | **1 is the default limit.** You can change the default to a value between 1 and 50 inclusively"; "Until iterations | - Default: 60 - Maximum: 5,000"; "Paginated items | 5,000 for Low, 100,000 for all others | To process more items, trigger multiple flow runs over your data"; "Concurrent outbound calls | 500 for Low; 2,500 for all others" (V-01, 2026-07-17).
- **Why it matters:** The default of 1 means most flows process arrays strictly sequentially unless a maker changed a setting — a common cause of "the flow is slow" that is a configuration fact, not a platform limit. Conversely raising it to 50 multiplies pressure on the connector and service-protection meters (AT2-02) at the same instant.
- **Decision impact:** High-volume independent-record processing inside one run → raise `Apply to each` concurrency **before** touching trigger concurrency, and re-check the connector throttle at the new parallelism. Requirement above the profile's array ceiling → partition across runs, not a bigger loop.
- **Confidence:** HIGH · **Sources:** V-01

#### AT2-08 — Cloud flows are the orchestration layer, not the volume-processing layer; Microsoft's remedy for bulk is bulk APIs and dataflows
- **Classification:** RECOMMENDATION · **Origin:** MS
- **Evidence:** "When you're working with large-scale data transformations, consider whether the task should be handled as an extract, transform, load (ETL) process… Dataflows handle large volumes of data efficiently and provide better performance for ETL tasks than cloud flows do… To manage data load with orchestration logic in cloud flows, combine cloud flows with dataflows." "If you need to create or update thousands of records in a data source, don't use a For each loop to process each record sequentially… Batch operations: group multiple operations into a single HTTP request… Bulk operations are posted and executed as a single operation. The entire bulk request is counted as one operation, which can significantly reduce the number of actions" — `CreateMultiple` replacing "100 Create Row actions… with just one action" (V-20, 2025-07-10).
- **Decision impact:** Good-fit pattern: flow triggers and orchestrates, dataflow or bulk Web API does the volume. Poor-fit pattern: the flow performs per-record work itself (§7).
- **Conditions:** Bulk Web API access requires direct HTTP "authenticated with Microsoft Entra ID" or "the HTTP connector in Power Automate with service principals" — i.e. premium licensing and an identity decision, not a designer toggle (V-20).
- **Confidence:** HIGH · **Sources:** V-20

#### AT2-09 — Query shaping, not parallelism, is the first throughput lever
- **Classification:** PATTERN · **Origin:** MS
- **Evidence:** "Instead, use OData query expansion to replace the nested loop with a single For each loop. This approach reduces the total number of requests to Dataverse to just one RetrieveMultiple call. Use the Expand Query parameter… Use the `$select` parameter to limit the columns returned… Use the Filter Rows parameter to apply conditions directly on the lookup table's columns" (V-20). "If you don't want your flows to run every time they're triggered, set them to execute only when a specific condition is met… Use the OData filter property to define precise conditions for when a flow should be triggered" (V-21, 2025-07-11).
- **Decision impact:** Every throughput problem is first a *request-count* problem: trigger conditions to avoid running at all, `$expand`/`$select`/`$filter` to collapse N calls into one. Only then tune parallelism. This ordering matters because the binding meters (AT2-02) count requests, not runs.
- **Confidence:** HIGH · **Sources:** V-20, V-21

#### AT2-10 — Time-bound throughput limits are per **flow version**, and sustained breach for 14 days turns the flow off
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** "If a cloud flow exceeds one of the limits, flow activity slows. It automatically resumes when the sliding window has activity below the limit. However, **if a cloud flow consistently remains above the limits for 14 days, the system turns it off.**… Because these limits are for a single version, if you update your flow, it resets the limits." Also "Flows with errors | 14 days | A cloud flow that has a trigger or actions that fail continuously is turned off"; "Flows without trigger activity | 90 days |… Flows owned by users with premium licenses or assigned capacity licenses (Power Automate Process, per flow) aren't subject to this suspension. Flow owners and co-owners are notified 30 days prior to suspension"; "Consistently throttled flows | 14 days |… Assign Power Automate Process licenses to the flow to dedicate capacity and avoid throttling"; content throughput "120 MB for Low; 1.2 GB for all others" per 5 minutes and "200 MB for Low; 2 GB for Medium; 10 GB for High" per 24 hours (V-01, 2026-07-17).
- **Why it matters:** Automation does not fail loudly at the limit; it slows, then dies quietly two weeks later. And "editing the flow resets the limits" means the throttling history is not durable evidence — a redeployment masks the symptom without fixing the design.
- **Decision impact:** Any production automation needs a monitored throttling-rate signal and a named owner, or it will stop without anyone deciding that it should (AT2-44). Do not treat "we edited it and it's fine now" as a resolution.
- **Confidence:** HIGH · **Sources:** V-01

### 5.3 Latency and duration (review checklist 10, 11 · review H-4)

#### AT2-11 — Latency in Power Automate is set by the trigger mechanism and by asynchronous write semantics, not by the 120-second timeout; the platform publishes no end-to-end latency figure
- **Classification:** CONSTRAINT + UNKNOWN · **Origin:** MS + INF
- **Evidence:** Scheduling floor: "Minimum recurrence interval | 60 seconds"; "Minimum postpone interval | Five (5) seconds for Low, one (1) second for all other performance profiles" (V-01). Trigger-mechanism behaviour: a polling trigger "checks the connected service periodically"; a webhook trigger registers "to receive notifications when specific events occur" (V-21). Downstream visibility: a cloud flow runs asynchronously after the triggering operation commits, so its effect is not synchronously visible to the caller (INF over the asynchronous trigger model; the nearest Microsoft statement, AA-27, is scoped to Dataverse→Power Pages cache freshness with a "service level agreement of 15 minutes" and is **not** a general statement about flow write visibility — do not cite it as one). Managed-connector polling can be materially slower than the recurrence floor — the Service Bus connector, for instance: "**all triggers are *long-polling*. This trigger type processes all the messages and then waits 30 seconds for more messages… The next trigger poll is based on the recurrence interval specified in the trigger's properties**" (V-08); and machine-group dispatch for desktop flows adds up to 50 seconds (AT2-38).
- **Why it matters:** v1 derived "sub-minute event frequency → put a broker in front" from the 60-second *scheduled recurrence* floor, which is a different mechanism from event triggers and does not support that inference. The honest position is that per-trigger latency is a **per-connector** property, not a platform property, and no aggregate figure is published.
- **Decision impact:** A freshness or latency requirement cannot be answered from the limits page. It must be answered per trigger: (a) event/webhook trigger where the source pushes → lowest latency available, bounded by the connector's own behaviour; (b) polling trigger → bounded below by the connector's poll interval, which must be read from that connector's reference page; (c) any requirement tighter than the connector's documented interval → the trigger is the wrong mechanism (broker push, Dataverse plug-in, or a synchronous call), not a tuning problem. Where the required freshness is sub-second or must be transactionally visible, only a synchronous plug-in / Custom API satisfies it (AT2-28).
- **Conditions:** Current per-licence polling intervals are **UNKNOWN** in this corpus: `data-architecture.md` records a conflict (15 min Free / 5 min Office 365 plans, from a troubleshooting page) against the current limits page, which "organises by Low/Medium/High profile without minute figures", and leaves it open as its U-20. Do not quote a polling-interval number until that is resolved (U-02).
- **Confidence:** HIGH (the mechanism facts) / UNKNOWN (numeric polling intervals) · **Sources:** V-01, V-08, V-21, DA (C-10/U-20)

#### AT2-12 — The 120-second synchronous ceiling is a *platform-family* property, and every alternative also caps synchronous response time — the only real escape is the asynchronous pattern
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** Power Automate: "Outbound synchronous request | 120 seconds (2 minutes)"; "Inbound request | 120 seconds (2 minutes)… Flows that contain a response action including **Respond to Copilot**, **HTTP Response**, and **Respond to a PowerApp or flow** always return a response within this limit. **Child flows that start before the response action continue running separately, and actions after the response action continue running beyond this limit**"; "Outbound asynchronous request | Configurable up to 30 days" (V-01, 2026-07-17). Logic Apps: "Outbound request | 120 sec (2 min) [multitenant] | **225 sec (3 min and 45 seconds) (Default)** [single-tenant]"; "Inbound request | 120 sec | 225 sec"; and for inbound, "if the **Response** action has the **Asynchronous response** setting turned on, or if your workflow doesn't include a **Response** action, the call pattern is asynchronous. Your workflow can take whatever time is needed to respond" (V-04, 2026-05-20). Azure Functions: "**Regardless of the function app timeout setting, 230 seconds is the maximum amount of time that an HTTP triggered function can take to respond to a request.** This limit exists because of the default idle timeout of Azure Load Balancer. For longer processing times, consider using the Durable Functions async pattern or defer the actual work and return an immediate response" (V-05, 2025-12-09).
- **Why it matters:** v1 treated 120 s as a Power Automate weakness whose remedy was "move the synchronous leg elsewhere". The evidence shows the ceilings are 120 s (Power Automate, Logic Apps Consumption), 225 s (Logic Apps Standard) and 230 s (Functions HTTP) — the same order of magnitude. Nothing in this technology family gives a synchronous caller a ten-minute answer.
- **Decision impact:** Requirement "caller waits for the result": under ~2 minutes → cloud flow is fine, no architecture change. 2–3¾ minutes → Logic Apps Standard buys headroom; a Function does not meaningfully. Above that → **the requirement itself must change** to accept-and-poll or webhook-callback (Durable Functions' async HTTP pattern is the named implementation), regardless of which product runs it. Note also the useful Power Automate escape hatch: place the response action early and let the remaining actions continue past the inbound limit.
- **Confidence:** HIGH · **Sources:** V-01, V-04, V-05

#### AT2-13 — Run duration is the sharpest genuine difference between Power Automate and Logic Apps: 30 days versus 90 days, with the stateless-workflow trap at 5 minutes
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** Power Automate: "Run duration | 30 days | Run duration is calculated using a run's start time and **includes flows with pending steps like approvals. After 30 days, any pending steps time out.**"; "Run retention in storage | 30 days" (V-01, 2026-07-17). Logic Apps: "Run duration | 90 days [multitenant] | - **Stateful workflow: 90 days (Default)** - **Stateless workflow: 5 min (Default)**"; "Run history retention in storage | 90 days | 90 days (Default)"; Consumption is configurable — "the default limit is 90 days. The minimum is 7 days. The maximum is 365 days"; and a warning that matters operationally: "**If the workflow's run duration exceeds the retention limit, this run is removed from the run history in storage**" (V-04, 2026-05-20). Durable Functions: "A durable orchestration can run for days, months, years, or even as an eternal orchestration" (V-06, 2026-08-24).
- **Why it matters:** This is one of the few boundaries where "move it to Logic Apps" is genuinely supported by a limit — a 3× to 12× longer window. It is also the boundary where Logic Apps Standard has a hidden cliff: choosing a *stateless* workflow for performance reduces the run duration to five minutes and the array-item ceiling to 100.
- **Decision impact:** Human wait states under 30 days → Power Automate approvals. 30–90 days of elapsed process time in one run → Logic Apps (stateful) is the smallest change. Indefinite or multi-year processes → Durable Functions, or externalised state plus re-triggering in any of them. Never choose Logic Apps *stateless* for a process with waits.
- **Confidence:** HIGH · **Sources:** V-01, V-04, V-06

#### AT2-14 — Beyond the run-duration ceiling, the architecture must change shape: the process record becomes the state, and the flow becomes a resumer
- **Classification:** PATTERN · **Origin:** INF over MS facts
- **Evidence:** The run is the only state container a cloud flow has, its lifetime is capped at 30 days including pending approvals, and its history is retained 30 days (V-01). Turning a flow off does not clear in-flight work — "When you turn off a cloud flow, no new runs start. All in-progress and pending runs continue until they finish" — but deleting it destroys it: "When you delete a cloud flow, no new runs start. **All in-progress and pending runs are canceled**" (V-01). Durable alternatives keep explicit state: Service Bus session state via `GetSessionStateAsync` checkpointing (V-22), Durable Functions orchestrator state (V-06).
- **Decision impact:** Requirement "process may take months, with reminders and escalation" → model an explicit process/task table with a status column and a due date, drive it from a scheduled flow, and treat each human interaction as a short-lived run against that record. Do not model it as one long run. This also makes the process observable and reportable, which the run history is not beyond 30 days (AT2-41).
- **Why it matters operationally:** Deleting or republishing a flow is a destructive act against in-flight business processes when the state lives in the run. With state externalised, redeployment is safe — which is also the answer to the versioning problem that Durable Functions has in code form (AT2-34).
- **Confidence:** HIGH (the facts) / MEDIUM (INF — the pattern is this file's synthesis) · **Sources:** V-01, V-06, V-22

### 5.4 Reliability: retry, idempotency, ordering (review checklist 4, 5, 6)

#### AT2-15 — Retry defaults differ by profile and by product; v1's "four retries" figure was a Logic Apps default, not a Power Automate one
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** Power Automate default retry policy: "Low | This policy sends up to two retries at *exponentially increasing* intervals, which scale by 5 minutes up to an interval of approximately 10 minutes for the last retry."; "Medium, High | This policy sends up to 12 retries at *exponentially increasing* intervals, which scale by seven (7) seconds up to an interval of approximately 1 hour for the last retry." Configurable ceilings: "Retry attempts | 90"; "Retry maximum delay | One (1) day"; "Retry minimum delay | Five (5) seconds" (V-01, 2026-07-17). Logic Apps: "Retry attempts | - Default: 4 attempts - Max: 90 attempts"; "Retry interval | None [Consumption] | Default: 7 sec [Standard]" (V-04, 2026-05-20). Retry policy types and guidance: "**Retry policy** in flow settings allows you to retry an action at either fixed or exponential intervals. Exponential retry policies are preferred because they can extend the retry period over time and increase the chances of successfully completing the action" (V-11, 2025-07-10). Well-Architected: "In most cases, avoid implementations that include duplicated layers of retry code… If you implement retry with a count of three on both calls, there are nine retry attempts in total against the service… Never implement an endless retry mechanism… Never perform an immediate retry more than once" (V-19, 2025-08-18).
- **Why it matters:** v1 carried this as an open conflict (its C-01) between a search-derived "four retries" and the fetched profile table. Resolved: **the profile table is correct for Power Automate; four is the Logic Apps Consumption default.** The search-derived figure was a different product leaking in. This also means the same action, moved from Power Automate to Logic Apps unchanged, changes its retry behaviour.
- **Decision impact:** Design retry at exactly one layer per call chain, prefer exponential, and state the retry owner explicitly in the design. A Low-profile flow retries twice over ~10 minutes; a Medium/High flow retries twelve times over ~1 hour — which changes both the duplicate-side-effect exposure (AT2-16) and the downstream load profile during an incident.
- **Confidence:** HIGH · **Sources:** V-01, V-04, V-11, V-19

#### AT2-16 — Microsoft states plainly that retrying a non-idempotent operation corrupts data; retry is the platform's default reliability mechanism, so idempotency is not optional design polish
- **Classification:** RISK · **Origin:** MS
- **Evidence:** "Consider whether retrying the same operation could cause inconsistencies in data. If some parts of a multistep process are repeated and the operations aren't idempotent, inconsistencies might occur. For example, **if an operation that inserts a record into Microsoft Dataverse is repeated, it might cause incorrect values in the table. Or, if you repeat an operation that sends a notification to the user, they might receive duplicate messages.** Consider the scope of operations that are retried… it might result in idempotency issues or unnecessary rollback operations." "There's no point in retrying operations that attempt an invalid operation, like updating a row in Microsoft Dataverse that doesn't exist or that the user doesn't have permission to" (V-19, 2025-08-18). Trigger-side: Dataverse trigger guidance is an "'at-least-once' design… design them to be idempotent… using key constraints in Dataverse" (DA-52, quoting the trigger documentation). The mechanism: alternate keys are "the integration-grade uniqueness mechanism" with "≤ 10 per table; ≤ 16 columns / 900 bytes; not on secured columns or virtual tables; reserved characters `/ # < > * % & : \ ? +` break GET/PATCH" (DA-53).
- **Why it matters:** This is Microsoft acknowledging that a feature enabled by default produces duplicate records, duplicate emails and duplicate downstream effects unless the maker designs against it. Combined with AT2-15's Medium/High default of twelve retries, the exposure window is up to an hour.
- **Decision impact:** Every retryable side-effecting action needs one of: a natural/business key with upsert-by-alternate-key semantics, an explicit idempotency-key check before the write, or a written acceptance of the duplicate risk by the business. Where the external system's id contains reserved characters or the natural key is a secured column, a sanitised surrogate or hash is required (DA-53). Where the side effect is external and non-idempotent (a payment, a notification to a customer), the action must be the last step and/or guarded by a claim-check record.
- **Confidence:** HIGH · **Sources:** V-19, DA-52, DA-53

#### AT2-17 — The compensating-transaction pattern is Microsoft's documented remedy where atomicity is impossible, with explicit limits on when it works
- **Classification:** PATTERN · **Origin:** MS (via PS-45, whose source id for this material is `S-58`)
- **Evidence:** Azure Architecture Center, quoted in full at **PS-45**: compensating transactions apply where a business operation "spans multiple steps, services, or data stores and must be undone if a later step fails … can't rely on atomic transactions"; "**It's not easy to generalize compensation logic. Saga mechanics from DA-52: "Pivot transactions serve as the point of no return"; "Sometimes manual intervention is the only way to recover"; irreversible steps last; "For asynchronous integrations, set up queues for checking and redoing actions, keeping aside any failed messages to fix later."
- **Correction to v1:** v1 attributed this material to "PS-58" in four places. `PS-58` is a different finding in `platform-suitability` (documentation drift as an evidence risk). The material lives in **PS-45**'s evidence and is sourced there as `S-58`. Traceability for the whole transaction-semantics boundary depended on this citation.
- **Decision impact:** Before designing a saga, test the exclusion clause: if the business cannot tolerate *temporary* inconsistency, compensation is the wrong answer and the operation must be restructured to fit inside one transaction boundary (Dataverse-only, via change set or plug-in) or moved to a system that can provide one. - **Confidence:** HIGH · **Sources:** PS-45, DA-52

#### AT2-18 — Ordering, deduplication, peek-lock and session state are documented Service Bus capabilities and are exposed to Power Automate through the connector — the remedy is MS-sourced even though the gap claim is not

#### AT2-19 — Atomicity exists only inside Dataverse; the flow-level construct is a same-connector change set with material restrictions
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** From PS-45 (VALIDATED): atomicity via Web API change sets ("all the operations are considered atomic… if any one of the operations fails, the batch request rolls back any completed operations"; batches "up to 1,000 individual requests"; `GET` not allowed), SDK `ExecuteTransactionRequest`, and the synchronous plug-in pipeline ("PreOperation/PostOperation *within the database transaction*"; "An exception thrown by your code at any synchronous stage within the database transaction causes the entire transaction to roll back"; asynchronous steps "run outside of the database transaction"). ### 5.5 Failure handling and partial failure (review H-1)

#### AT2-20 — Power Automate's structural error handling is run-after plus scopes, and it must be designed in; the fetched guidance names the try/catch/finally equivalent explicitly
- **Classification:** PATTERN · **Origin:** MS
- **Evidence:** "Use **Run after** settings to specify what should happen if an action fails, times out, is skipped, or is successful. Run identification for logging: the `workflow()` function "returns a JSON object containing details about the workflow, including its ID, name, and other metadata", including `tags.environmentName`, `tags.logicAppName`, `tags.environmentFlowSuspensionReason` and `run.name`, from which a run URL can be composed. Explicit stop: "Add the **Terminate** action when you need to stop the flow due to an error. - **Why it matters:** v1 carried this load-bearing primitive on search-derived evidence. It is now fetched Tier 1, including the specific expressions (`result()`, `workflow()`) a design needs, and including Microsoft's own warning that custom logging is itself an anti-pattern when overdone — which matters because each logging action consumes entitlement (AT2-02).
- **Decision impact:** Any flow beyond trivial length wraps risk-bearing sections in a Scope with a paired run-after-failed Scope; error detail comes from `result()`; the run URL from `workflow()` goes into the notification or log record; `Terminate` with status Failed prevents silent continuation. - **Confidence:** HIGH · **Sources:** V-11

#### AT2-21 — There is no rollback: a flow that fails mid-way leaves completed actions completed, and nothing in the documentation describes an automatic undo
- **Classification:** CONSTRAINT + RISK · **Origin:** MS (for the absence of a rollback construct outside Dataverse change sets) + INF (for the general partial-completion statement)
- **Evidence:** The fetched error-handling guidance (V-11) describes detection, alternative paths, notification and termination — **it describes no rollback or undo mechanism**. The only rollback construct documented anywhere in this corpus is the Dataverse change set / transaction boundary (AT2-19), which is same-connector and cannot contain `Apply to each`. Microsoft's cross-service remedy is compensating transactions, i.e. explicit forward-written undo logic, not a platform feature (AT2-17). `Terminate` "stop[s] the flow and set[s] the status to 'Failed' to ensure that no further actions are executed" — it stops further work; it does not reverse prior work (V-11).
- **Why it matters:** The single most consequential thing v1 never said. "The flow failed" and "the business operation did not happen" are different statements, and in Power Automate they are routinely both true only by accident. A mid-loop failure in an `Apply to each` over 500 records leaves an unknown prefix of those records processed.
- **Decision impact:** For any multi-write flow, the design must answer three questions explicitly, in writing: (1) what state is the world in if the run fails at each step; (2) how is that state discoverable afterwards (a status column, a ledger row, a dead-lettered message — the run history is not a business record and expires in 30 days); (3) who or what completes or reverses it (a recovery flow, a reconciliation job, a named human). If none of the three has an answer, the requirement needs a transaction boundary or a saga, not better error handling.
- **Conditions:** For loops specifically, partial completion is the expected outcome of a mid-loop failure; treat "the loop is atomic" as false. This is INF from the absence of any atomicity statement for loops plus the explicit exclusion of `Apply to each` from change sets — **treat as unsupported until a Microsoft statement is found** (U-05).
- **Confidence:** HIGH (no rollback construct exists outside the Dataverse transaction boundary) / MEDIUM (INF for the loop partial-completion framing) · **Sources:** V-11, AT2-17, AT2-19, PS-45

#### AT2-22 — Trigger outage behaviour fails in opposite directions and neither is safe by default
- **Classification:** CONSTRAINT + RISK · **Origin:** MS
- **Evidence:** "After it's registered, a polling trigger checks the connected service periodically. When the flow is turned off, the trigger stops polling the service but isn't deregistered. When the flow is turned back on, the trigger picks up where it left off… This behavior ensures that no data is missed… **However, if a large number of events occurred while the flow was off, they're all processed when the flow is turned on again, possibly leading to delays and performance issues.**" "Webhook triggers register with the service to receive notifications when specific events occur. When the flow is turned off, the trigger doesn't receive notifications of new events… **If any events occurred while the flow was off, they're not processed**… you might miss some events if the flow is turned off for an extended period of time" (V-21, 2025-07-11).
- **Why it matters:** Combined with AT2-10 (a consistently failing or throttled flow is turned off automatically after 14 days), the platform can put a flow into exactly the state where one trigger type floods and the other loses data — without a human deciding to turn it off.
- **Decision impact:** Loss-sensitive or order-sensitive sources → do not rely on either trigger's outage behaviour. Either put a durable broker in front so the backlog is the broker's problem and redelivery is bounded by `MaxDeliveryCount` (AT2-18), or design an explicit reconciliation/backfill query that can rebuild the missed window from the source system. The recovery design is part of the architecture, not an operations afterthought.
- **Confidence:** HIGH · **Sources:** V-21, V-01

### 5.7 Messaging and asynchronous architecture (review checklist 13; user brief §4)

#### AT2-26 — Broker choice is decided by message *type and guarantee*, not by "we need a queue"
- **Classification:** DECISION CRITERION · **Origin:** MS
- **Evidence:** "A command is a message that requests a specific action from the consumer… **A command must be delivered at least once. If a command doesn't reach its destination, the entire business transaction might fail**… consumers shouldn't process a command more than one time. Duplicate processing can cause erroneous transactions, like duplicate orders or double billing." "An event is a message that a producer raises to announce that something happened… has no expectation that the event will result in any specific action… Events can have multiple subscribers or no subscribers at all." Selection: "Use Service Bus messaging queues to transfer commands from producers to consumers"; "Use Event Grid for discrete events… Event Grid attempts to deliver each message at least once for each subscription… **Event Grid doesn't guarantee order for event delivery**… **If your workload requires enterprise messaging features like strictly ordered processing (sessions), transactions, or duplicate detection, use Service Bus instead**"; "When you work with event streams, use Event Hubs as the message broker. Event Hubs buffers large volumes of data at low latency… can ingest millions of events per second." Event Grid pull delivery exists for consumers that "have intermittent availability", have "network restrictions that require a private link", or "can't expose a push notification endpoint" (V-22, 2026-02-11).
- **Decision impact:** Command → Service Bus. Discrete event with fan-out → Event Grid, and the consumer must be idempotent because delivery is at-least-once and unordered. Stream → Event Hubs. A flow reacting to a *stream* is the wrong unit of work entirely. Where the consumer is a flow behind corporate network restrictions, Event Grid pull delivery is the documented accommodation.
- **Confidence:** HIGH · **Sources:** V-22

#### AT2-27 — Back-pressure, retry isolation and burst absorption are broker-layer properties; the documented remedies are queue-based load levelling and competing consumers
- **Classification:** PATTERN · **Origin:** MS
- **Evidence:** "Producers generate varying message volumes that can spike suddenly. **Rather than adding consumers to handle the extra load, a message broker buffers the messages. Consumers then process messages at a manageable rate without overloading the system**" (Queue-Based Load Leveling). "Producers can post a large number of messages for multiple consumers to process. Use a message broker to distribute processing across servers and improve throughput… You can dynamically add or remove consumers to scale the system as needed" (Competing Consumers). Crossover patterns are documented both ways: an Event Grid subscription with a Function handler to "drain the queue" for idle queues, and Event Grid routing commands into a Service Bus queue while sending notification events to Logic Apps (V-22). Consumer-side requirements from DA-52: "Design consumer logic to be idempotent"; "route them to a dead-letter queue"; and the exclusion — queue-based load levelling is not suitable when "**The caller requires a low-latency, synchronous response.**"
- **Why it matters:** This answers the "ignoring throttling" and "retry storm" problems structurally rather than by tuning. A broker converts a whole-flow failure into a per-message failure (retry isolation), converts a burst into a backlog (back-pressure), and converts a poison payload into a dead-lettered message instead of a 14-day flow shutdown (AT2-10).
- **Decision impact:** Bursty producer + rate-limited consumer (which, given AT2-02's three meters, is nearly every Power Automate integration at volume) → insert a broker and size the consumer to the *smallest* of the three meters. Do not insert a broker where the caller needs a synchronous answer — that is the documented exclusion, and it is the case where the 120-second boundary (AT2-12) governs instead.
- **Confidence:** HIGH · **Sources:** V-22, DA-52

#### AT2-28 — The Service Bus managed connector has its own envelope, and two of its properties will surprise a design that assumed native SDK semantics
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** Class and throttle: "Power Automate | **Premium**"; "API calls per connection | **6000** | 60 seconds"; not available in "US Government (GCC High)" (V-08). Batch read defaults: "If maximum message count is not provided, it reads 20 messages." Polling model: "**all triggers are *long-polling*. This trigger type processes all the messages and then waits 30 seconds for more messages to appear in the queue or topic subscription. If no messages appear in 30 seconds, the trigger run is skipped.** Otherwise, the trigger continues reading messages until the queue or topic subscription is empty." Session cache: "Per Service Bus messaging entity… the Service Bus connector can save up to **1,500 unique sessions** at a time to the connector cache. **If the session count exceeds this limit, old sessions are removed from the cache.**" Authentication: "Currently, **managed identity authentication is supported only for Azure Logic Apps**" — for Power Automate the options are Entra ID, connection string, or client certificate. Loop hazard: "Use caution when you select both a trigger and action that have the same connector type and use them to work with the same entity… This combination can create an infinite loop." Built-in vs managed: "The Azure Service Bus *built-in* connector is available only for Standard logic app workflows" (V-08). Broker-side ceilings that bound the design: message size "256 KB" on Basic and Standard, Premium "AMQP protocol: Up to 100 MB for single message. HTTP and SBMP protocols: Up to 1 MB for single message. All protocols: Up to 1 MB for message batch"; "Operations per second | 1,000 | 1,000 | N/A [Premium: no fixed limit]"; "Number of concurrent receive requests on a queue, topic, or subscription entity | 5,000"; "Maximum number of session states per messaging entity | 1,000,000"; "Number of messages per transaction | 100" (V-07, 2026-01-16).
- **Why it matters:** Three concrete design consequences v1 could not state. **(1) Payload:** a Standard-tier queue caps at 256 KB while a cloud flow allows 100 MB messages — a document-passing design must use a claim-check (pointer to storage), not the queue body. **(2) Ordering at scale:** session ordering is real but the connector caches only 1,500 sessions and evicts the oldest, so a design with a session per order/customer at higher cardinality has an undocumented failure mode. **(3) Security:** managed identity is Logic Apps-only, so a Power Automate consumer holds a connection string or certificate — which is itself an argument for putting the broker-facing leg in Logic Apps Standard when the security posture demands no stored secrets.
- **Decision impact:** Sizing a "flow consumes from Service Bus" design requires four numbers together: the broker tier's message size, the connector's 6,000/60 s throttle, the trigger's 20-message batch default, and the 1,500-session cache. Above any of them, move the consumer to Logic Apps Standard (built-in connector, managed identity) or a Function.
- **Confidence:** HIGH (broker quotas, fetched) / HIGH (connector reference, fetched — but note the connector page's own `ms.date` is 2024-03-01 with a 2026-07-11 update stamp, so treat the throttle figure as the most volatile item here) · **Sources:** V-07, V-08

#### AT2-29 — Dataverse's own outbound channels have distinct semantics, and the synchronous webhook is a documented dual-write hazard
- **Classification:** RISK + DECISION CRITERION · **Origin:** MS (via DA-50)
- **Evidence:** From DA-50 (VALIDATED, HIGH): a synchronous webhook is a dual-write hazard — "**the data operation rolls back but the request sent to the configured endpoint can't be recalled**"; 60-second timeout; one extra attempt on 502/503/504. The Service Bus path from Dataverse is "async-only, queued, retried exponentially by the async service, **192 KB payload truncation**"; "Azure Service Bus works for high scale processing, and provides a full queuing mechanism… **Webhooks can only scale to the point at which your hosted web service can handle the messages**"; "register the plug-in to run asynchronously for best system performance"; and the master-data reference warns "**When the first listener is 'live', it's hard to change the model.**"
- **Why it matters:** For "Dataverse must tell another system something happened", the flow is only one of three mechanisms, and it is not always the right one. The synchronous webhook is the option that can create phantom records in the downstream system on rollback — the exact failure the transaction discussion is meant to prevent.
- **Decision impact:** Requirement "the ERP must reliably learn of app changes" → asynchronous Service Bus (or change-tracking pull), plus consumer idempotency; **never a synchronous webhook for side effects**. Note the 192 KB truncation when designing the message contract, and version the contract before the first consumer goes live.
- **Confidence:** HIGH · **Sources:** DA-50

#### AT2-32 — COMPUTE is a distinct concern from workflow and orchestration, and the Functions plan decides the compute envelope — including a hard 230-second HTTP response cap that no plan removes
- **Classification:** CONSTRAINT + DECISION CRITERION · **Origin:** MS
- **Evidence (V-05, `ms.date` 2025-12-09):** Timeout by plan — "Flex Consumption plan | 30 | Unbounded"; "Premium plan | 30 | Unbounded"; "Dedicated plan | 30 | Unbounded" (requires Always On); "Container Apps | 30 | Unbounded"; "**Consumption plan | 5 | 10**". Caveats: "There's no maximum execution timeout duration enforced. However, the grace period given to a function execution is 60 minutes during scale in for the Flex Consumption and Premium plans, and a grace period of 10 minutes is given during platform updates." HTTP cap: "**Regardless of the function app timeout setting, 230 seconds is the maximum amount of time that an HTTP triggered function can take to respond to a request.**" Scale-out: Flex "1000"; Premium "Windows: 100, Linux: 20-100"; Dedicated "10-30, 100 (ASE)"; Consumption "Windows: 200, Linux: 100". Cold start: Consumption — "Apps can scale to zero when idle, meaning **some requests might have more latencies at startup**"; Premium — "Supports always ready instances to avoid cold starts by letting you maintain one or more *perpetually warm* instances"; Dedicated — "the Functions host can run continuously on a prescribed number of instances, which means that cold start isn't really an issue". Consumption connection ceiling: "Max outbound connections (per instance) | … | 600 active (1200 total)". Lifecycle: "**The Consumption plan is a legacy hosting plan. For new serverless function apps, use the Flex Consumption plan**"; Linux Consumption "is retiring on 30 September 2028"; v3-runtime Linux Consumption apps "stop running after September 30, 2026".
- **Why it matters:** v1's compute boundary was one line inheriting PS-08/PS-09 with no Functions facts at all, so "move the compute to a Function" had no envelope, no cost shape and no latency profile. Three consequences now stated: (1) the **legacy Consumption plan's 5/10-minute timeout is the tightest compute ceiling in the whole option set** — tighter than a Dataverse plug-in's 2 minutes only by degree, and a design that assumes "Functions have no timeout" is wrong on that plan; (2) cold start is a real latency term for a scale-to-zero consumer sitting behind a user-facing flow, and the documented remedy (always-ready instances) costs money continuously; (3) the 230-second HTTP cap means a Function is **not** an escape from the synchronous-response problem (AT2-12) — only the async pattern is.
- **Decision impact:** Requirement "a step needs real computation" → Function, and the plan is part of the decision: Flex Consumption for variable event-driven work with VNet needs, Premium where cold start is unacceptable or the run is long, Dedicated/ASE where compute isolation or full predictability is required. Requirement "compute must answer a waiting user in under a few seconds" → Premium/Dedicated (always-warm), never scale-to-zero. Requirement "compute takes longer than ~4 minutes and a caller waits" → async pattern is mandatory regardless of plan.
- **Confidence:** HIGH · **Sources:** V-05

#### AT2-33 — Durable Functions is the documented answer for PROCESS ORCHESTRATION and DISTRIBUTED PROCESSING patterns that the declarative designer does not express
- **Classification:** PATTERN · **Origin:** MS
- **Evidence:** "For Azure Functions, you develop orchestrations by writing code and using the Durable Functions extension. For Azure Logic Apps, you create orchestrations by using a visual designer… **You can mix and match services when you build an orchestration.** For example, you can call functions from logic app workflows and call logic app workflows from functions." The named use case is fan-out/fan-in: "to process a batch of orders, you might execute many instances of a function in parallel, wait for all instances to finish, and then execute a function that computes a result on the aggregate." Comparison: Durable Functions "Development | Code-first (imperative)" and "Connectivity | A dozen built-in binding types - Write code for custom bindings" versus Logic Apps "Designer-first (declarative)" and "1,400+ prebuilt connectors… Enterprise Integration Pack for B2B scenarios"; monitoring "Azure Application Insights" versus the Azure Monitor/Defender/Health Check set; execution context "Can run locally or in the cloud" versus "Can run in Azure, locally in Visual Studio Code, or in partially connected environments" (V-09, 2026-03-23). Orchestrations are explicitly long-lived: "Orchestrators are stateful, reliable, and they're built to run for a long time"; "A durable orchestration can run for days, months, years, or even as an eternal orchestration" (V-06, 2026-08-24).
- **Decision impact:** Requirement includes fan-out with aggregation, sub-orchestrations, an eternal/monitor loop, or resumable stateful progress in code → **Durable Functions**. The trade is connectivity: a dozen bindings versus 1,400 connectors, so a Durable orchestration that needs to touch many SaaS systems will still want a flow or a Logic App at its edges. That is the expected hybrid shape, not a failure of either product.
- **Confidence:** HIGH · **Sources:** V-06, V-09

#### AT2-34 — Durable Functions' power is paid for with determinism constraints and a versioning hazard that has no equivalent in a cloud flow
- **Classification:** CONSTRAINT + RISK · **Origin:** MS
- **Evidence (V-06, `ms.date` 2026-08-24):** "Orchestrator functions use event sourcing to ensure reliable execution and to maintain local variable state. The replay behavior of orchestrator code creates constraints on the type of code you can write… **orchestrator functions must be *deterministic*: an orchestrator function replays multiple times, and it must produce the same result each time.**" Concretely forbidden inside an orchestrator: current-time APIs ("Time-based APIs are nondeterministic and should never be used… Each orchestrator function replay produces a different value"); random GUIDs ("APIs that return a random GUID or UUID are nondeterministic because the generated value is different for each replay"); random numbers without a fixed seed; bindings and direct I/O ("Don't use bindings in an orchestrator function… **Orchestrator functions can replay multiple times, causing nondeterministic and duplicate I/O with external systems**"); static variables; environment variables ("can change over time, resulting in nondeterministic runtime behavior"); direct HTTP; blocking sleeps; and arbitrary async — "**Orchestrator code must never start any async operation, except operations defined by the orchestration trigger's context object.** For example, never use `Task.Run`, `Task.Delay`, and `HttpClient.SendAsync`". Threading: "The Durable Task Framework runs orchestrator code on a single thread and can't interact with any other threads… The framework throws a **NonDeterministicOrchestrationException**… However, **this detection behavior won't catch all violations, and you shouldn't depend on it.**" Versioning: "A durable orchestration can run for days, months, years… **Code changes that affect running orchestrations can break replay behavior, so plan carefully before you update your app.**" Also a live migration deadline: "**Support will end for the in-process model on November 10, 2026.** We highly recommend that you migrate your apps to the isolated worker model."
- **Why it matters:** v1 cited Durable Functions' "versioned replay" as a **capability** and gave it a STRONG verdict with no downside evidence at all (review: missing negative evidence). The reality is the opposite: replay is why versioning is dangerous. A team that deploys an orchestrator change while instances are in flight can corrupt them, the framework's own guard is explicitly unreliable, and the constraint list is long enough to be a genuine skills requirement rather than a coding style note.
- **Decision impact:** Durable Functions is CONDITIONAL on a pro-dev team that (a) understands the determinism rules, (b) has a deployment strategy for in-flight orchestrations (side-by-side deployment or version-specific task hub names are the named strategies), and (c) has an owner for the in-process → isolated worker migration before 10 November 2026. Where none of those hold, an externalised-state design driven by a flow (AT2-14) is more robust in practice even though it is less elegant — because its "version change" is a row in a table, not a replay history.
- **Confidence:** HIGH · **Sources:** V-06

### 5.9 In-platform alternatives to a cloud flow (review C-6)

#### AT2-35 — Plug-ins and Custom APIs are the correct answer for transactional, immediate, high-volume Dataverse logic, and the exemption from service protection limits is the decisive fact
- **Classification:** DECISION CRITERION · **Origin:** MS
- **Evidence:** Transaction participation (PS-45): synchronous plug-in stages run "within the database transaction" and "An exception thrown by your code at any synchronous stage within the database transaction causes the entire transaction to roll back"; asynchronous steps "run outside of the database transaction". Metering exemption (V-03, 2026-01-09): "**Service protection limits don't apply to data operations that originate from plug-ins and custom workflow activities.** Plug-ins and custom workflow activities run within the isolated sandbox service. Dataverse operations invoked on the sandbox service don't use the public API endpoints" — with the caveat that "the extra computation time that these operations contribute is added to the initial request that triggered them". Entitlement is *not* exempt (V-02, 2026-08-14): "Do requests generated from classic Dataverse workflows and plug-ins in Dataverse count against the request limits? **Yes, if these requests make CRUD, assign, or share-type requests, they count.**" Execution ceiling: the plug-in limit is 2 minutes (PS-09), and "heavy processing belongs in Azure" is Microsoft's own framing there. Flow-side contrast: a cloud flow runs asynchronously, after the triggering operation commits, so it cannot veto that operation and its own effect is not synchronously visible to the caller (INF over the asynchronous trigger model — not an MS statement). The developer-guidance page frames the ladder as declarative-first: "**Whenever possible, consider applying one of the several declarative process options** to define or apply business logic… When a declarative process doesn't meet a requirement, you have several options as a developer" — plug-ins, and custom workflow activities (V-18, 2026-08-28).
- **Why it matters:** v1 had no plug-in column and left the plug-in-vs-flow question as an open unknown (its U-06), which meant the file could not answer one of the most common real design questions in Power Platform work. Three distinct reasons now separate them, all MS-sourced: transaction participation, latency/guarantee, and one of the three meters.
- **Decision impact:** Dataverse-internal logic that must be **immediate, unbypassable, or transactional** → synchronous plug-in / Custom API. Dataverse-internal logic at **sustained high volume** → plug-in for the data-heavy leg, because it consumes no service-protection budget (though it still consumes entitlement, and it still costs execution time against the triggering request). Logic that must call **many external SaaS systems**, or must be owned and changed by the business → cloud flow. Logic needing **more than 2 minutes of computation** → neither; Azure Function (AT2-32). A reusable, contract-defined callable operation invoked from both apps and flows → Custom API, which also avoids the change-set restrictions that make a flow changeset unusable for anything with a loop (AT2-19).
- **Conditions:** Microsoft's declarative-first framing (V-18) must be preserved — a plug-in is a *developer* artefact with ALM, testing and skills implications, and the guidance is to exhaust declarative options first. The plug-in-versus-flow question is not answered by a single Microsoft decision table; this finding is assembled from four pages (U-08).
- **Confidence:** HIGH (each constituent fact) / MEDIUM (the assembled decision boundary — no single Microsoft page states it) · **Sources:** V-02, V-03, V-18, PS-09, PS-45

#### AT2-36 — Business process flows are a human-guidance rail with published caps and no logic of their own; they are complementary to cloud flows, not an alternative
- **Classification:** CONSTRAINT + PATTERN · **Origin:** MS (via AA-19)
- **Evidence:** From **AA-19** (VALIDATED, HIGH, page `ms.date` 2026-08-15): "up to 10 business process flow processes per table … up to 30 stages … up to five tables"; BPFs "**don't provide any conditional business logic or automation beyond … controlling entry into stages**"; stage-path branching exists; "Offline only single-table BPFs; last-stage exit workflow never triggers." The platform-level framing lists BPFs alongside cloud, instant, scheduled and desktop flows as one of the Power Automate "flow types": "Business process flows | Define a set of steps that run in a Power Apps model-driven app for people to follow to take them to a desired outcome" (V-17, `ms.date` 2019-12-20 — aged, use for framing only).
- **Correction to v1:** v1 left "whether business process flows have any documented volume/performance limit of their own" open as its U-07 and said matrix row 3 "currently has no dedicated limit citation". The corpus already answered it at HIGH confidence in `application-architecture.md`; v1's declared AA cross-reference was never actually made. **U-07 is closed.**
- **Decision impact:** Requirement "guide people through a multi-stage process inside a model-driven app" → BPF within the 10/30/5 caps, paired with cloud flows for the system-side actions triggered on stage change. Requirement "heavy conditional wizard logic" → custom page, not BPF (AA-19). Never expect a BPF to perform integration or automation, and note the offline restriction and the last-stage exit-workflow defect as design constraints.
- **Confidence:** HIGH (limits, via AA-19) / MEDIUM (the pairing pattern; the framing page is aged) · **Sources:** AA-19, V-17

### 5.10 RPA / Power Automate Desktop (review H-7; user brief §9)

#### AT2-37 — Attended and unattended RPA are different architectures with different infrastructure, licensing and failure models
- **Classification:** CONSTRAINT · **Origin:** MS + search-derived (licensing)
- **Evidence:** Hardware and OS (V-23, `ms.date` 2026-03-24): "Processor: 1.00 GHz or faster with two or more cores. **For unattended mode, four or more cores are needed**… Minimum RAM: 2 GB… Recommended: 4 GB." Supported OS "Windows 10 (Home, Pro, Enterprise), Windows 11 (Home, Pro, Enterprise), Windows Server 2016, 2019, 2022, or 2025 (devices with ARM processors aren't supported)"; "If your device runs Windows 10 Home or Windows 11 Home, you can use Power Automate to create desktop flows and monitor them… **However, you can't trigger desktop flows from the cloud.**" Multi-session density: "Basic requirements for the first user session: CPU 4 cores, RAM 4 GB, Storage 2 GB. **Per additional user session: CPU 2 cores, RAM 4 GB**… You need a DSL-range internet (not LAN) bandwidth to function properly." Artefact and logging ceilings: "Desktop flows in v1 schema environments can't exceed 100 MB in size"; "**The number of actions that can be logged in a single desktop flow run is limited to 10,000. Extra actions are performed but aren't logged.**" Licensing (V-26, search-derived, T3): attended RPA is included under the premium per-user licence; unattended requires a separate Process or Hosted Process licence, priced per bot, and "**Each simultaneous unattended process needs its own bot license**". Metering exemption (V-02, 2026-08-14): "**Important: Desktop flow executions don't consume Power Platform requests.**"
- **Why it matters:** Two facts change RPA cost models in opposite directions. Unattended RPA scales cost with **concurrency** (bots), not with volume or number of processes — unlike cloud flows, which meter requests. But desktop-flow *executions* are exempt from the Power Platform request meter entirely, so an RPA leg does not consume the cloud flow's entitlement (the orchestrating cloud flow's own actions still do). Meanwhile the observability ceiling is hard: past 10,000 actions in a run, the automation still runs but stops being auditable.
- **Decision impact:** Any RPA proposal must carry three line items, not one: the Power Automate licence, the per-concurrent-bot Process/Hosted Process licence, and the Windows compute (cores/RAM per session, VM or hosted machine). Attended-only requirements avoid the second entirely. Long desktop flows must be designed to stay under 10,000 logged actions or accept blind spots.
- **Confidence:** HIGH (prerequisites, logging cap, PPR exemption) / MEDIUM (per-bot licensing; exact prices unverified — U-06) · **Sources:** V-02, V-23, V-26

#### AT2-38 — The unattended RPA runtime is a queue with published ceilings, and those ceilings — not UI fragility — are what decide whether RPA can meet a volume or latency requirement
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence (V-13, `ms.date` 2025-12-10):** "You can assign desktop flows to a machine group, and they'll be automatically **queued** to it when triggered to run. Then, when a machine in the group is available, Power Automate will assign the next available desktop flow to it." Published limits: "Maximum number of machines in a group | **300**"; "Maximum amount of time a desktop flow can run | **24 hours**"; "Maximum amount of time a desktop flow can be queued | **12 hours**"; "Maximum number of desktop flows in the queue | **500**". Dispatch latency: "When you trigger multiple desktop flows in parallel on a machine group, **machine selection might take up to 50 seconds** before assigning the desktop flow to an available machine. In these rare cases, desktop flow runs might seem to be running sequentially, if they have short run durations." Planned-outage behaviour: "The maintenance mode allows you to stop all the desktop flow runs on machines or machine groups… **When a machine group is in maintenance mode, the desktop flow run is put in the run queue. Timeout remains the same by default.**" Regional exclusion: "Machine groups aren't available in the Government Community Cloud (GCC), Government Community Cloud - High (GCC High), Department of Defense (DoD), or China regions." Credential coupling: "If you use local Windows accounts, **all machines in the group must have the same local account with the same password**." Access model: co-owner versus user permissions at the *group* level — "Access for machine groups is managed at the group level. All machines in the group will use the same permissions and connections."
- **Why it matters:** v1 graded unattended RPA at scale CONDITIONAL with no throughput model behind it. The model is now explicit and it is a bounded queue: at most 500 waiting runs, at most 12 hours of waiting, up to 50 seconds of dispatch latency per run, and a hard 24-hour ceiling per run. Effective throughput is therefore (machines in group) ÷ (mean run duration), and the queue silently becomes the constraint long before machine count does.
- **Decision impact:** Sizing an unattended RPA architecture requires: expected trigger rate × mean run duration → required concurrent machines; then verify the peak backlog stays under 500 runs and under 12 hours, and that dispatch latency is acceptable to the business SLA. If required concurrency exceeds what the per-bot licence budget allows, the requirement is not satisfiable by RPA at that latency and must be re-scoped or re-platformed to an API. Sovereign-cloud tenants cannot use machine groups at all.
- **Confidence:** HIGH · **Sources:** V-13

#### AT2-39 — RPA credential and log hygiene is admin-configured, not secure-by-default
- **Classification:** RECOMMENDATION + RISK · **Origin:** MS (registry/governance controls) + search-derived (credential vaults)
- **Evidence:** Registry-level governance controls are extensive and IT-admin-configured, including `DisableScreenshotCaptureOnError`, `DisableUNCPaths` and `DisableCloudConnectors` (V-24, `ms.date` 2026-07-03). Credential handling (V-30, search-derived): "use the **Get credential** action to retrieve sensitive values instead of passing them as input variables. This practice ensures credential variables are marked as sensitive by default and aren't stored in the flow run logs"; storage of connection credentials in Azure Key Vault or CyberArk is supported. Machine-group password mechanics add a concrete weakening path: group keys are "encrypted into a PFX file using the AES256 algorithm", but "Windows Server 2016 doesn't support exporting or importing PFX files protected with AES256. Instead, it uses 3DES, a deprecated encryption algorithm"; Microsoft's own warning: "**3DES is a deprecated encryption algorithm. Using the machine group feature with Windows Server 2016 weakens your group's security and isn't recommended**" (V-13, 2025-12-10).
- **Decision impact:** RPA governance checklist, all items to be confirmed before go-live: `Get credential` used rather than variables or hardcoding; screenshot-on-error and log-upload settings matched to the sensitivity of the screens being automated; machine registration restricted via the `Flow Machine` / `Flow Machine Group` security-role permissions rather than the default Environment Maker; no Windows Server 2016 members in a group whose keys must remain AES256.
- **Confidence:** HIGH (registry controls, machine-group crypto) / MEDIUM (credential-vault claims, search-derived) · **Sources:** V-13, V-24, V-30

#### AT2-40 — API beats RPA wherever a programmatic path exists; RPA is a bridge with a documented cost, not an integration strategy
- **Classification:** ANTI-PATTERN · **Origin:** MS (the API-preference statement) + MEDIUM (the fragility framing)
- **Evidence:** Microsoft's planning guidance, cited at **PS-21**: "APIs are meant to be stable even as the application changes over time"; RPA "is susceptible to breaking when things change". The fragility framing itself — "Many legacy applications don't have a method for accessing their data or functionality except through their user interface. This inherent reliance on UI automation can make such solutions fragile" — remains **search-derived** (V-27) and was not confirmed as a verbatim Microsoft statement in this pass (U-07 carried from v1's U-03). Mitigation exists but does not remove the cause: AI self-healing selectors locate elements at execution time and repair them for future runs (V-27, search-derived).
- **Why it matters:** The evidence for "prefer API" is a Microsoft statement about **stability**; the additional cost argument is now MS-sourced from this file's own findings rather than from the fragility narrative — per-concurrent-bot licensing (AT2-37), dedicated Windows compute per session (AT2-37), a bounded run queue (AT2-38), a 10,000-action logging ceiling (AT2-37), and admin-configured credential hygiene (AT2-39). The case does not depend on the unverified fragility quote.
- **Decision impact:** RPA is justified when **all** of: no API or supported programmatic interface exists; the target system's remaining lifetime does not justify building or exposing one; the volume and latency fit inside AT2-38's queue model; and an owner exists for selector maintenance and machine patching. Where a stable API exists, an RPA-first proposal should be challenged in Discovery/Options. Where RPA is chosen, record it as a bridge with an exit condition, not as the target architecture.
- **Confidence:** HIGH (API-preference statement, and the cost facts) / MEDIUM (fragility framing — treat as an analyst characterisation, not a Microsoft admission) · **Sources:** PS-21, V-27, AT2-37, AT2-38, AT2-39

### 5.11 Observability and operations (review checklist 17; user brief §10)

#### AT2-41 — Native observability spans four surfaces, all short-retention, and the durable one requires deliberate configuration
- **Classification:** FACT · **Origin:** MS
- **Evidence (V-25, `ms.date` 2026-06-01):** in-designer run history is "a rolling 30-day run history"; per-flow Analytics has "Known limitations: This feature isn't currently available in government and sovereign clouds. **Data refresh cycle: Reports refresh approximately every 24 hours. - **Decision impact:** Any audit or trend requirement beyond ~30 days must be met by the Dataverse `FlowRun` table or an export, planned as part of the architecture. Before assuming Application Insights is needed for performance diagnosis, use the free built-in process-insights report — it also gives the action-burst signal that predicts throttling (AT2-10).
- **Confidence:** HIGH · **Sources:** V-25, V-01

#### AT2-42 — Application Insights export is the correlation-and-alerting answer, and it carries three constraints v1 did not state: Managed Environments only, not lossless, and not in sovereign clouds
- **Classification:** CONSTRAINT + RECOMMENDATION · **Origin:** MS
- **Evidence (V-16, `ms.date` 2025-01-16, **no preview banner in the fetched body** — v1's U-05 is closed):** "Power Automate telemetry flows into two tables on Application Insights – **Requests** and **Dependencies**." Mapping: "Requests | Contains *cloud flow runs*"; "Dependencies | Contains *cloud flow triggers* and *cloud flow actions*". Gating: "**This feature is turned on and supported for managed environments only.**" Fidelity: "**The logs powering the Power Automate telemetry in Application Insights aren't transactional data and hence are not 100% lossless. Small data losses on this telemetry data might happen due to temporary, non-repeating service issues. - **Why it matters:** v1 flagged only the preview-status question. The three real constraints are more consequential. **Managed Environments only** makes enterprise observability a licensing decision, not just a setup task. **Not 100% lossless** means Application Insights must never be the system of record for an audit or billing claim — the run history is. And the sovereign-cloud exclusion removes the option entirely for public-sector tenants, who also lose per-flow Analytics (AT2-41) and machine groups (AT2-38).
- **Decision impact:** Observability design: Application Insights for alerting, correlation and trend analysis (with alert rules on Failed requests and Dependency call failures); run history or `FlowRun` as the transactional record for audit; and for sovereign-cloud tenants, neither is available — the design must fall back to explicit in-flow logging to a Dataverse table, budgeted against the request meter (AT2-20's over-logging caution).
- **Conditions:** Requires an Azure subscription and an Application Insights resource, i.e. a cost and ownership boundary outside the Power Platform environment.
- **Confidence:** HIGH · **Sources:** V-16

#### AT2-43 — Microsoft's own operational-telemetry guidance is specific: log retries as warnings, distinguish throttling from other faults, and treat rising throttling as a design signal
- **Classification:** RECOMMENDATION · **Origin:** MS
- **Evidence:** "**Log transient faults as warning entries rather than as error entries so that monitoring systems don't detect them as application errors that might trigger false alerts.** Consider storing a value in your log entries that indicates whether retries are caused by throttling in the service or by other types of faults… so that you can differentiate them during analysis of the data. **An increase in the number of throttling errors is often an indicator of a design flaw in the application or the need to add premium capacity.**" Dependency-down handling: "Consider how to handle operations that continue to fail at every attempt… The application can periodically test the service, on an intermittent basis and with long intervals between requests, to detect when it becomes available… In the meantime, you might be able to perform some alternative operations… For example, it might be appropriate to store requests for the service in a queue or data store and retry them later. Or you might have to return a message to the user to indicate that the application isn't available" (V-19, `ms.date` 2025-08-18).
- **Decision impact:** Alerting must separate "retry happened and succeeded" (informational) from "retries exhausted / run failed" (actionable), and must track throttling rate as a **leading** indicator — it predicts the 14-day auto-off (AT2-10) and tells you whether the answer is a design change or a Process licence. A production automation also needs an explicit dependency-down runbook (queue-and-retry-later, or a user-facing degraded-mode message), not just per-action retry settings.
- **Confidence:** HIGH · **Sources:** V-19

#### AT2-44 — Operational ownership is an architectural decision in this platform, because ownership is wired into throughput, identity and survival
- **Classification:** DECISION CRITERION · **Origin:** INF over MS facts
- **Evidence:** Four MS-sourced facts converge. Throughput follows the owner's licence and collapses to Low when the owner leaves (AT2-01). Background flows "always use the limits of the owner of the process, regardless of why the process started or which accounts are used for connections" (V-02). A flow's effective data access follows the connection owner, not the invoker, unless connections are explicitly configured otherwise (AT2-48). And a non-solution-aware flow's owner **cannot be changed in place** — "In-place ownership change for non-solution-aware cloud flows isn't available because **the owner is part of the flow identity**" (V-14, 2026-08-19). Add the automatic suspensions: errors 14 days, throttling 14 days, inactivity 90 days with 30 days' notice to owners and co-owners (V-01).
- **Why it matters:** In Logic Apps, RBAC is at the resource level and "if the workflow creator leaves, you don't lose access to their workflows" (V-10). In Power Automate the opposite is true by design, and the consequences are throughput loss, broken connections and — for non-solution flows — an unfixable ownership record. This is why "who owns this flow" belongs in the architecture document, not the runbook.
- **Decision impact:** For any business-critical automation: build it **in a solution** (so ownership is transferable and connection references exist — AT2-45), give it a service principal or a capacity-licensed owner rather than an individual, add co-owners, and route the platform's owner notifications to a monitored mailbox rather than one person's inbox. Where the organisation cannot commit to that, the requirement is a signal toward Logic Apps Standard's resource-level model (AT2-31).
- **Confidence:** HIGH (each constituent fact) / MEDIUM (the assembled criterion) · **Sources:** V-01, V-02, V-10, V-14

### 5.12 Maintainability and ALM (review H-5; user brief §2 DevOps)

#### AT2-45 — Solution-aware flows plus connection references are the mechanism that makes a flow deployable; a flow built outside a solution is an ALM dead end
- **Classification:** CONSTRAINT + PATTERN · **Origin:** MS
- **Evidence (V-15, `ms.date` 2026-01-09):** "A *connection reference* is a solution component that contains a reference to a connection about a specific connector. Both solution-aware canvas apps and operations within a solution-aware flow bind to a connection reference instead of directly to a connection. **During solution import into a target environment, a connection is provided for all the connection references so any referencing flows can be turned on automatically after the import completes.**" Flows differ from apps here: "**Flows use connection references for all connectors**, whereas canvas apps only use them for implicitly shared (non-OAuth) connections." Non-solution origin is sticky: "Canvas apps and flows added from outside solutions **will not automatically be upgraded** to use connection references"; "Flows created outside a solution use connections directly. Flows created in a solution use connection references"; the remediation is to export/import in an unmanaged solution, or to act on the flow checker warning to "**Remove connections so connection references can be added**". Activation is permission-gated: "When a flow is turned on (enabled), the user turning on the flow needs to own or have permission to use all the connections in the flow"; "The '**ConnectionAuthorizationFailed**' error indicates that the user trying to activate the flow doesn't have permissions to at least one of the connections the flow is using." Known ALM breakages: "**Copy environment breaks connection references for custom connectors**… a new connection reference must be created to the new custom connector. Then, any apps or flows using the old connection references will need to be fixed"; and "**Custom connectors need to be imported in a separate solution from their connection references**, before connection references or flows." OAuth sharing constraint: "OAuth connections can only be explicitly shared with a user representing a **service principal**."
- **Why it matters:** v1 had nothing on this at all, yet it is the difference between an automation that can be promoted dev → test → prod and one that must be rebuilt by hand in each environment. It also explains the most common deployment failure in practice (`ConnectionAuthorizationFailed`) as a permissions design problem rather than a bug.
- **Decision impact:** Any automation intended to outlive its author or reach production through environments must be authored **inside a solution** from the start. The deployment design must name: who owns each connection, who activates the flow (the connection owner, or a user the connections are shared with), and — for OAuth connections — that sharing is only possible to a service principal, which effectively makes a service principal mandatory for automated deployment. Custom connectors ship in their own solution, first.
- **Confidence:** HIGH · **Sources:** V-15

#### AT2-46 — Ownership and versioning are weaker than the Azure equivalents in specific, documented ways
- **Classification:** CONSTRAINT · **Origin:** MS + MS-V
- **Evidence:** Solution-aware flows support in-place ownership change; non-solution flows do not — "To change the ownership of a non-solution-aware cloud flow, you must create a new flow via export/import, **Save as**, or **Send a copy**. In-place ownership change for non-solution-aware cloud flows isn't available because the owner is part of the flow identity." Departure handling: "If the shared flow still has an active owner, the flow continues to run… **If the flow uses any active or embedded connections that belong to the user who left the organization, those specific actions might fail.**" And "If there's no active owner for a flow, you should change the owner. To change the owner of a flow, make a copy of the flow, and then let the intended owner create the flow from the copy" (V-14, 2026-08-19). Comparative position (V-10, MS-V): Power Automate "**Limited versioning**" versus Logic Apps Standard "Full Git integration using CI/CD pipelines with Azure DevOps, GitHub, or other tools" with "change tracking includes full version history so you can revert to previous workflow versions if necessary", plus deployment slots for "zero downtime deployment". Power Platform's counterpart is real but different: "Power Platform tools that integrate with DevOps and GitHub Actions so you can build automated pipelines for the ALM cycle."
- **Why it matters:** PS-24 established that vendor comparisons overstate Power Automate's ALM gaps because pipelines and Git integration exist. That correction still stands for *deployment*. It does not extend to *per-workflow version history and rollback*, or to deployment slots, where the Logic Apps advantage is a concrete capability rather than positioning.
- **Decision impact:** Requirement "must be able to roll back to a previous version of the workflow definition on demand", or "must deploy with zero downtime" → Logic Apps Standard, or a discipline of exporting solution versions to source control. Requirement "automation must survive staff turnover without rebuild" → solution-aware from day one (AT2-45), because the non-solution path has no ownership fix.
- **Confidence:** HIGH (the ownership facts) / MEDIUM (the versioning comparison — vendor-side, and PS-24 documents that such comparisons overstate the gap) · **Sources:** V-10, V-14, PS-24

#### AT2-47 — Testing is the weakest link in flow maintainability across the whole corpus
- **Classification:** RISK · **Origin:** MS (via PS-53) + INF
- **Evidence:** The corpus records that Power Platform's Test Engine is deprecated as of April 2026 and "Playwright samples are the documented path" (PS-53) — a browser-level testing story aimed at apps, not at flow definitions. No Microsoft-documented unit-test or contract-test mechanism for a cloud flow definition was found in this pass. Logic Apps Standard, by contrast, supports local development, debugging and running in Visual Studio Code (V-10), which makes a test loop possible in principle.
- **Why it matters:** Combined with AT2-21 (no rollback) and AT2-16 (retry duplicates side effects), an untestable automation that writes to production systems is a standing operational risk, and the platform provides no native way to close it.
- **Decision impact:** For automation with material financial or compliance consequence, the design must include a test strategy that does not depend on a platform feature: a dedicated test environment with environment-variable-driven endpoints (DA-53), idempotent writes so a re-run is safe, and a documented manual verification path. Where that is unacceptable, the requirement is an argument for the code-first option, where the team's existing test tooling applies.
- **Conditions:** **Treat "there is no documented flow unit-testing mechanism" as an inferred absence, unsupported until verified** (U-09).
- **Confidence:** MEDIUM (INF absence; PS-53 for the deprecation) · **Sources:** PS-53, V-10

### 5.13 Security and identity (review H-6; user brief §2 security)

#### AT2-48 — A flow acts as the **connection owner**, not as the person who triggered it, unless connections are explicitly configured otherwise — this is the platform's most consequential and least visible security boundary
- **Classification:** RISK + DECISION CRITERION · **Origin:** MS
- **Evidence (V-14, `ms.date` 2026-08-19):** Connections in a flow are either "**Embedded**: These connections are used in the flow" or "Other". For run-only sharing: "As an owner, you can specify whether run-only users need to provide their own connections or you can use a connection already defined in the flow." The two identity modes are stated explicitly: "**All users of the flow use embedded connections**, but only the user that provides them uses connections provided by a run-only user. When the flow connects to a service via a connector, the **Provided by run-only user** connections allow the flow to **act as the run-only user and access the data that the user has access to**." (Exported definitions mark these with "a **RuntimeSource** value of **invoker**.") Entitlement follows the same asymmetry: "Instant flows, which run on demand, use the limits of the account that starts the process. Workflows or automated and scheduled flows that run in the background **always use the limits of the owner of the process, regardless of why the process started or which accounts are used for connections**" (V-02).
- **Why it matters:** With embedded connections — the default — a flow shared as run-only executes against data using the **owner's** permissions. A user who can trigger the flow can therefore cause reads and writes they could not perform themselves. This is a legitimate and often intentional design (it is how a controlled elevation is built), but it is invisible in the flow definition and is not what most makers believe is happening. v1 had nothing on this.
- **Decision impact:** Every shared flow needs an explicit decision, recorded: does this flow act **as the service** (embedded connection — deliberate elevation, and the flow's actions must then validate authorisation itself) or **as the caller** ("Provided by run-only user" — the flow's reach is the caller's reach)? Where a flow touches sensitive data and is broadly shared, the caller-identity mode is the safe default and the elevation mode requires a documented justification. Note that the "act as the caller" mode cannot be shared onward: "Can another user use a connection provided by the run-only user? **No.**"
- **Confidence:** HIGH · **Sources:** V-02, V-14

#### AT2-49 — Power Automate's authorisation model is user-level with DLP as the tenant-wide net; resource-level RBAC and managed identity are Logic Apps/Azure properties
- **Classification:** CONSTRAINT + TRADE-OFF · **Origin:** MS-V (comparison) + MS (facts)
- **Evidence:** "In Azure Logic Apps, RBAC works at the resource level where you assign role-based access to a specific resource. So, if the workflow creator leaves, you don't lose access to their workflows… **In Power Automate, RBAC works at the user level**" (V-10, 2025-07-18). Power Automate's security column: "Basic user roles and permissions with Microsoft Entra ID", "Microsoft 365 security audit logs", "Data loss prevention (DLP)", encryption at rest and in transit. Managed identity: for the Service Bus connector, "Currently, managed identity authentication is supported **only for Azure Logic Apps**" (V-08) — so a Power Automate consumer stores a connection string or client certificate. Governance practice from the sharing guidance (V-14): "Grant the Environment Maker role only to users who genuinely need to create or edit flows in that environment. End users who only run flows should stay as basic users"; "**Leverage Run-Only access instead of co-ownership**… Run-Only users can execute the flow manually or through connectors… without seeing or altering the flow's design"; and DLP as the backstop — "DLP policies don't directly stop sharing flows, but they mitigate risks if flows are broadly shared. By classifying connectors into **Business** versus **Non-Business**… you prevent flows (even those shared widely) from using connectors that could exfiltrate data." DLP's runtime bite is already documented at PS-29: blocked connectors fail at design time and existing flows are suspended or quarantined at runtime.
- **Decision impact:** Requirement "no stored secrets / managed identity mandated" → the connector-facing leg belongs in Logic Apps Standard or a Function, not a cloud flow. Requirement "access must survive personnel change and be auditable at the resource level" → same. Requirement is satisfiable in Power Automate when the controls that *do* exist are used deliberately: Environment Maker restricted to real makers, run-only rather than co-ownership for consumers, DLP policies classifying connectors, and periodic sharing audits (V-14 recommends monthly or quarterly reviews of flows with owners outside expected teams or guest owners).
- **Confidence:** HIGH (capability facts) / MEDIUM (the comparative framing — vendor-side) · **Sources:** V-08, V-10, V-14, PS-29

#### AT2-50 — Secrets in automation have three documented homes and one documented anti-home
- **Classification:** RECOMMENDATION · **Origin:** MS + search-derived
- **Evidence:** Environment variables are the sanctioned per-environment configuration mechanism but are explicitly **not** a secret store for arbitrary values — they are for configuration "when the value likely needs to be different in other environments" and are "limited to a maximum of 2,000 characters" (DA-53). Desktop flows: "use the **Get credential** action to retrieve sensitive values instead of passing them as input variables… credential variables are marked as sensitive by default and aren't stored in the flow run logs", with Azure Key Vault or CyberArk backing (V-30, search-derived). Logic Apps Standard connects "even more securely to key services such as SQL Server and **Azure Key Vault**… by using built-in operations" (V-10). The anti-home: run history stores action inputs and outputs, and run-history raw inputs/outputs are readable through the runtime endpoint at "Read calls per 5 minutes | 6,000 for Low; 60,000 for all others" (V-01) — so a secret passed as an action input is visible to anyone who can read the run.
- **Decision impact:** Never pass a secret as a flow or desktop-flow input variable. Use `Get credential` (desktop), Key Vault via a premium connector or via the Azure-side leg (cloud), and environment variables only for non-secret, per-environment configuration. Any design that logs action inputs for diagnostics must be checked for secret leakage into run history.
- **Confidence:** HIGH (run-history exposure, environment-variable purpose) / MEDIUM (credential-vault mechanics, search-derived) · **Sources:** V-01, V-10, V-30, DA-53

### 5.14 Licensing and capacity as an architectural input (user brief §20)

#### AT2-51 — Capacity is bought in three different shapes, and the shape determines which architectures are affordable
- **Classification:** DECISION CRITERION · **Origin:** MS
- **Evidence:** **Per user** — 40,000 requests per paid Power Platform/Dynamics 365 licence per 24 h; 6,000 for seeded M365, per-app and Team Member; multiple licences stack for one user ("if a user has both a Dynamics 365 Customer Service Enterprise base license and a Power Apps per user license then that user has a total of 40,000 + 40,000 = 80,000 requests") (V-02, 2026-08-14). **Per flow** — a Process licence gives "250,000 Power Platform requests across all users of the flow in a 24-hour period"; "You can stack multiple Power Automate Process licenses on a single cloud flow. Each additional license adds 250,000 PPR to the flow's daily entitlement. **The flow must be in a solution**"; or "share a single Process license across up to 25 flows by using a flow group. **Stacking isn't available for flow groups** - if a workload needs more than 250,000 actions per day, assign Process licenses directly to the individual flow" (V-02, V-01). **Per bot** — unattended RPA needs a Process or Hosted Process licence per concurrent bot (V-26, search-derived), and desktop-flow executions consume no Power Platform requests at all (V-02). **Pooled, non-licensed** — service principals and application users draw on a tenant pool: "Power Automate (all licenses) | 25,000 base requests with no per-license accrual for the tenant", or 500,000 + 5,000 per USL up to 10,000,000 where Dynamics 365 Enterprise/Professional licences are present; "**A Power Automate cloud flow owned by a service principal doesn't use the non-licensed user pool if it has a Process or Per-flow license, belongs to a flow group that has a Process license assigned, or has a designated licensed user.**" Overflow options: "Each capacity add-on raises the request limit by another 50,000 per 24 hours"; or pay-as-you-go — "If your Power Automate flows are throttled, try Pay-as-you-go to make sure none of the flows in the environment are throttled."
- **Why it matters:** The metering shape, not the price, is what constrains architecture. A per-user model punishes a design that concentrates all automation on one owner. A per-flow model rewards consolidating a high-volume workload into **one** flow (because stacking works per flow but not per flow group). A per-bot model punishes concurrency. A pooled model silently caps every service-principal-owned integration in the tenant at 25,000 requests/day unless a Process licence or designated user is attached — which is a very low ceiling and a common surprise.
- **Decision impact:** Before committing to an architecture: identify the owner identity, then read the ceiling from the matching shape. A service-principal-owned integration platform built on cloud flows must have Process licences or designated licensed users attached, or it is drawing on a 25,000/day tenant pool shared with everything else. A workload above 250,000 actions/day must be a single flow with stacked Process licences, not a flow group. An RPA architecture is priced on peak concurrency.
- **Conditions:** All of these numbers sit inside the transition period (AT2-03) and the enforcement date is unknown; capacity add-ons cannot currently be assigned. Full cost modelling is deferred to Area 10 (§12).
- **Confidence:** HIGH (entitlement mechanics) / MEDIUM (RPA per-bot pricing, search-derived — U-06) · **Sources:** V-01, V-02, V-26

### 5.15 Organisational fit (user brief §13; review H-8)

#### AT2-52 — Where an enterprise workflow, BPM or integration capability already exists, the decision is about the operating model, not the technology (**inference only — no external evidence evaluates incumbent platforms**)
- **Classification:** DECISION CRITERION · **Origin:** INF over MS facts
- **Evidence:** No Microsoft page states this; it is inference over PS-41's "configure or buy before build; do not replicate the legacy solution; every extension carries performance, ALM, upgrade and support cost", PS-24's framing that the Power Automate / Logic Apps choice turns on ownership and network posture rather than volume, and V-09's "You don't have to choose just one of these services."

## 6. Hybrid architectures — why each boundary exists

Each shape below is a *boundary justified by a documented constraint*. The arrow is where the constraint bites. None of these is a recommended default; each is the answer to one specific requirement that the simpler shape cannot meet.

### 6.1 Power Apps → Power Automate → Service Bus → Logic Apps / Functions → enterprise system

**Where the boundaries are and why:**

| Boundary | The constraint that creates it | Evidence |
|---|---|---|
| Power Apps → flow | The app must not wait: the flow's inbound synchronous window is 120 s, and a canvas call has its own 180 s ceiling | AT2-12, PS-28 |
| flow → Service Bus | The flow cannot guarantee delivery, ordering or dedup of its own accord, and cannot absorb a burst; the broker can (sessions, duplicate detection, DLQ, TTL) | AT2-18, AT2-26, AT2-27 |
| Service Bus → Logic Apps / Function | The consumer needs managed identity, private networking, longer run duration, or no per-owner licence dependency | AT2-28 (managed identity is Logic Apps-only on this connector), AT2-31, AT2-01 |
| Logic Apps / Function → enterprise system | The enterprise system's own throughput, auth and network posture govern; this is where retry ownership sits | AT2-43, DA-52 |

**Why not do it all in the flow.** The flow can consume from Service Bus with full peek-lock semantics (AT2-18), so a two-tier design (app → flow → Service Bus → flow) is legitimate and cheaper. The third tier is justified only when a *named* capability is required: managed identity to the broker, private networking to the enterprise system, a run longer than 30 days, or throughput above the connector's 6,000-calls-per-60-s ceiling. If none of those apply, the extra tier is cost without benefit (AT2-53).

**Cost of this shape:** a Premium connector licence, an Azure subscription with Service Bus (Standard caps messages at 256 KB — a document-carrying design needs a claim-check), the Azure-side ALM and monitoring estate, and cross-boundary correlation (§6.4).

### 6.2 Power Automate → Azure Function

**The boundary:** computation. Cloud-flow expressions are not a general-purpose imperative language (PS-08); a Dataverse plug-in caps at 2 minutes (PS-09); a Function's plan determines its envelope up to unbounded execution (AT2-32).

**Why the boundary exists exactly here:** the flow retains what it is good at — the business trigger, the connector reach, the approval, the notification — and hands over only the step that needs code. This is Microsoft's own "no-cliffs" extension model (PS-09, PS-30).

**What must be decided at the boundary, not after:** the Functions **plan** (a legacy Consumption plan caps at 10 minutes and cold-starts; Premium/Dedicated do not — AT2-32); whether the call is synchronous (then the 230 s HTTP cap and the flow's own 120 s outbound limit both apply, and the tighter one wins) or asynchronous (accept-and-poll, and the flow's "outbound asynchronous request | Configurable up to 30 days" applies); and idempotency, because the flow will retry the call (AT2-15, AT2-16).

### 6.3 Power Automate → API → enterprise system

**The boundary:** the contract. A custom connector or HTTP action wraps a REST endpoint; the API is the stable surface the enterprise system's owner commits to, which RPA is not (AT2-40, PS-21).

**Why this is often the correct answer instead of §6.1:** it removes the broker, the second ALM estate and the Azure run cost, and keeps the whole automation inside one operating model. The constraints to check are the connector-layer ones: "Number of custom connectors | 50 per user" and "500 requests per minute per connection", premium licensing, and the on-premises data gateway if the system is not internet-reachable (AT2-02, PS-26).

**When it is not enough:** when the API cannot absorb the arrival rate (→ insert a broker, §6.1), when the call exceeds the synchronous window (→ async pattern, AT2-12), or when the operation must be transactional across systems (→ saga, AT2-17).

### 6.4 The cross-cutting problem every hybrid creates: correlation

**The constraint.** Each half of a hybrid observes only itself. Power Automate telemetry lands in Application Insights as `Requests` (runs) and `Dependencies` (triggers and actions), keyed on `environmentId` and `resourceId` (the flow id) — and is "not 100% lossless" (AT2-42). The Azure half emits its own telemetry. Service Bus messages carry a `CorrelationId` and a `MessageId` that the Power Automate connector exposes on send (AT2-18), and the flow's own `workflow()` function yields the run id (AT2-20).

**The consequence.** A hybrid design that does not propagate an explicit correlation id through the message properties cannot answer "what happened to this business transaction" without manual reconciliation across two portals with different retention windows (30 days one side, whatever the Azure retention is set to on the other).

**The design rule.** Propagate a business correlation id — not the run id — from the originating flow through `CorrelationId` on every message and into every log record on both sides. Where the same Application Insights resource receives both halves, this makes a single KQL query possible; where it does not, the correlation id is the only join key that exists.

- **Classification:** PATTERN · **Origin:** INF over MS facts · **Confidence:** MEDIUM (the rule is this file's synthesis; the mechanisms are MS-sourced) · **Sources:** AT2-18, AT2-20, AT2-42

## 7. Anti-patterns

Each entry states its evidence class explicitly. **MS-documented** means Microsoft names the pattern as something to avoid. **MS-derived** means the constituent constraints are Microsoft statements but the anti-pattern framing is this file's. **T3** means an independent source frames it and Microsoft does not.

#### AT2-54 — The four Microsoft-documented cloud-flow anti-patterns
- **Class:** MS-documented · **Origin:** MS
- **Evidence (V-20, `ms.date` 2025-07-10):** (1) Nested `For each` loops — "Nested For each loops can be resource-intensive… if you have two loops that each have 10 iterations, the total number of iterations is 10 x 10 = 100… They can exceed limits and quotas… They can degrade performance"; remedy is OData `$expand` (AT2-09). (2) Self-triggering infinite loops — "Cloud flows can trigger themselves, creating an infinite loop… Power Automate warns you… 'Actions in this flow may result in an infinite trigger loop'"; remedies are trigger conditions and a `Terminate` safeguard. (3) Large-scale data transformation inside a flow — "consider whether the task should be handled as an ETL process". (4) Per-record loops for bulk writes — "If you need to create or update thousands of records in a data source, don't use a For each loop to process each record sequentially".
- **Decision impact:** These four can be encoded in the pack as Microsoft-sourced without qualification.
- **Confidence:** HIGH · **Sources:** V-20

#### AT2-55 — Layered retry across a call chain
- **Class:** MS-documented · **Origin:** MS
- **Evidence:** "In most cases, avoid implementations that include duplicated layers of retry code… If you implement retry with a count of three on both calls, there are nine retry attempts in total against the service… Never implement an endless retry mechanism… Never perform an immediate retry more than once" (V-19). Aggravating factor specific to this platform: the Medium/High default is already "up to 12 retries… up to an interval of approximately 1 hour" (AT2-15), so a custom retry layered on top multiplies an already-long window.
- **Decision impact:** One retry owner per call chain, named in the design. Multiplied retries hit the downstream system hardest exactly when it is already failing.
- **Confidence:** HIGH · **Sources:** V-19, V-01

#### AT2-56 — Relying on retry without designing for duplicate side effects
- **Class:** MS-documented · **Origin:** MS
- **Evidence:** AT2-16 in full — Microsoft's own examples are a repeated Dataverse insert causing "incorrect values in the table" and a repeated notification producing "duplicate messages". Trigger-side delivery is at-least-once (DA-52).
- **Decision impact:** Idempotency is a precondition for enabling retry on a side-effecting action, not a later refinement. The concrete mechanism is an alternate key with upsert semantics (DA-53).
- **Confidence:** HIGH · **Sources:** V-19, DA-52, DA-53

#### AT2-57 — Turning on trigger concurrency to get ordering
- **Class:** MS-documented (as a caution) → functions as an anti-pattern at volume · **Origin:** MS
- **Evidence:** "**Turning on Concurrency Control can't be undone** without deleting and re-adding the trigger"; "**To ensure all triggers result in flow runs, leave the Concurrency Control setting off in the flow's trigger**"; waiting runs cap at 10 + parallelism and overflow triggers "might not succeed"; `SplitOn` collapses to 100 items with concurrency on (V-01). Microsoft's own best practice: "leave the concurrency control at its default setting" and isolate it "on a flow with the least number of actions" (V-21).
- **Decision impact:** Ordering at volume is a broker requirement (AT2-18), not a trigger setting. Concurrency = 1 is acceptable only for low-volume, loss-tolerant, order-sensitive work in an isolated child flow.
- **Confidence:** HIGH · **Sources:** V-01, V-21

#### AT2-58 — Using a cloud flow as a synchronous application backend
- **Class:** MS-derived · **Origin:** INF over MS facts
- **Evidence:** Three MS constraints combine. The inbound synchronous window is 120 s and a canvas outbound call is 180 s (AT2-12, PS-28). Every action, including retries and pagination, consumes the owner's request entitlement (AT2-02, V-02) — so user traffic is metered against one person's licence. And a flow executes asynchronously, so an app that calls a flow and then reads back can see pre-flow data (INF over the asynchronous execution model, not an MS statement — AA-27's "never guaranteed to be immediate" is scoped to Power Pages cache freshness and must not be generalised).
- **Decision impact:** A flow is acceptable as an app's *command* channel for fire-and-forget or short operations. It is not an API layer: for a request/response contract used at user-facing volume, the correct answers are a Dataverse Custom API (AT2-35), a Function, or Logic Apps Standard. Where a flow is used, size the request consumption against expected user concurrency and make the owner a service principal or capacity-licensed identity.
- **Confidence:** HIGH (the constituent constraints) / MEDIUM (the anti-pattern framing) · **Sources:** V-02, AT2-12, PS-28

#### AT2-59 — Giant flows and deep child-flow chains
- **Class:** MS-derived · **Origin:** MS (the ceilings and the degradation warning) + INF (the chaining framing)
- **Evidence:** "Actions per workflow | 500 | **Flows with a large number of actions might encounter performance issues while you edit them, even if they have fewer than 500.** Consider using child flows to reduce the number of actions in a single flow or if you need more than 500"; nesting depth 8; variables 250 (V-01). Note the designer degrades *before* the limit. On chaining: a child flow invoked synchronously is subject to the 120 s inbound window, though "Child flows that start before the response action continue running separately" (V-01); each level's actions consume entitlement independently (AT2-02); and the run history of a chain is per-flow, so a failure three levels down is diagnosed across three separate run histories (AT2-41).
- **Decision impact:** Decompose for maintainability, but a chain is not free: it multiplies the observability problem and the entitlement consumption, and each synchronous hop re-imposes the 120 s window. Prefer a shallow decomposition with one clear orchestrator over a deep chain. Where the chain is deep because the process is genuinely complex, that is the signal for code-first orchestration (AT2-33).
- **Confidence:** HIGH (ceilings, degradation) / MEDIUM (the chaining framing) · **Sources:** V-01, AT2-41

#### AT2-60 — Excessive polling
- **Class:** Conditional anti-pattern — MS-derived, with a documented counterweight · **Origin:** MS
- **Evidence:** Trigger conditions and OData filters are Microsoft's documented technique for keeping a high-frequency source inside throughput limits — "If you don't want your flows to run every time they're triggered, set them to execute only when a specific condition is met" (V-21). But the counterweight is equally documented: webhook triggers silently drop events while a flow is off, whereas polling triggers replay the backlog (AT2-22). And some connectors only offer polling; the Service Bus connector's triggers are all long-polling with a 30-second wait (AT2-28).
- **Decision impact:** Prefer event/push triggers for latency-sensitive requirements, always add a trigger condition on a busy source, and never treat "switch to a webhook" as a pure win — it trades backlog flood for silent loss. This is a trade-off to be decided per source, **not an unconditional anti-pattern**.
- **Confidence:** HIGH · **Sources:** V-21, V-08

#### AT2-61 — Ignoring the meters until the flow is turned off
- **Class:** MS-derived · **Origin:** MS
- **Evidence:** A throttled flow does not fail loudly — "flow activity slows. It automatically resumes when the sliding window has activity below the limit. However, if a cloud flow consistently remains above the limits for 14 days, the system turns it off" (V-01); the same 14-day shutoff applies to continuously erroring flows; and "**if you update your flow, it resets the limits**", so redeployment masks the symptom. Microsoft's own leading indicator: "An increase in the number of throttling errors is often an indicator of a design flaw in the application or the need to add premium capacity" (V-19). The free built-in signal exists: process insights reports action counts per run "helping you understand if your flow might run into daily action bursts throttling limits" (V-25).
- **Decision impact:** Throttling rate is a monitored metric with a named owner, or the automation stops without a decision. Treat "we republished it and it's fine" as masking, not resolution.
- **Confidence:** HIGH · **Sources:** V-01, V-19, V-25

#### AT2-62 — Heavy computation in a flow
- **Class:** MS-documented · **Origin:** MS
- **Evidence:** PS-07: "complex business logic and large-scale transformation do not belong in cloud flows"; PS-08: Power Fx lacks imperative loops and mutable local state. Expression ceilings bound it concretely: "Expression evaluation limit | 131,072 characters" and `Until` iterations capped at 5,000 (V-01).
- **Decision impact:** Compute goes to a Function (AT2-32). A flow that has grown a computation is usually also approaching the action ceiling (AT2-59) — treat both as the same signal.
- **Confidence:** HIGH · **Sources:** V-01, PS-07, PS-08

#### AT2-63 — Using RPA where an API exists
- **Class:** MS-documented (the stability preference) · **Origin:** MS + MEDIUM (cost extension)
- **Evidence:** AT2-40 in full — PS-21's "APIs are meant to be stable even as the application changes over time" against RPA's susceptibility "to breaking when things change", plus this file's per-bot licensing, per-session compute, bounded run queue and 10,000-action logging cap.
- **Confidence:** HIGH (preference) / MEDIUM (the fragility framing) · **Sources:** PS-21, AT2-37, AT2-38

#### AT2-64 — Simulating distributed transaction guarantees with flow logic
- **Class:** MS-derived · **Origin:** MS
- **Evidence:** No cross-connector transaction construct exists; the Dataverse change set cannot contain `Apply to each` and cannot chain outputs (AT2-19); there is no rollback mechanism in the error-handling guidance (AT2-21); and Microsoft's own remedy carries an explicit exclusion — compensation is unsuitable when "The system can't tolerate temporary inconsistency" (AT2-17).
- **Decision impact:** A flow that "checks everything succeeded and undoes it if not" is a hand-built saga with no durable state and a 30-day expiry on its own run history. Either give it real state (AT2-14) or move the operation inside one transaction boundary. Never describe such a flow to a business stakeholder as transactional.
- **Confidence:** HIGH · **Sources:** AT2-17, AT2-19, AT2-21

#### AT2-65 — Tightly coupled multi-system workflows
- **Class:** MS-derived · **Origin:** MS (the coupling facts) + INF (the framing)
- **Evidence:** A synchronous chain across N systems fails if any one is unavailable, and Microsoft's documented remedies are all decoupling: queue-based load levelling, competing consumers, dead-lettering (AT2-27), asynchronous Service Bus rather than a synchronous webhook out of Dataverse (AT2-29), and a dependency-down runbook that queues work for later (AT2-43). DA-51 names the adjacent data anti-patterns directly, including "Repeated connections between on-premises and cloud apps … send data in batches instead". Contract coupling is also documented: "**When the first listener is 'live', it's hard to change the model**" (DA-50).
- **Decision impact:** Each additional synchronous hop multiplies the failure surface and pins the whole chain to the slowest and least available participant. Decouple at the first boundary where availability differs, and version the message contract before the first consumer goes live.
- **Confidence:** HIGH (the constituent facts) / MEDIUM (the framing) · **Sources:** AT2-27, AT2-29, AT2-43, DA-50, DA-51

#### AT2-66 — "Power Automate as a general-purpose application backend" as an architectural argument
- **Class:** **T3** — explicitly not a Microsoft statement · **Origin:** T3
- **Evidence:** "Power Automate enables rapid workflow creation, but it lacks a standardized approach for error handling, failure propagation, observability, and cross-flow traceability, which leads to hidden failures and operational blind spots as solutions scale" (V-28, T3 blog). This is consistent with, but not identical to, the Microsoft-documented constraints in AT2-20 (error handling must be designed in), AT2-41/AT2-42 (short retention, gated and lossy export), AT2-19 (no cross-system transactions) and AT2-02 (three meters).
- **Decision impact:** The pack **must not** encode this framing as a Microsoft statement. Encode instead the MS-sourced constraints it is assembled from — and where the concrete claim is needed, use AT2-58, which reaches a narrower version of the same conclusion entirely from Microsoft facts.
- **Confidence:** MEDIUM (T3 framing) / HIGH (the underlying MS constraints) · **Sources:** V-28; AT2-02, AT2-19, AT2-20, AT2-41, AT2-42, AT2-58

## 14. Implications for the aisa knowledge model (pointers, not pack content)

Nothing below is a question, glossary term, signal or decision-tree node; these are pointers for later pack authoring.

**Technology-neutral Discovery signals the evidence justifies collecting.** Which of the four shapes does this requirement have (§2)? Who will own the automation, and will that person still be here in two years? What is the expected event rate, and the expected action count per event? Is there a step whose result the caller must wait for, and for how long? What is the longest human wait in the process? Can any step be retried safely — is there a natural key? Must anything be all-or-nothing across systems, and can the business tolerate temporary inconsistency? Does the target system have a stable API? How long must execution evidence be retained? How many unattended bots would run at peak? Is a private network, managed identity or resource-level RBAC mandated? Does the organisation already own an Azure operating model, or an enterprise workflow engine?

**Hard boundaries safe to encode as CONSTRAINT (all MS-sourced, fetched, dated).** 500 actions / 8 nesting / 100,000 array items / 30-day run duration / 30-day retention / 120 s synchronous / 14-day error and throttle shutoff / 90-day inactivity suspension (AT2-01, AT2-06, AT2-07, AT2-10, AT2-12, AT2-13). Dataverse service protection 6,000 requests, 1,200 s execution and 52 concurrent per user per web server per 5 minutes (AT2-04). No cross-connector transaction (AT2-19). Retry duplicates non-idempotent effects (AT2-16). Polling backlog flood versus webhook silent drop (AT2-22). Logic Apps' identical 500/8 ceiling and 90-day duration (AT2-30). Functions' 230 s HTTP cap and plan timeouts (AT2-32). Durable determinism and versioning hazard (AT2-34). Service Bus Standard 256 KB messages (AT2-28). RPA queue of 500 runs / 12 h wait / 24 h run (AT2-38). App Insights managed-environments-only and not lossless (AT2-42).

**Corrected boundaries (myth versus mechanism) the pack should actively teach.**
- *"Hit 500 actions? Move to Logic Apps."* — **False.** Identical limit (AT2-30).
- *"Logic Apps is for large scale, Power Automate for small."* — Unsupported as stated; the real differences are duration, sync window, networking, identity, RBAC and ALM (AT2-31, C-03).
- *"Add a queue and it's exactly-once."* — False without an idempotent consumer; and the connector's session cache holds only 1,500 sessions (AT2-18, AT2-28).
- *"Move it to a Function to beat the 2-minute timeout."* — Only to 230 s; beyond that the async pattern is mandatory (AT2-12, AT2-32).
- *"Durable Functions gives you versioned replay."* — Replay is exactly why versioning is dangerous (AT2-34).
- *"Application Insights gives observability for free."* — Managed Environments only, not lossless, unavailable in sovereign clouds (AT2-42).
- *"The flow runs as the person who triggered it."* — Only if connections are configured that way; the default is the owner's identity (AT2-48).
- *"Plan capacity from the daily request number."* — Three meters apply and the daily one is usually not the binding constraint (AT2-02).
- *"RPA is a quick win with no infrastructure."* — Per-bot licence, per-session compute, bounded queue, 10,000-action logging ceiling (AT2-37, AT2-38).

**Architecture options the pack must be able to output.** Cloud-flow-only (business workflow, approvals, notification, moderate integration). Cloud flow + bulk API or dataflow (high-volume Dataverse writes). Cloud flow + Service Bus or Event Grid (ordering, dedup, decoupling, burst). Cloud flow + Function (compute). Cloud flow + Durable Functions or Logic Apps Standard (distributed orchestration, saga). Plug-in or Custom API (transactional, immediate, high-volume Dataverse-internal). BPF + cloud flow (guided human process plus system automation). Power Automate Desktop as a bounded bridge with an exit condition. Logic Apps Standard / Functions / custom service as the default when private networking, dedicated compute, managed identity, resource RBAC, long duration or extreme throughput dominate. Existing enterprise engine (do not duplicate). And for each of these, the *operating model* that goes with it (AT2-53).

**Validation before commitment (typical).** Confirm the flow owner and licence class before estimating any throughput headroom. Express the throughput requirement in all three metering units and identify which binds. Prototype the retry and idempotency design on the highest-risk write path before building the rest. Confirm whether any step needs cross-system atomicity before assuming a saga is unnecessary. Size RPA against the queue model, not against machine count. Confirm the environment is a Managed Environment before promising Application Insights. Decide the connection-identity mode for every shared flow. Build in a solution from day one. Load-test rather than quote a number (U-10).

**Gate conditions proposed for downstream use.** (1) Every verdict keeps its origin tag; INF absence claims are phrased "treat as unsupported until verified" wherever they appear. (2) MS-V sourced characterisations (V-10) may contribute capability facts but never scale or performance adjectives. (3) Before pack authoring, resolve U-01 (Medium profile), U-03 (approvals mechanics), U-06/U-11 (RPA pricing and stacking cap), and U-12 (high-throughput mode status). (4) The T3 "general-purpose backend" framing (AT2-66) must not be encoded as a Microsoft statement; use AT2-58 instead. (5) Deferrals in §12 back-reference this file; undelivered deferrals revert the corresponding matrix cells to UNKNOWN. (6) Re-verify every number against its `ms.date` before encoding — the request model is explicitly mid-transition and its enforcement date is unannounced. (7) The Copilot Studio agent-flow deferral must be assigned an owner or explicitly ruled out of scope.
