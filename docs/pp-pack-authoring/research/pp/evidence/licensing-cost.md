# Licensing and Cost — Research Evidence

Research area: **10 — Licensing and Cost** (`../research-areas.md`).
Research date: **2026-09-03**. Source policy: `../source-policy.md`.
Sibling files produced in the same block, deliberately kept conceptually distinct: `performance-scale.md` (**PF-nn**) answers *whether the workload's runtime behaviour fits*; `operations-support.md` (**OP-nn**) answers *how the workload is run in production*. This file answers only the **economic architecture**: which requirements and which design choices materially change what the solution costs to own. Where a cost driver has a performance or operations origin, this file states the economic consequence and points at the sibling finding rather than re-deriving the mechanism (§10).

Cross-references to peer files, statuses verified 2026-09-03: `platform-suitability.md` (VALIDATED, Gate PASS, MEDIUM) as **PS-nn**; `application-architecture.md` (VALIDATED, Gate PASS, MEDIUM) as **AA-nn**; `data-architecture.md` (VALIDATED, Gate PASS, **HIGH**) as **DA-nn**; `automation-architecture.md` (VALIDATED, Gate PASS, MEDIUM) as **AT2-nn**. Findings here are **LC-nn**; sources are **L-nn**.

**The question this file answers.** Not *"how much does Power Platform cost?"* but:

> **Which requirements and which architectural choices materially change the total cost of owning this solution — and when does the cheapest licence produce the most expensive architecture?**

Every finding runs **REQUIREMENT → COST DRIVER → ARCHITECTURAL CONSEQUENCE**. This file is **not a price catalogue**. Prices appear only where the *unit of billing* is itself an architectural fact — because the unit (per active user per app per month, per flow run, per GB, per unique authenticated website visitor per month) determines which designs are cheap and which are expensive, in a way that survives price changes even when the numbers do not.

### 0.4 The structural finding that frames everything else

**Power Platform Well-Architected has no Cost Optimization pillar.** Its five pillars are Reliability, Security, Operational Excellence, Performance Efficiency and Experience Optimization (L-06, `ms.date` 2025-08-22). Azure Well-Architected has a sixth, Cost Optimization, with a full CO:01–CO:14 checklist (L-07). So Microsoft publishes a cost-optimisation discipline for Azure workloads and **not** for Power Platform workloads.

This is the most important negative finding in the area (LC-01). Its practical effect is that there is no first-party, structured cost-review method for Power Platform, and any cost discipline applied to a Power Platform workload has to be borrowed from Azure's pillar and translated. §4 does that translation explicitly.

## 1. The economic model in one page

Power Platform is not priced on one axis. Five economic mechanisms operate simultaneously, and a design decision can move cost from one to another without reducing it.

| # | Mechanism | Billing unit | What makes it grow | Where |
|---|---|---|---|---|
| 1 | **Per-user entitlement** | A named user, per month | Number of *people*, and whether they need premium capability | LC-03, LC-04 |
| 2 | **Per-app / per-scope entitlement** | A user × an app (stackable), per month | Number of *(person, app)* pairs — so app **count** is a cost driver | LC-04 |
| 3 | **Capacity licence** | An automation object (flow, machine, hosted machine) | Number of *automations* needing autonomous entitlement or higher throughput | LC-08 |
| 4 | **Consumption meter** (pay-as-you-go) | Active user/app/month · flow run · GB-month · credit · unique website visitor/month | *Actual usage* — so idle capacity costs nothing and spikes cost linearly | LC-16…LC-21 |
| 5 | **Stored capacity** | GB-month of database / file / log, pooled at tenant level | *Data volume, file volume, audit volume, index volume* over time | LC-05, LC-10, LC-11 |

**The two questions that most change the answer**, and which are asked before any product is named:

- **Who** needs the capability — a fixed team, a whole workforce, or an unpredictable external population? (Mechanisms 1/2 vs 4.)
- **What is the shape of the demand** — steady per-person daily use, or bursty/seasonal/long-tail use? (Mechanism 1/2 vs 4; Microsoft's own guidance in LC-19 draws exactly this line.)

**The mechanism that surprises people**: (5). Storage is pooled at tenant level, accrues per licence in small increments, is consumed by things nobody budgeted (audit logs, search indexes, attachments, DR replicas), and going over it **blocks administrative operations** (LC-10, LC-11).

- **Classification:** DECISION CRITERION · **Origin:** INF over MS-L facts · **Confidence:** MEDIUM (the taxonomy is synthesis; every mechanism is MS-sourced below) · **Sources:** synthesis over LC-03…LC-24

## 2. Findings

### 2.1 The structural absence

#### LC-01 — Microsoft publishes **no Cost Optimization pillar for Power Platform**, only for Azure
- **Classification:** CONSTRAINT (evidence gap) · **Origin:** MS
- **Evidence:** Power Platform Well-Architected lists exactly five pillars: *"Reliability… Security… Operational Excellence… Performance Efficiency… Experience Optimization"* (L-06, `ms.date` 2025-08-22). No Cost Optimization pillar exists, and no `power-platform/well-architected/cost-optimization/*` path resolves. Azure Well-Architected does have one, with a fourteen-item checklist CO:01–CO:14 covering financial responsibility, cost models, cost data collection, spending guardrails, rates, billing-increment alignment, component/environment/flow/data/code/scaling cost optimisation, personnel time and consolidation (L-07, `ms.date` 2023-11-15).
- **Why it matters:** Three consequences. (1) There is **no first-party design-review method** for Power Platform cost, so cost is not systematically challenged in the way reliability and performance now are. (2) Where cost guidance does exist in Power Platform documentation, it appears as *incidental trade-off callouts inside other pillars* (LC-27, LC-26) rather than as a discipline. (3) An organisation that has adopted Power Platform Well-Architected as its review standard has, without noticing, adopted a review standard that does not look at cost.
- **Decision impact:** aisa should not expect a Microsoft-shaped cost review to exist and should not present one as Microsoft guidance. The defensible move is to borrow Azure's CO:01–CO:14 and translate it to Power Platform's actual cost drivers — done in §4 — while labelling the translation as inference (INF), not Microsoft guidance for this platform.
- **Conditions:** Absence verified against the pillars hub page and two searches; a cost-optimisation pillar may be added later. Re-verify (LC-U-01).
- **Confidence:** HIGH (that the pillar is absent on the dates checked) · **Sources:** L-06, L-07

#### LC-02 — Licensing entitlement is **not authoritatively documented on Learn**; the Licensing Guide and the customer's agreement govern
- **Classification:** CONSTRAINT · **Origin:** MS-L
- **Evidence:** L-01 (`ms.date` 2025-06-17) opens by deferring to the *"Microsoft Power Platform Licensing Guide"* and repeats the deferral for Microsoft 365 plan inclusions, Dynamics 365 inclusions and Copilot Studio. L-02 (2026-08-17) defers for all capacity licensing. L-05 (2026-07-20) defers for the exact set of plans including Power Automate and for add-ons. L-08 (2026-08-14) defers for AI Builder credit management. And the terms above the documentation: *"The Universal License Terms for Online Services apply to your organization's use of the online service, including consumption that exceeds the online service's documented entitlements or usage limits."* Enforcement is explicit: *"If you use more than your documented entitlements or usage limits, you must buy more licenses. If your storage consumption exceeds the documented entitlements or usage limits, **Microsoft might suspend use of the online service.** Microsoft provides reasonable notice before suspending"* (L-02).
- **Why it matters:** It sets the epistemic ceiling for this whole area. The best available public evidence is *derivative*. And the consequence of getting it wrong is not merely a bill — it is a documented right of suspension.
- **Decision impact:** Encode the licensing **model shape** and its architectural consequences; route entitlement questions to the Licensing Guide and to the customer's agreement, with a named owner. Any licence-dependent architecture decision must carry a validation action ("confirm with the customer's licensing desk"), not an assumption. Treat *"suspension after reasonable notice"* as a genuine availability risk with a commercial root cause (→ OP-22).
- **Confidence:** HIGH · **Sources:** L-01, L-02, L-05, L-08

### 2.2 Licensing model — the architectural consequences

#### LC-03 — The premium/standard connector boundary is the **single largest licence-shaping architectural decision**
- **Classification:** DECISION CRITERION · **Origin:** MS-L + T3
- **Evidence:** Microsoft's connector reference marks premium connectors with a badge whose legend reads: *"This is a Premium connector for Power Automate and Power Apps or a Standard connector for Azure Logic Apps"* (L-09). Premium-tier connectors include the whole enterprise-integration set relevant to most engagements — SQL Server, Salesforce, SAP, HTTP, Azure Blob Storage, Azure Key Vault, Azure Cosmos DB, Azure Data Factory, Azure DevOps, Amazon S3, Amazon SQS, Azure OpenAI (L-09). Entitlement: Power Automate Premium, Process and Hosted Process all include *"Standard connectors: Included; Premium connectors: Included; Custom connectors: Included"*, whereas Power Automate Free is *"limited to standard connectors only"* (L-05). For Power Apps, the Microsoft 365 seeded plan includes *"Connect to cloud services using standard connectors: Yes"* and *"Access on-premises data or use premium or custom connectors: —"* (L-01). And for pay-as-you-go, the boundary determines whether a meter fires at all: a user with a Microsoft 365 plan is *"Not counted in the meter"* for an app with standard connectors but *"Charged via Azure subscription"* for an app with premium connectors (L-03).
- **Why it matters:** This is the point where a *technical* choice — which system the solution talks to — silently determines the *commercial* model for every user of that solution. Custom connectors are premium; the on-premises data gateway is premium; SQL and HTTP are premium. So a design decision as ordinary as "read the data from SQL rather than from a SharePoint list" can move an entire user population from seeded entitlement to paid licensing.
- **Decision impact:** **Connector tier must be established at design time, not at deployment.** For every candidate integration path, record whether it crosses the premium boundary and how many users are consequently affected. Where a standard-connector path exists and meets the requirement, the licence saving is not marginal — it is the difference between a seeded and a paid population. Where it does not, the premium cost is a legitimate, planned cost and should appear in the option's economics from the first comparison.
- **Conditions:** The connector reference page does **not** itself state the licensing rule (L-09) — the entitlement statements come from the licence pages (L-05, L-01) and the meter behaviour from L-03. Independent practitioner sources describe premium-connector discovery-after-build as the commonest source of mid-project licence shock and quantify it (order of 20–35% of makers moved onto paid plans unnecessarily; one account of ~$30,000/year unplanned for a 500-user premium-dependent estate) — these are **T3, unverified**, directionally consistent with the Microsoft mechanism but not to be encoded as figures (L-10).
- **Confidence:** HIGH for the mechanism; MEDIUM for the magnitude · **Sources:** L-09, L-05, L-01, L-03, L-10

#### LC-04 — Per-app licensing makes **the number of apps a cost driver**, and the counting rules reward consolidation asymmetrically
- **Classification:** DECISION CRITERION · **Origin:** MS-L
- **Evidence:** *"**Power Apps Premium** is licensed per user and entitles the licensed user to build, modernize, and run unlimited custom applications and access unlimited websites for $20/user/month (or $12 per user/month with 2,000+ new user licenses). **Power Apps per app** enables individual users to run (one custom app or access one Power Pages website) for a specific business scenario based on the full capabilities of Power Apps for $5/user/app/month."* Stacking: *"Each per app license provides an individual user with rights to one app (canvas and/or model-driven) **within a single environment**. A single user might be covered by multiple per app licenses to allow the user to use multiple apps… In other words, the per app license is stackable."* Two counting rules that matter: *"**Do embedded canvas apps in model-driven apps count consume multiple per-app plans?** No. Embedded canvas components within the model-driven app are recognized as a single app."* And *"You can mix and match Power Apps licenses… across the users in your organization"* (L-04, `ms.date` 2026-08-14).
- **Why it matters:** The break-even is arithmetic and it drives *architecture*: at list prices, four per-app licences for one user equals one premium licence. So "how many separate apps does this user need?" becomes a licensing question, and app decomposition — a design decision usually made on usability or maintainability grounds (PF-06 argues for splitting large apps) — has a direct, opposite-signed cost effect. The embedded-canvas rule creates a genuine architectural lever: a model-driven app with embedded canvas components counts as **one** app, while the same functionality as separate canvas apps counts as several.
- **Decision impact:** Requirement "users need several distinct capabilities" → model the *(person, app)* matrix before choosing the app decomposition, and compare (a) one premium licence per user, (b) stacked per-app licences, (c) a model-driven container with embedded canvas pages counted as one app, (d) pay-as-you-go per active user per app (LC-17). Note the per-app licence is scoped to **one environment**, which couples licensing to environment strategy (LC-25). And note the direct tension with PF-06: performance and maintainability push toward splitting apps; per-app licensing pushes toward consolidating them. That tension needs an explicit decision, not a default.
- **Conditions:** Prices are list, dated 2026-08-14, and volume-discounted at 2,000+ licences; treat as illustrative per 0.3.
- **Confidence:** HIGH (for the model and the counting rules on that date) · **Sources:** L-04

#### LC-05 — Dataverse has **no technical size limit** — the ceiling is purchased entitlement, and it is pooled at tenant level
- **Classification:** FACT · **Origin:** MS
- **Evidence:** ***"There's no technical limit on the size of a Dataverse environment. The limits mentioned on this page are entitlement limits based on product licenses you purchase."*** Three separate capacity types with distinct rates and distinct consumers: **database** (*"All other tables count for your database"*), **file** (Attachment, AnnotationBase, any table with file or image columns, `WebResourceBase`, `RibbonClientMetadataBase`, Insights `– Analytics` tables), **log** (`AuditBase`, `PlugInTraceLogBase`, **elastic tables**). Sources of entitlement: *"**Org (tenant) default**: The default capacity given at the time of sign up. **User licenses**: More capacity added for every user license purchased. **Additional storage**: Any extra storage you bought"* (L-02, `ms.date` 2026-08-17). Per-licence accrual, from the licensing FAQ: Power Apps per app **+50 MB** database, **+400 MB** file, **+0** log; Power Apps per user **+250 MB** database, **+2 GB** file, **+0** log. Power Automate per user **+250 MB** / **+2 GB** / **+0**; per flow **+50 MB** / **+200 MB** / **+0** (L-04). Power Automate Premium adds *"Dataverse database storage | 250 MB per license"* and *"Dataverse file storage | 2 GB per license"*; Process and Hosted Process add 50 MB / 200 MB (L-05).
- **Why it matters:** Three consequences, and the third is the one that bites. (1) Scale is a **commercial** ceiling, not a technical one — which is the correct answer to "will Dataverse hold our data?" (→ PF-17). (2) Entitlement grows with the *user* population, so a solution with much data and few users is structurally under-entitled while one with many users and little data has headroom it did not buy deliberately. (3) **Log capacity accrues at +0 from every Power Apps and Power Automate licence.** Auditing, plug-in trace logs and elastic tables all consume log capacity, and no user licence provides any. So enabling auditing — a governance and operations requirement (→ OP-10) — creates a capacity need that the licence model does not fund.
- **Decision impact:** Requirement "retain audit history" or "high-volume elastic-table workload" → budget log capacity explicitly as an add-on or a pay-as-you-go meter; do not assume licences cover it. Requirement "large data volume, small user population" → model capacity separately from seats. Because capacity is pooled at tenant level, this is a **tenant-level** conversation that a project-level budget cannot resolve alone (→ OP-21).
- **Confidence:** HIGH · **Sources:** L-02, L-04, L-05

#### LC-06 — A Power Apps licence includes Power Automate **only in the app's context**, and the boundary is data-source identity
- **Classification:** CONSTRAINT · **Origin:** MS-L
- **Evidence:** *"Power Apps licenses continue to include Power Automate capabilities. **However, flows need to run within the context of the app, which refers to using the same data sources for triggers or actions as the app. Consuming standalone Power Automate flows unrelated to the app(s) requires purchase of a Power Automate license**"* (L-04). The pay-as-you-go mechanics show the same boundary operationally: *"Flows triggered directly from an app created using Power Apps have no extra cost since by running the Power App, the user's standalone Power Apps license or the Power Apps pay-as-you-go meter covers their usage of Power Automate."* And for automated triggers: *"For cloud flows only, if the flow uses the same data sources as a Power App, you can **link that flow to the app using a PowerShell script**. When you link a flow to an app, usage is covered by the user's standalone Power Apps license or the Power Apps pay-as-you-go meter"* (L-03, `ms.date` 2026-08-14). The example is unambiguous: *"User with Power Apps per user with flow runs out of the app context | 10 runs (not charged) | 10 runs [charged] | 5 runs | 5 runs | **15 runs** [Azure billable]"*.
- **Why it matters:** This is one of the least-known and most architecturally consequential rules in the model. "In context" is defined by **shared data sources**, not by whether a user pressed a button. So a background flow that touches the same tables as the app is in context and covered; the same logic pointed at a different system is out of context and needs its own licence. That makes *where the automation reads and writes* a licensing decision.
- **Decision impact:** For every flow, record whether it is in the app's data-source context. Design consequence: consolidating an automation onto the app's own data sources (rather than reaching directly into a second system) can keep it inside the Power Apps entitlement — but that is only legitimate where it is the right design, not a licence-driven contortion (see LC-28). Note the operational catch: linking an automated flow to an app requires a **PowerShell script**, so the entitlement depends on a configuration step that is invisible in the maker experience and easily lost on redeployment (→ OP-17).
- **Confidence:** HIGH · **Sources:** L-04, L-03

#### LC-07 — External and guest users are licensed like internal users, and the licence must be in the **right tenant**
- **Classification:** CONSTRAINT · **Origin:** MS-L
- **Evidence:** *"The guest user must have a Power Apps license assigned through one of the following tenants: The tenant hosting the app being shared; The home tenant of the guest user. **When using Microsoft Dataverse as the data source, be sure that the guest user is licensed from the same tenant where you have Dataverse data located.** Also, the guest must have the same license that's required for non-guests to run an app"* (L-04). For Power Pages internal users the same tenant rule applies: *"Users should access the Power Pages site using their Entra ID and utilizing the out of the box Azure AD provider. **Users need a license assigned in the same tenant as the Power Pages site. If the user's license is assigned in a different tenant, it's not recognized**"* (L-04).
- **Why it matters:** "Share it with the partner's team" is not a free action, and the *location* of the licence matters as much as its existence. A guest holding a Power Apps licence in their own tenant is covered for a non-Dataverse app but **not** for a Dataverse-backed one unless licensed in the host tenant. This is a silent trap in supplier-collaboration and joint-venture scenarios.
- **Decision impact:** Requirement "external organisations participate in the process" → the economics change qualitatively, and two paths diverge: guest-licensed app access (needs licences in the correct tenant, and Dataverse tightens that) versus Power Pages authenticated capacity (priced per unique visitor per month, LC-12). For a large or unpredictable external population the second is normally the intended model; for a handful of named partners the first may be simpler. Decide this in Options, and record the tenant of record for every licence.
- **Confidence:** HIGH · **Sources:** L-04

#### LC-08 — Capacity licences buy **throughput and autonomy**, not access — and they cannot replace user licences
- **Classification:** CONSTRAINT + TRADE-OFF · **Origin:** MS-L
- **Evidence:** The distinction: *"**User license** — User-centric: a user license is assigned to a user. It entitles the user to access specific capabilities. **Capacity license** — Automation-centric: a capacity license is allocated to a Power Automate automation (cloud flow, machine, hosted machine, hosted machine group). It provides the automation entitlements (the same way a user license provides entitlements to a user)."* Process licence: *"When assigned to a cloud flow, a Power Automate Process license entitles it to higher action limits and allows use of premium and custom connectors **regardless of the owning or triggering user's license. Flows must be in a solution for a Process license to be assigned.** Allocated to a machine, a Process license becomes an unattended bot that can run one desktop flow at a time… Each Process license includes up to 250,000 actions per day… **Up to 10 Process licenses can be stacked on a single cloud flow**, with each additional license adding 250,000 actions… Alternatively, you can assign a Process license to a **flow group** to share 250,000 actions per day across up to 25 cloud flows. Child flows must be explicitly added to the group. Stacking isn't available for flow groups."* And the boundary, stated as an Important callout: *"**Capacity licenses aren't meant to replace user licenses in an environment**, as some essential capabilities are only available to licensed users, including creating and running automations running desktop flows attended or unattended… Allocation of a Process license to a machine (required by the unattended mode) **still prerequires the machine was registered by a Power Automate Premium user**"* (L-05, `ms.date` 2026-07-20). Microsoft also gives the sizing method: *"To ensure you purchase sufficient capacity, estimate your daily usage — (actions per run) × (runs per day) — and purchase Process licenses to cover that volume"* (L-05).
- **Why it matters:** Capacity licensing is the mechanism that decouples an automation's economics from its owner's payroll status — which is exactly what a business-critical automation needs (→ PF-29: throughput follows the owner's licence and reverts to Low when the owner leaves). But it comes with a hard prerequisite chain: a Process licence on a machine still requires a Premium *user* to have registered that machine, so unattended RPA cannot be licensed purely by capacity. The stacking arithmetic is also a genuine design lever: 10 stacked Process licences on one flow give 2.5 million actions/day, whereas a flow group spreads one Process licence across up to 25 flows and cannot be stacked — so *concentrated high volume* and *many low-volume flows* have different optimal shapes.
- **Decision impact:** Requirement "business-critical automation must not depend on an individual" → capacity licence assigned to the flow (which requires the flow to be **in a solution**, coupling licensing to ALM, → OP-15). Requirement "high daily action volume in one process" → stack Process licences on the flow. Requirement "many modest flows under one owner-independent budget" → flow group. Requirement "unattended RPA" → Process/Hosted Process **plus** a Premium user to register the machine. Size with Microsoft's own formula before purchasing.
- **Conditions:** *"The Power Automate Hosted Process superset behavior (allowing it to be applied to machines and cloud flows) isn't yet available"* — a documented gap between the stated model and the current implementation (L-05).
- **Confidence:** HIGH · **Sources:** L-05

#### LC-09 — API consumption is metered, retries are billed, and the enforcement date is **unknown**
- **Classification:** RISK · **Origin:** MS-L
- **Evidence:** What counts: *"**Power Apps**: All API requests to connectors and Microsoft Dataverse. **Power Automate**: All API requests to connectors, process advisor analysis, HTTP actions, and built-in actions from initializing variables to a simple compose action. **Both successful and failed actions count toward these limits. Retries and requests from pagination also count as action executions.** **Dataverse**: All create, read, update, and delete (CRUD), assign, and share operations including user-driven and internal system requests… These operations include plug-ins, classic workflows, and custom controls"* (L-11, `ms.date` 2026-08-14). Overage handling: *"Microsoft reserves the right to enforce limits for overages. If you experience high usage enforcement, you might see throttling. **Buy more capacity to avoid high usage enforcement, or move your environment to pay-as-you-go and pay for usage above daily limits.**"* The add-on: *"Each capacity add-on raises the request limit by another 50,000 per 24 hours. Multiple capacity add-ons can be assigned to increase limits"* — but *"You can't assign Power Platform requests capacity add-on packs to users or flows during the transition period."* Timing: *"Any possible high usage enforcement won't happen until six months after Power Platform Request usage reporting is generally available in the Power Platform admin center"* and *"**There's no current ETA for when GA happens.**"* Non-licensed pool: *"500,000 base requests + 5,000 requests accrued per USL up to 10,000,000 max"* for Dynamics 365 Enterprise/Professional; *"25,000 base requests with no per-license accrual"* for Power Apps and for Power Automate; *"All application users, non-interactive users, administrative users, and system users within the tenant **share tenant-level limits**"*; entitlements *"don't roll over"* day to day or month to month (L-11).
- **Why it matters:** Three cost effects. (1) An unreliable dependency is a *cost* driver, not only a reliability problem: retries are billed, and Medium/High profiles retry up to 12 times per action (→ PF-38). (2) The remedy Microsoft offers for throttling is **commercial** — buy capacity, buy a Process licence, or switch to pay-as-you-go — so a performance symptom is resolved with a purchase order. (3) The tenant-level non-licensed pool is shared by every service principal and integration account, so one integration's growth consumes another project's headroom, with no project-level visibility. And the enforcement date being unknown means an estate can be structurally non-compliant today with no bill and no error.
- **Decision impact:** Model API consumption as a cost line, not only a limit: (actions per run) × (runs per day) × (1 + expected retry rate), per identity. Record the tenant non-licensed pool as a **shared resource with a named owner** (→ OP-21). Treat the transition period as a dated risk with a revalidation trigger (PPR reporting GA), and check whether any option's economics depend on transition-period generosity (→ LC-AP-06 below).
- **Confidence:** HIGH · **Sources:** L-11

### 2.3 Cost drivers

#### LC-10 — Storage overage **blocks environment lifecycle operations**, which turns a capacity problem into a delivery and recovery problem
- **Classification:** RISK · **Origin:** MS
- **Evidence:** *"The following administrative environment lifecycle operations aren't available when the required storage capacity isn't available to support the operation: **Create a new environment** (requires minimum 1-GB capacity available); **Copy an environment**; **Restore an environment**; Convert a trial environment to paid; **Recover an environment**; Add Dataverse database to an environment."* Notification ladder: *"Notifications for capacity approaching storage limits are triggered when any of the three storage capacities (database, file, or log) have less than **15%** of capacity available after cross capacity-type borrowing is applied. Another warning notification that admin operations could be impacted is sent when any of the three storage capacities have less than **5%** of capacity available."* Cross-type borrowing is one-directional: *"Capacity can flow only from Database to File, and never in the opposite direction: Database → Log → File"* — so *"Database overages can't be offset because Database is the highest-value storage type"* and *"File capacity can't be used to offset Database or Log overages."* Also *"All environments consume 1 GB, regardless of whether they have an associated database"*, and Teams, Trial, Preview, Support and Developer environments *"don't count against capacity and show as 0 GB"* (L-02).
- **Why it matters:** This is the sharpest **cost ↔ operations** coupling in the platform, and it inverts the usual intuition. Being over storage entitlement does not degrade the running solution — it disables **restore**. So a capacity problem discovered during an incident is a recovery problem (→ OP-14: restore requires 1 GB free). It also disables environment creation and copying, which stops ALM (→ OP-15). And the one-directional borrowing rule means a large file estate cannot rescue a database overage, only the reverse.
- **Decision impact:** Capacity headroom is a **recoverability** requirement, not a finance nicety. Encode: monitor all three types independently; treat the 5% notification as an incident-readiness alarm; keep ≥ 1 GB free at all times as a restore precondition. Note the environment-count effect: every environment costs 1 GB even empty, so environment proliferation has a direct capacity cost (→ LC-25), while developer and trial environments are free of it.
- **Confidence:** HIGH · **Sources:** L-02

#### LC-11 — The largest **unbudgeted** storage consumers are audit logs, search indexes and file attachments, and one of them can only be reduced by disabling a capability
- **Classification:** RISK · **Origin:** MS
- **Evidence:** Log capacity is consumed by `AuditBase`, `PlugInTraceLogBase` and elastic tables (L-02), and **no Power Apps or Power Automate user licence accrues any log capacity** (LC-05). Search index: *"Storage consumed by Dataverse search is reported at the environment level as a table called **DataverseSearch**… **All Dataverse indexes are reported at the Dataverse database capacity rate.**"* And the index is not optional in practice: *"**Don't turn off Dataverse search.** Turning off Dataverse search directly impacts all dependent generative AI experiences in your different applications and all users using them."* Turning it off is also slow and destructive: *"Environment admins have 12 hours to turn the feature back on without losing indexed data. After 12 hours: The system permanently deletes all indexed Dataverse data… Syncing might take up to an hour or more for average size organizations, and **a couple of days for large organizations**… an organization with 500 GB [of indexed data] might take multiple days."* Indexes generally: *"Database storage includes both the database rows **and index files**… Common causes for an increase in index size include: An organization uses new functionality… Data volume or complexity changes… If you configure Quick Find lookups for data that's frequently used, this configuration also creates more indexes."* Files migrate between types on their own: *"File-type data such as 'Annotation' and 'Attachment' is moving from database to file storage. This change leads to decreased usage of database capacity and an increase in file capacity"* (L-02).
- **Why it matters:** All three are *consequences of doing the right thing*. Auditing is a governance requirement; search indexing powers the search and AI experiences users expect; attachments are how people actually work. None appears in a licence-based capacity estimate, log capacity is funded by no licence at all, and search index storage is billed at the **highest** rate (database). The 12-hour/multi-day asymmetry means "turn off search to save storage" is not a reversible tuning action.
- **Decision impact:** Any capacity model must include, as separate lines: audit volume × retention (a governance decision with a direct cost, → OP-10), search index size (a function of how many tables and columns are indexed), and attachment growth. Requirement "retain audit for N years" → cost it, and consider long-term retention/archival (→ LC-11 remedy below) rather than live log capacity. Do not plan to reclaim storage by disabling search.
- **Confidence:** HIGH · **Sources:** L-02

#### LC-12 — Power Pages is priced per **unique visitor per website per month**, which makes the counting rules an architectural specification
- **Classification:** DECISION CRITERION · **Origin:** MS-L
- **Evidence:** *"Power Pages licensing is capacity based and offers two types of capacities based on user type: **Authenticated users per website/month** and **Anonymous users per website/month**."* Counting: *"Authenticated users per website/month are calculated as unique users who log into the website in a calendar month duration. Even if a user logs in multiple times to a website in a calendar month, then that user is counted as one user. **Uniqueness is determined by using the ID of the contact record (Microsoft Dataverse contact table) to which the user is mapped.**"* And anonymously: *"Uniqueness is determined through a unique anonymous user ID stored in a browser cookie. **If the user accesses the site using different browsers or devices or cleans up browser cookies, then a new anonymous user ID is generated and the user would be counted as a different user.**"* Sizing is by *actual* unique users, not potential: *"Suppose I create a Power Pages website that can potentially be used by 100,000 authenticated users. However, in a given month it will only be used by 5,000 users… **the customer should purchase capacity for 5,000 users.**"* Subscription tiers (per capacity pack per month, list): authenticated 100 users/pack at **$200** (tier 1), **$75** (tier 2, min 100 packs), **$50** (tier 3, min 1,000 packs); anonymous 500 users/pack at **$75**, **$37.50**, **$25**. Minimum assignment per environment: *"**Authenticated users**: Minimum quantity that needs to be assigned to an environment is 25… **Anonymous users**: Minimum 200 per environment."* No carry-over: *"Power Pages are licensed at a monthly rate that is based on a customer's anticipated user volume. **They aren't accumulated as individual assets and wouldn't carry forward month to month.**"* Included capacity: authenticated plan 5 GB database per tenant + 2 GB database and 16 GB file per capacity pack; anonymous plan 5 GB + 500 MB and 4 GB (L-04, `ms.date` 2026-08-14).
- **Why it matters:** The counting rules are load-bearing design constraints, not billing trivia. (1) Authenticated uniqueness is the **contact record**, so a contact-deduplication defect is a billing defect — the same human counted twice. (2) Anonymous uniqueness is a **browser cookie**, so cookie clearing, multiple devices and privacy-mode browsing all inflate the count, which means the anonymous meter systematically over-counts a privacy-conscious audience. (3) Per-website counting means a user visiting three sites in one environment counts three times, so **site decomposition is a cost driver** exactly as app decomposition is (LC-04). (4) Unused capacity evaporates monthly, so this is a forecast-and-true-up model with a real penalty for over-buying — and it has steep volume tiers, so the *shape* of the forecast changes the unit price by 4×.
- **Decision impact:** Requirement "public-facing site" → forecast *unique monthly visitors*, not page views or registered accounts; size anonymous capacity with a deliberate over-count allowance for cookie churn; verify contact deduplication is part of the solution (a data-quality requirement with a commercial consequence, → DA cross-ref). Requirement "several external-facing surfaces" → prefer one site with role-based content over several sites, unless there is a governance reason to separate them. Compare subscription against the pay-as-you-go meter (LC-20) on demand *predictability*, not on unit price.
- **Confidence:** HIGH (for the model and rules on that date; treat prices per 0.3) · **Sources:** L-04

#### LC-13 — Power Pages performance capacity and licensing capacity are **the same purchase**
- **Classification:** TRADE-OFF · **Origin:** MS
- **Evidence:** *"**Scaling of these application servers is done automatically based on the Power Pages licensing capacity assigned to the environment**"* (L-12, `ms.date` 2026-04-28 — see PF-16 for the full architecture). CDN and WAF are not separately charged: *"**Do I require extra licensing for Power Pages content delivery network (CDN) and web application firewall (WAF) capabilities?** No. Both CDN and WAF capabilities are included as part of Power Pages licensing and don't require any extra licenses to be purchased"* (L-04).
- **Why it matters:** The only published dial for Power Pages throughput is a commercial one. So "the site is slow under load" and "we need to buy more capacity" are the same sentence — which means a performance requirement translates directly into a licensing line, and a licensing decision to buy the minimum viable capacity is simultaneously a decision about performance headroom. The CDN/WAF inclusion is the compensating good news: the two highest-leverage scale and protection features cost nothing extra and should be switched on by default (CDN is off by default, PF-16).
- **Decision impact:** Requirement "external site must absorb a campaign or seasonal peak" → capacity headroom is the mechanism, and it must be bought *before* the peak because unused capacity does not carry forward (LC-12) and the peak month is the month that counts. Always enable CDN and WAF — they are free and they reduce the capacity needed. This is the cleanest example in the corpus of **performance ↔ cost** being one decision (→ PF-16).
- **Conditions:** The relationship between capacity purchased and throughput delivered is **UNPUBLISHED** (PF-U-03) — so the size of the headroom bought cannot be predicted, only observed.
- **Confidence:** HIGH for the coupling; UNKNOWN for its magnitude · **Sources:** L-12, L-04

#### LC-14 — Dataverse for Teams is a **capped free tier** whose ceiling is a migration trigger, not a purchasable limit
- **Classification:** CONSTRAINT · **Origin:** MS-L
- **Evidence:** *"When the environment capacity limits are reached (**2 GB per environment**) new solutions (apps, chatbots, flows) can't be created or installed in that specific Dataverse for Teams environment."* Existing work survives: *"Existing solutions in the environment continue to work (CRUD allowed). **The environments will be able to continue to grow beyond the 2 GB limit.**"* No purchase path: *"**Can customers purchase more capacity for a Dataverse for Teams environment?** No. Dataverse for Teams provides support for approximately **1 million rows per team.**"* Capability exclusions: *"**Can I use AI Builder with Dataverse for Teams?** No."* *"**Can I use desktop flows with Dataverse for Teams?** No."* *"Custom connectors aren't supported in Dataverse for Teams."* Premium connectors *do* work but only with licences: *"accessing premium connectors in the context of an app requires all users accessing the app to be licensed by either the Power Apps per app or per user plan."* And the exit is not clean: *"**Can customers package and export their solution (app/flow/chatbots) built in Dataverse for Teams, and then import that into an environment…?** This capability isn't available yet, but is included in our roadmap."* Reasons to upgrade beyond capacity: *"Enterprise ALM, data types; Support for log and managed data lake; Rich access control, auditing; Governance and security"* (L-04). Teams environment capacity *"doesn't count toward your organization's Dataverse usage"* (L-02).
- **Why it matters:** It is genuinely free and genuinely a trap for anything that succeeds. The 2 GB ceiling stops *new* solution creation while letting data keep growing, so the failure mode is "we can't change it any more" rather than "it stopped". And with solution export to a full environment not yet available, a successful Teams-built solution may have to be **rebuilt** rather than migrated — a technical-debt cost created by an economic decision taken at the start.
- **Decision impact:** Dataverse for Teams is appropriate for genuinely departmental, non-critical, Teams-scoped work with no audit, ALM, RPA, AI Builder or custom-connector requirement. Any solution with a plausible path to business-criticality should start in a standard environment, because the migration path is incomplete. Encode as a Discovery-detectable decision: "is there any chance this becomes business-critical?" → if yes, the free tier is more expensive.
- **Confidence:** HIGH · **Sources:** L-04, L-02

#### LC-15 — AI and Copilot consumption is a **separate currency with monthly peak-based enforcement**, and one entitlement is already scheduled for removal
- **Classification:** CONSTRAINT + RISK · **Origin:** MS-L
- **Evidence:** *"AI Builder consumes either AI Builder credits or Copilot Credits, depending on the context. You need to have this capacity available in your environment to run AI Builder features."* Enforcement shape: *"Whether you use AI Builder credits or Copilot Credits, capacity is enforced on a monthly basis. **Purchase capacity for the peak utilization monthly period.**"* Consumption is not predictable per operation: *"**The amount of capacity consumed varies based on the AI model and the size and complexity of the data set**… Different scenarios (for example, forms processing, prediction, etc.) consume service credits at different rates."* Training is free: *"Training a model doesn't consume any kind of credits."* Included entitlement, and its expiry: Premium, Process and Hosted Process each include *"AI Builder credits | 5000 per month"* (L-05) — but *"**Note: The 5,000 AI Builder credits will be removed on November 1, 2026**"* (L-04). Copilot Studio consumption meter: *"The Copilot Studio pay-as-you-go meter counts the total number of **Copilot Credits** consumed by agents. Copilot Credits are a measure of the time and effort required for your agent to retrieve information and respond to your prompts and any actions that the agent takes… The number of Copilot Credits decreased for each response or action is dependent on the complexity of the task completed by the agent"* at **$0.01 per credit** (L-03).
- **Why it matters:** Three properties make AI consumption economically different from everything else in the platform. (1) It is **peak-based** — you buy for your worst month, not your average, so a seasonal AI workload is priced at its seasonal peak all year unless run on the consumption meter. (2) Per-operation consumption is *"dependent on the complexity of the task"*, which means **unit cost is not knowable in advance** and cannot be modelled from a volume estimate alone. (3) A currently-included 5,000-credit entitlement disappears on a published date, so any business case resting on it has a known expiry.
- **Decision impact:** Requirement "AI/Copilot capability" → do not model it from a per-transaction estimate; establish consumption empirically in a pilot, then size for the peak month or use the consumption meter. Any option economics using the bundled 5,000 credits must state the **1 November 2026** expiry as a dated assumption with a revalidation trigger. This is the highest-volatility sub-area in the highest-volatility file — treat every AI cost claim as Assumed with a short validity.
- **Confidence:** HIGH (that these are the mechanisms and the date) / UNKNOWN (unit consumption per operation) · **Sources:** L-04, L-05, L-03, L-08

### 2.4 The consumption model — where architecture and economics meet

#### LC-16 — Pay-as-you-go replaces commitment with an Azure meter, and it **overrides prepaid capacity in the same environment**
- **Classification:** FACT + RISK · **Origin:** MS-L
- **Evidence:** *"Pay-as-you-go is a new way to pay for Power Apps and Power Automate using an Azure subscription, which allows you to get started building and sharing apps **without any license commitment or upfront purchasing**… allows you to share apps and Power Automate flows with any user in your organization and then only pay if and when they're used"* (L-13, `ms.date` 2025-05-29). Mechanics: *"you can link environments to an Azure subscription using a billing policy… An environment can only be linked to one billing plan at a time"*, and the Azure resource created is a *"Power Platform account resource"*, so *"Customers can also use Azure resource groups and Azure tags to organize their Power Platform account resources and track and allocate spending."* And the override behaviour, stated three times for three different prepaid assets: *"If an environment already has **app passes** assigned and is enabled for pay-as-you-go, **app passes are ignored and not consumed.** You can reallocate those app passes to a different environment."* *"When an environment is enabled for pay-as-you-go, any capacity for Power Apps portal logins/page views or **Power Pages authenticated user/anonymous user prepaid capacity** that is assigned to the environment **is ignored and not consumed.**"* *"If an environment has **Unattended bot add on units** assigned and then pay-as-you-go is turned on for that environment, every unattended flow run in the environment is charged. **Any Unattended bots add-on units are ignored** and can be reassigned"* (L-03).
- **Why it matters:** Two things. (1) It converts a licence-procurement problem into an Azure cost-management problem, with real benefits: no commitment, per-environment cost attribution via billing policies, resource groups and tags — which is the only mechanism in the platform for allocating Power Platform cost to a business unit. (2) The override is a genuine footgun: switching an environment to pay-as-you-go **silently invalidates** prepaid capacity assigned to it. An admin doing the right thing for flexibility can double-pay unless the prepaid capacity is deliberately reallocated.
- **Decision impact:** Requirement "attribute Power Platform cost to business units" → billing policies plus Azure tags is the documented mechanism, and it operates **per environment**, which couples cost attribution to environment strategy (LC-25). Before enabling pay-as-you-go on any environment, audit what prepaid capacity is assigned to it and reallocate. Record pay-as-you-go enablement as a change with a cost consequence, needing an owner (→ OP-21).
- **Confidence:** HIGH · **Sources:** L-13, L-03

#### LC-17 — The consumption units are the architectural facts worth encoding
- **Classification:** FACT · **Origin:** MS-L
- **Evidence:** Verbatim meters and rates (L-03, `ms.date` 2026-08-14; **prices illustrative per 0.3**):

| Meter | Unit counted | Rate |
|---|---|---|
| Power Apps per-app | *"The total number of unique monthly active users of each app… An active user is someone who opens an app at least once in the given month. Repeat access of an app by a user isn't counted. Users with Power Apps per-user licenses aren't counted."* | $10 per active user/app/month |
| Power Automate flow runs (preview) | *"Flow runs for premium cloud flows and desktop flows. **Flows with standard connectors are excluded from charges.**"* | $0.60 per cloud or attended-desktop run; **$3.00** per unattended or hosted-RPA run |
| Dataverse | *"any usage exceeding 1 GB or the allocated capacity per pay-as-you-go environment"* for database and file; *"If auditing is turned on, any resulting log storage usage exceeding allocated capacity is counted."* | **$48** per GB/month database · **$2.40** per GB/month file · **$12** per GB/month log |
| Power Platform requests (coming soon) | Requests above the daily licence entitlement | $0.00004 per request/day above entitlement |
| Power Pages (preview) | Unique monthly active authenticated / anonymous users per website | $4 per authenticated user/website/month · $0.30 per anonymous |
| Copilot Studio | Copilot Credits consumed by agents | $0.01 per credit |

Measurement of storage: *"The measurement of usage for each category of Dataverse storage happens once per day (30 measurements per month). The usage snapshot in each snapshot is then multiplied by 1/30th to get the fractional usage."* Free allowances: *"For pay-as-you-go environments, the first 1 GB of Dataverse database storage and 1 GB of file storage are included at no charge. **However, any log storage consumption is billed immediately.** Log storage is utilized only if auditing is enabled."*
- **Why it matters:** The **relative** rates encode design guidance that outlives the absolute numbers. Database storage costs **20× file storage** per GB, so where a large object can legitimately live in file storage rather than database storage that is a 20× decision — and Microsoft is actively migrating attachments in that direction anyway (LC-11). Log storage costs **5× file storage** and has **no free allowance**, which prices auditing explicitly. An unattended RPA run costs **5× a cloud flow run**, which prices the choice between API integration and screen automation. And a standard-connector flow run costs **nothing**, which prices the premium boundary a second way (LC-03).
- **Decision impact:** Encode the *ratios*, not the prices: database ≫ log ≫ file per GB; unattended RPA ≫ cloud flow per run; premium flow run ≫ standard flow run (which is free). Requirement "store many large documents" → file storage, not database columns. Requirement "automate a legacy UI" → the 5× multiplier is part of the case for building an API instead (→ AT2 RPA findings). Requirement "full audit" → a priced, unfunded line (LC-05, LC-11).
- **Confidence:** HIGH (for units and ratios on that date) · **Sources:** L-03

#### LC-18 — Microsoft publishes the **break-even logic** between prepaid and consumption, and it is about demand shape
- **Classification:** DECISION CRITERION · **Origin:** MS-L
- **Evidence:** The rule: *"**Pay-as-you-go is optimal for seasonal flows or flows with fewer runs but more users. Prepaid is optimal for personal automation flows and flows with lot of runs.**"* And Microsoft's own worked comparison (L-03, prices illustrative):

| Flow shape | Prepaid, 3 months | Pay-as-you-go, 3 months | Microsoft's recommendation |
|---|---|---|---|
| Automated/scheduled, 1 user, 145 runs | $45 (1 × per-user × 3) | $87 | **Per-user licence** |
| Instant, 10 users, 145 runs | $450 (10 × per-user × 3) | $87 | **Pay-as-you-go** |
| Attended RPA, 10 users, 145 runs | $1,200 | $87 | **Pay-as-you-go** |
| Unattended RPA, 2 concurrent | $1,020 | $435 | **Pay-as-you-go** |
| Seasonal, 1 user, 40 runs in month 3 only | $45 | $24 | **Pay-as-you-go** |
| Organisational flow under a service principal | $300 (per-flow licence) | $87 | **Pay-as-you-go** |

Also, for apps: *"**Widely distributed apps:** Use the pay-as-you-go plan for apps that need to be shared with a large user base with infrequent and/or unpredictable use. **Establish usage patterns:** Understand adoption patterns for new apps to determine whether prepaid licenses make financial sense"* (L-13). And they coexist: *"Prepaid flows and Pay-as-you-go flows can coexist in same environments as Pay-as-you-go plan complements prepaid subscriptions. Admins can understand usage patterns using Power platform admin center reports and move users to prepay licenses for optimal pricing"* (L-03).
- **Why it matters:** The discriminator is not price, it is **the shape of demand**: many users × few interactions favours consumption; few users × many interactions favours prepaid. That is a *requirements* question answerable in Discovery without naming a product ("how many people, how often each?"), which makes it exactly the kind of thing aisa should be asking early. Note that five of Microsoft's own six examples come out in favour of pay-as-you-go, which is a useful corrective to the default assumption that licences are the norm.
- **Decision impact:** For every candidate solution, capture the *(population × frequency)* shape before comparing costs, and evaluate prepaid and consumption side by side. Use consumption deliberately for the "establish usage patterns" case — a rollout where adoption is genuinely unknown should not be committed to per-user licences before it is measured. Plan a periodic true-up: Microsoft's own advice is to move users to prepaid once patterns are known.
- **Confidence:** HIGH · **Sources:** L-03, L-13

#### LC-19 — The consumption meter has **exemptions and asymmetries** that change automation design
- **Classification:** FACT · **Origin:** MS-L
- **Evidence:** Free by design: *"To make it easy to test and fix your flows, **no charges are incurred if you're testing your flow in the designer or resubmitting failed runs.**"* Child-flow asymmetry: *"**If you use the 'Child flow' feature for cloud flows or attended flows, there's only a single charge for the parent flow run, no charges are incurred for child flow runs. For unattended flows, both parent and child flow runs are charged.**"* Whose entitlement applies: *"For automated or scheduled flows, the license entitlements of the **flow owner** apply. For instant and Power Apps-triggered flows, the license entitlements of the **user running the flow** apply."* Service principals: *"If the owner of a flow is service principal, the flow runs are charged unless the flow has a per-flow license."* Standard connectors: *"Flow runs of flows with standard connectors aren't charged."* Preview cap: *"During the public preview, there may be limits on the maximum number of runs that are charged to a single flow in a pay-as-you-go environment per day. Starting on 9/1, the limit is **1000 per day**… The downloadable pay-as-you-go report in the Power Platform admin center shows the full and accurate number of flow runs, but **the number billed to Azure may be lower.** We recommend that any flows with a high number of runs use a Power Automate per flow plan, as that is a fixed price per month"* (L-03).
- **Why it matters:** These are design levers, not billing details. (1) Child-flow decomposition — which PF-33 recommends on *maintainability* grounds to stay under the 500-action limit — is **free for cloud/attended flows** and **doubly charged for unattended** ones. So the same good design practice has opposite cost signs depending on run mode. (2) Free resubmission of failed runs means retry-and-fix operations do not carry a cost penalty, which removes a perverse incentive against proper error handling (→ OP-09). (3) The 1,000-run/day billing cap during preview means today's bill may understate real usage — a number that will change without the usage changing.
- **Decision impact:** Decompose cloud-flow logic into child flows freely; think twice for unattended RPA. For any high-run-count automation, Microsoft's own recommendation is a per-flow (capacity) licence for price certainty rather than the consumption meter. Do not build a cost model on the preview-capped billed figure — use the admin-centre report's full count.
- **Confidence:** HIGH · **Sources:** L-03

#### LC-20 — The Power Pages anonymous meter systematically **over-counts a privacy-conscious audience**, and monitoring can inflate it
- **Classification:** RISK · **Origin:** MS-L
- **Evidence:** *"For Anonymous users, uniqueness is determined through a unique anonymous user ID stored in a browser cookie. Repeat access of the website by a user isn't counted as long as the anonymous user ID stored in the cookie remains same. **If the user accesses the site using different browsers or devices or cleans up browser cookies, then a new unique anonymous user ID is generated and user would be counted as a different user.**"* Exclusions that do work: trial and private mode; authentication pages (sign in, register, invitation, external authentication callback); system pages starting `/_` such as `/_services` and `/_resource`; 3xx, 4xx and 5xx responses; static resources only (CSS, JavaScript, images); *"Bots and crawler access of the anonymous pages of the website isn't counted"*; and a user who authenticates later the same UTC day is counted only as authenticated. Monitoring caveat: *"If you use a monitoring system setup to test website availability periodically, its usage of the website isn't counted if it sends a nonbrowser user agent. **If your monitoring system sends a user agent of any standard browser, it might be counted as an anonymous user.** We recommend to targeting your monitoring service at the /_services/about page of your website to ensure that it isn't counted"* (L-03, L-04).
- **Why it matters:** Two independent inflation sources on a meter that is billed monthly with no carry-over. (1) The same human on a phone and a laptop, or one who clears cookies, is billed two or three times — so the *same* audience costs more if it is privacy-conscious or multi-device, which correlates with exactly the public-sector and consumer audiences Power Pages targets. (2) An availability monitor — a good operational practice (→ OP-07) — can bill itself as traffic unless it is deliberately pointed at `/_services/about` or sends a non-browser user agent. The operations team's uptime check can become a line on the bill.
- **Decision impact:** Forecast anonymous capacity with an explicit multi-device/cookie-churn multiplier rather than from a unique-person estimate. Configure any external availability monitor per Microsoft's guidance (`/_services/about`, non-browser UA) — and record that as an operations requirement with a cost rationale. This is the clearest **cost ↔ operations** interaction in the file.
- **Confidence:** HIGH · **Sources:** L-03, L-04

### 2.5 Total cost of ownership

#### LC-21 — Licence cost is one of at least twelve cost lines, and the documentation only prices one of them
- **Classification:** DECISION CRITERION · **Origin:** INF over MS facts
- **Evidence:** Microsoft prices licences and capacity (L-01…L-05, L-11, L-13, L-03). It states, but does not price, the following as real costs of ownership. **Environments and non-production estate:** *"There are costs associated with maintaining separate test environments, storing data, using tooling, and running tests"* (L-14, `ms.date` 2026-07-17); *"All environments consume 1 GB, regardless of whether they have an associated database"* (L-02). **Monitoring:** *"**Tradeoff**: Logic monitoring tools are likely to increase costs"* (L-15, `ms.date` 2025-08-15); *"**Tradeoff**: There are cost implications for storing and querying logs. Notice how your log analysis and retention affects your budget"* (L-16, `ms.date` 2025-08-18). **Personnel and skills:** *"Performance needs time, money, effort, and people. Allocate resources wisely from the beginning of your project. For example, developers might need extra time to find efficient ways to implement business logic and optimize code. You'll also need a testing environment and a team to conduct performance testing"* and *"Performance is not a one-time activity. As your workload usage changes and the platform evolves, you need to revisit the code and continue to find ways to optimize"*; also *"**Personnel**: Assess the human resources required to manage and maintain the infrastructure, handle customer support, perform system maintenance, and ensure smooth operations"* (L-17, `ms.date` 2025-08-15). **Optimisation expertise:** *"**Tradeoff**: Optimizing logic and hot paths requires expertise. Identifying logic inefficiencies is subjective and might require highly skilled individuals, whom you may need to pull from other tasks"* (L-15). **Testing effort:** *"**Tradeoff**: Testing takes time and skill to perform and can affect operational efficiency"* (L-14). **Support plans:** creating a support request *"you must have an active support plan"*, with advisory services only at Professional Direct and Unified levels (L-18, `ms.date` 2026-05-15; L-19, `ms.date` 2025-07-31). **Azure dependencies:** Application Insights, Log Analytics and Sentinel are Azure-billed (L-16); pay-as-you-go itself runs through an Azure subscription (L-13). **Governance tooling:** the CoE Starter Kit *"is no longer actively maintained"* and its capabilities have moved into the admin centre (→ OP-27), so governance tooling cost has shifted from a free community kit to product features gated by managed environments (LC-23).
- **Why it matters:** Because there is no Cost Optimization pillar for Power Platform (LC-01), these lines are scattered as incidental callouts inside performance and reliability guidance. Assembled, they show that a licence-only business case omits: non-production environments, monitoring and log retention, support plans, Azure services, testing effort, optimisation expertise, ongoing performance work, governance tooling, migration, training, and technical debt. Two of those — monitoring and testing — are things Microsoft *requires* for a well-architected workload while simultaneously flagging that they cost money.
- **Decision impact:** Every option's economics must include at minimum: (1) licences and capacity; (2) storage across all three types including audit and index (LC-05, LC-11); (3) environment count × 1 GB, plus non-production tooling; (4) monitoring, telemetry retention and any Azure services; (5) support plan tier appropriate to the criticality (→ OP-24); (6) build effort; (7) ongoing optimisation and maintenance effort; (8) governance/ALM tooling and its licence gating (LC-23); (9) migration and training; (10) an explicit technical-debt provision. Items (4)–(10) are where a Power Platform business case usually fails, and none of them is priced by Microsoft.
- **Confidence:** MEDIUM (each individual cost is MS-stated; the assembly into a TCO model is INF) · **Sources:** L-14, L-15, L-16, L-17, L-18, L-19, L-02, L-13

#### LC-22 — Support is a **separate purchase**, and its tier determines what help exists for a production incident
- **Classification:** CONSTRAINT · **Origin:** MS
- **Evidence:** *"You can access self-help resources in the Support experience without a support plan. **However, to create a support request, you must have an active support plan**"* — the named plans being *"Subscription support; Professional direct support; Unified support"* (L-18). Scope by tier: *"Support for billing, subscription management issues, and technical break-fix issues is available at all support levels. **Advisory, escalation, and account management services are available at the Professional Direct and Microsoft Unified Support levels.**"* Initial response times: Severity A *"Less than one hour"* on all three tiers with 24×7 access; Severity B *"Standard: Less than four hours; ProDirect: Less than two hours; Unified enterprise: Less than two hours"*; Severity C *"Standard: Less than eight hours; ProDirect: Less than four hours; Unified enterprise: Less than four hours"*, business hours only (L-19).
- **Why it matters:** The right to open a ticket is a purchase, and the difference between tiers is measured in hours of initial response on the severities that are *not* a total outage — which is where most real production pain sits. It also means an organisation can hold every Power Platform licence and still have no route to Microsoft when something breaks.
- **Decision impact:** Support-plan tier is a **cost line derived from the criticality requirement**, and it must appear in the option's economics whenever the workload is business-critical (→ OP-24 for what support does and does not do, including the four-hour performance-case limit and the refusal to conduct RCAs). Requirement "mission-critical, 24×7" → a Standard plan's eight-hour Severity C response is likely insufficient, and that is a budget consequence of an availability requirement.
- **Confidence:** HIGH · **Sources:** L-18, L-19

#### LC-23 — Managed environments put the **governance and operations feature set behind a premium licence**
- **Classification:** CONSTRAINT · **Origin:** MS-L
- **Evidence:** *"Managed environments are a suite of **premium capabilities**… A managed environment encompasses, but isn't limited to, the following features: Environment groups; Limit sharing; Weekly usage insights; Data policies; **Pipelines in Power Platform**; Maker welcome content; Solution checker; **IP Firewall**; IP cookie binding; **Customer Managed Key (CMK)**; **Lockbox**; **Extended backup**; Data policies for desktop flow; **Export data to Azure Application Insights**; Administer the catalog; Default environment routing; …**Virtual Network support**; Conditional access on individual apps; Control which apps are allowed in your environment; Create and manage masking rules."* Entitlement: *"Managed environments are included as an entitlement with standalone Power Apps, Power Automate, Microsoft Copilot Studio, Power Pages, and Dynamics 365 licenses."* And a carve-out: *"Managed environment **isn't included as an entitlement in the Developer Plan** when users run their assets"* (L-20, `ms.date` 2026-02-23). Concrete gating consequences elsewhere in this corpus: extended backup to 28 days is *"for production managed environments"* only (→ OP-14); cross-region DR requires *"a managed environment… This environment requires a premium license tier"* (→ LC-24); flow telemetry export is *"turned on and supported for managed environments only"* (→ OP-11); PPAC Monitor **recommendations** require a managed environment (→ OP-12); and for pipelines, *"All other environments used in pipelines must be enabled as managed environments. **Licenses granting premium use rights are required for all managed environments**"* (L-21, `ms.date` 2026-01-12).
- **Why it matters:** Nearly every capability an enterprise needs to *operate* a Power Platform solution responsibly — telemetry export, extended backup, DR, ALM pipelines, network isolation, customer-managed keys, DLP for desktop flows, sharing limits — is inside managed environments, and managed environments require premium user licensing for the environment's users. So **operational maturity is not free**: choosing to operate a solution properly changes the licence footprint of everyone who uses it. Conversely, an organisation that licences its users only through Microsoft 365 seeded rights cannot operate a managed environment, and therefore cannot have extended backup, DR, telemetry export, or pipelines.
- **Decision impact:** The moment a workload is classified as business-critical, the licence model is implicated — not because of what the app does but because of what operating it requires. Model this explicitly in Options: *criticality → operational requirements → managed environment → premium licences for that environment's users*. This is the most consequential **cost ↔ operations** coupling in the file, and it is the reason a "cheap" departmental solution becomes expensive the day it matters.
- **Confidence:** HIGH · **Sources:** L-20, L-21

#### LC-24 — Cross-region resilience costs a **second full copy of storage** plus a managed environment
- **Classification:** TRADE-OFF · **Origin:** MS
- **Evidence:** *"**What are the costs associated with using self-service disaster recovery?** You must select a managed environment. This environment requires a premium license tier… For secondary regions, your prepaid free storage and free Dataverse entitlements are used. **For example, suppose you have 10 GB of capacity consumption in the primary location. When you turn on self-service disaster recovery, you create a copy of the data in the remote secondary region and this copy consumes another 10 GB.** For the secondary region, this 10 GB storage comes from your existing entitlements."* Billing: *"A pay-as-you-go billing plan is no longer a mandatory requirement. The system checks for available free capacity in your tenant. All pooled Dataverse entitlements at the tenant level count towards secondary storage enablement. **Microsoft is evaluating various overage initiatives. Overage management is outside of self-service disaster recovery management scope.**"* Visibility: *"When you allow self-service disaster recovery, you see more storage consumption displayed in the Dataverse capacity graph, clearly indicating the extra capacity used by the cross-region backup"*, tagged *"Disaster recovery active"* (L-22, `ms.date` 2026-08-20).
- **Why it matters:** Regional resilience is priced in **storage capacity**, drawn from the same tenant pool that everything else draws from (LC-05) — so enabling DR on one environment reduces headroom for every other environment, and can push the tenant toward the overage state that blocks restore and environment creation (LC-10). The compounding irony: turning on disaster recovery can consume the capacity that restore requires.
- **Decision impact:** Requirement "survive regional loss" → cost it as (a) premium licences for the managed environment's users, (b) 2× the environment's storage consumption drawn from the tenant pool, (c) the throughput degradation for high-volume automation (→ PF-42), and (d) drill effort (→ OP-18). Verify tenant capacity headroom *before* enabling, and re-check the 15%/5% thresholds afterwards.
- **Confidence:** HIGH · **Sources:** L-22

#### LC-25 — Environment count is a cost driver on **four** independent axes
- **Classification:** DECISION CRITERION · **Origin:** INF over MS facts
- **Evidence:** (1) Storage floor: *"All environments consume 1 GB, regardless of whether they have an associated database"*, while *"Trial, preview, support, and developer environments don't count"* (L-02). (2) Per-app licence scope: *"Each per app license provides an individual user with rights to one app… **within a single environment**"* (L-04) — so the same app in two environments is two entitlements. (3) Power Pages minimum assignment: *"Minimum quantity that needs to be assigned to an environment is 25"* authenticated and *"Minimum 200 per environment"* anonymous (L-04) — so a small site in its own environment still pays a floor. (4) Managed-environment licensing: *"Licenses granting premium use rights are required for all managed environments"* (L-21), and pipelines require every non-development environment in the pipeline to be managed. Pay-as-you-go billing policies are also per environment (L-13), and *"An environment can only be linked to one billing plan at a time"* (L-13).
- **Why it matters:** Environment strategy is normally decided on governance and ALM grounds. Each of the four axes above means it is *also* a cost decision, and they point in different directions: more environments improve isolation and ALM but add storage floors, per-app entitlement duplication, Power Pages minimums, and managed-environment licence obligations. Meanwhile developer environments are free of the storage floor, which makes them the right place for the fan-out that ALM wants (L-21 confirms development environments in pipelines need not be managed and *"can be used for development and testing with the developer plan"*).
- **Decision impact:** Design the environment topology with the cost axes visible: keep development on developer-plan environments (free of capacity and managed obligations), keep the count of *managed* environments to those that genuinely require the premium feature set, consolidate Power Pages sites to avoid per-environment minimums, and align billing policies to the business units that should carry the cost. Cross-reference the governance-driven environment strategy rather than deciding it here.
- **Confidence:** MEDIUM (each fact is MS-sourced; the four-axis synthesis is INF) · **Sources:** L-02, L-04, L-21, L-13

### 2.6 Cost architecture — when the cheapest licence is the most expensive design

#### LC-26 — The Low performance profile is the clearest case of a cheap licence forcing an expensive architecture
- **Classification:** TRADE-OFF · **Origin:** INF over MS facts
- **Evidence:** Assembling the profile deltas (all from L-23, `ms.date` 2026-07-17, and L-11): a **Low**-profile owner gets 10,000 Power Platform requests/24 h, 5,000 array items per loop, 5,000 paginated items, **200 MB** content throughput per 24 h, 500 concurrent outbound calls, a 5-second minimum postpone interval, and a default retry policy of **2** attempts. A **High**-profile (Process/per-flow) owner gets 500,000 requests, 100,000 array items, 100,000 paginated items, **10 GB** content throughput, 2,500 concurrent outbound calls, a 1-second postpone floor and **12** retries. Membership is set by the *owner's licence* (Free, Microsoft 365 plans, Power Apps per app, Power Automate Plan 1, all trials and Team Member are Low). And Microsoft's own remedy for throttling is a purchase: *"Assign Power Automate Process licenses to the flow to dedicate capacity and avoid throttling"* (L-23). Separately, the 90-day inactivity suspension exempts *"Flows owned by users with premium licenses or assigned capacity licenses"* (L-23).
- **Why it matters:** The spread is not marginal — it is **50× on request entitlement and 50× on content throughput**. A team that licences the automation owner cheaply is buying an architecture that must be decomposed into more flows, more partitioned runs and more workarounds to fit inside a 200 MB/day and 10,000-request/day envelope. That decomposition is build effort, maintenance effort and complexity (→ PF-33), all of which cost more than the licence delta in most engagements. And a low-frequency but business-critical flow owned by a non-premium user is **switched off after 90 days**, so the cheap licence buys an availability defect.
- **Decision impact:** For any automation with meaningful volume, meaningful payload size, or business criticality, the owner's licence is an **architectural** decision and should be priced against the workaround effort it avoids. Encode the specific trap: document-heavy automation on a Low profile is capped at 200 MB/day and will need partitioning that a premium owner would not.
- **Confidence:** MEDIUM (facts are MS; the "cheaper licence costs more overall" conclusion is INF and engagement-specific) · **Sources:** L-23, L-11

#### LC-27 — Licence-avoidance architectures have documented costs of their own
- **Classification:** ANTI-PATTERN · **Origin:** INF over MS facts
- **Evidence:** Four documented cases where working around a licence boundary creates a worse architecture. (1) **Avoiding premium connectors by staying on SharePoint.** Standard-connector paths are licence-cheap (LC-03, LC-17) but SharePoint carries the documented performance penalties of all-column transmission, dynamic-column overhead and mandatory partitioning above hundreds of thousands of rows (→ PF-24), plus the ~5,000-item List View Threshold. (2) **Avoiding premium by keeping data duplicated into a standard-connector store.** Duplication consumes capacity twice (LC-05) and creates a synchronisation flow whose runs, retries and pagination all consume PPR (LC-09) — and Microsoft's own anti-pattern guidance is to avoid unnecessary data processing (L-15). (3) **Avoiding Dataverse capacity cost by keeping files in the database as columns.** Database storage is **20×** file storage per GB (LC-17), and Microsoft is actively migrating attachments the other way (LC-11). (4) **Avoiding managed environments to avoid premium licences.** This forfeits telemetry export, extended backup, DR, pipelines and network isolation (LC-23) — which are the mechanisms by which incidents get diagnosed and recovered, so the saving is paid back in support burden and outage duration (→ OP-21, OP-24).
- **Why it matters:** Each of these is a *rational local optimisation* that produces a globally worse system, and each is common. The pattern is always the same: a licence line is visible and a workaround cost is not, so the invisible cost wins the decision.
- **Decision impact:** Whenever a design choice is justified primarily by licence avoidance, require the workaround cost to be stated explicitly alongside the licence saving: extra storage, extra synchronisation runs, extra build effort, forfeited operational capability, extra support burden. If the workaround cost cannot be estimated, the licence-avoidance justification is not established.
- **Confidence:** MEDIUM (the individual mechanisms are MS-sourced; the anti-pattern framing is INF) · **Sources:** L-15, L-17, L-02, LC-03, LC-23, PF-24

#### LC-28 — Not-doing-it and doing-it-manually are legitimate economic options and are frequently the honest answer
- **Classification:** DECISION CRITERION · **Origin:** INF
- **Evidence:** No Microsoft source frames this — the absence is the point. Microsoft's cost guidance for Azure does: *"Regularly remove or optimize legacy, unneeded, and underutilized workload components"* (CO:07) and *"Align the cost of each flow with flow priority… Optimizing flow spend often requires strategic compromises"* (CO:09) (L-07). Applied to Power Platform, the platform's own consumption economics make the comparison sharp: an automation that runs 40 times a year costs approximately nothing on a consumption meter (LC-18, Microsoft's own seasonal example) but a per-user licence for its owner costs the same as one that runs continuously.
- **Why it matters:** aisa's mission requires it to be able to conclude *"not Power Platform"* and also *"not now"* or *"not automated"*. The economic case for automating a low-frequency, low-value process is often negative once §2.5's full TCO lines are counted — build effort, monitoring, support plan, environment, ongoing maintenance, technical debt — even when the licence is free. This is the option most often missing from a Power Platform business case.
- **Decision impact:** In Options, always carry: (a) process change without technology, (b) the existing capability already licensed, (c) Power Platform, (d) alternatives, (e) do nothing. Price (c) with the full TCO lines, not the licence line. For genuinely low-frequency processes, the consumption meter plus a deliberately minimal operational model may be the right answer — or not automating at all may be.
- **Confidence:** MEDIUM (INF; framed from Azure's CO:07/CO:09 by analogy) · **Sources:** L-07

#### LC-29 — Technical debt is a cost line with documented mechanisms in this platform
- **Classification:** RISK · **Origin:** MS + INF
- **Evidence:** Microsoft names technical debt as a performance-efficiency concern: *"When you design and implement for performance, focus on the efficiency and effectiveness of cost, complexity, supporting new requirements, **technical debt**, reporting, and toil"* (L-24, `ms.date` 2025-08-15). Documented debt-creating mechanisms in this corpus: formulas over 256,000 characters in apps with long load times (→ PF-06); flows approaching 500 actions where Microsoft's remedy is *"Consider redesigning your flow"* (→ PF-33); Dataverse for Teams solutions with no export path to a full environment (LC-14); the deprecation stream, which forces unplanned remediation on published dates (→ OP-28); and connection references requiring new connections after every restore (→ OP-17). The productivity-vs-mission-critical contrast is Microsoft's own: *"Built ad-hoc | Built to last; Built by one | Built and maintained by a team; No tests | Automated tests; **Development in production | Exercises application lifecycle management**; Users monitor quality | Monitored to improve; Short lifecycle | Long lifecycle"* (L-25, `ms.date` 2026-05-04).
- **Why it matters:** Low-code lowers the cost of the *first* version, which shifts the cost of ownership toward change. The mechanisms above are all cases where a decision that saved effort early creates mandatory rework later, and none of them appears in a licence-based business case. Microsoft's productivity-vs-mission-critical table is effectively a debt ledger: each left-hand item is a saving now and a cost later.
- **Decision impact:** For any solution expected to last, carry an explicit provision for: deprecation-driven remediation (a recurring, unavoidable line, → OP-28), refactoring as artefacts approach structural limits, and the migration cost of any deliberately-cheap starting point (Dataverse for Teams, non-solution artefacts, development in production). Where a sponsor wants the productivity-workload cost with the mission-critical lifecycle, name the contradiction.
- **Confidence:** MEDIUM (mechanisms are MS-sourced; the debt-as-cost-line framing is INF) · **Sources:** L-24, L-25, PF-06, PF-33

#### LC-30 — Advanced security controls can introduce **external licence prerequisites across the governed population**
- **Classification:** DECISION CRITERION + VOLATILE VALUE
- **Origin:** MS-L / MS
- **Evidence:** Current Microsoft documentation says Power Platform IP firewall and customer-managed key require managed environments and additional A5/E5/G5-class Microsoft 365/Office 365 or named compliance/security subscriptions for users in environments where the control is enforced. The current Power Platform licensing FAQ lists VNet support with the same advanced-security/governance prerequisite family. Microsoft Entra states that Conditional Access requires Entra ID P1, while risk-based Conditional Access requires P2. These are entitlement prerequisites, not list-price evidence; customer agreements can differ.
- **Why it matters:** the security control can create a larger cost line than the Power Apps/Automate licence itself because the unit is **the affected user population**, not the number of apps.
- **Decision impact:** model **control → required entitlement → affected population → current customer holdings/gap → incremental cost**. Revalidate at implementation and renewal. Never remove a required security control merely to make the Power Platform option appear cheaper; instead mark the option economically infeasible or choose another architecture/control.
- **Confidence:** HIGH for the prerequisite shape on the cited dates; actual commercial entitlement/pricing is **VOLATILE VALUE** and customer-contract-specific.
- **Sources:** `https://learn.microsoft.com/en-us/power-platform/admin/ip-firewall`; `https://learn.microsoft.com/en-us/power-platform/admin/customer-managed-key`; `https://learn.microsoft.com/en-us/power-platform/admin/powerapps-flow-licensing-faq`; `https://learn.microsoft.com/en-us/entra/fundamentals/licensing`.

**REQUIREMENT → COST DRIVER → ARCHITECTURAL CONSEQUENCE.** Phrased so each can be asked in Discovery without naming a product.

|---|---|---|---|
| **DC-01** | Which systems must the solution read from or write to? | Premium/standard connector boundary determines whether the whole user population needs paid licensing (LC-03) | Establish connector tier at design time. Where a standard path meets the requirement, the saving is population-wide; where it does not, the premium cost belongs in the option's economics from the first comparison |
| **DC-02** | How many people, and how often does each of them interact? | Population × frequency selects between per-user, per-app, capacity and consumption models (LC-04, LC-18) | Many users × few interactions → consumption. Few users × many interactions → prepaid. Unknown adoption → consumption first, true up later |
| **DC-03** | How many distinct applications or sites does one person need? | Per-app licences are stackable and per-environment; Power Pages counts per website (LC-04, LC-12) | App and site decomposition is a cost driver. | **DC-04** | How much data, how many files, and what audit retention? | Three separate capacity types; **no user licence accrues log capacity**; borrowing is one-directional (LC-05, LC-10, LC-11) | Cost database, file and log separately. | **DC-12** | Must the solution survive the loss of a region? | Doubles storage consumption from the tenant pool, requires a managed environment, and degrades high-volume automation (LC-24) | Verify tenant capacity headroom before enabling; cost premium licences + 2× storage + drill effort; re-check the 15%/5% thresholds afterwards |
| **DC-13** | How many environments does the governance and ALM model require? | Four axes: 1 GB storage floor each, per-app entitlement scoped per environment, Power Pages per-environment minimums, and premium licences for every managed environment (LC-25) | Keep development on developer-plan environments (free of both); minimise the count of *managed* environments; consolidate sites; align billing policies to the business units that carry cost |
| **DC-14** | Which security controls are mandatory and how many people are in their enforcement scope? | IP firewall/CMK/VNet and Conditional Access can require external Microsoft 365/Entra entitlements in addition to Power Platform licensing (LC-30) | Price the affected population before accepting the architecture; if unfunded, the option is economically infeasible rather than “secure by configuration” |

Do not build a business case on transition-period generosity |

## 5. Cost anti-patterns

| # | Anti-pattern | Mechanism | Origin | Sources |
|---|---|---|---|---|
| **LC-AP-01** | **Choosing the architecture by licence price.** Selecting the data source, connector or ownership model to minimise the visible licence line. | Produces documented worse outcomes: SharePoint performance penalties, duplicated data with synchronisation runs, database-stored files at 20× the file rate, forfeited operational capability | INF over MS | LC-27 |
| **LC-AP-02** | **Discovering the premium boundary after the build.** Designing against SQL, HTTP, a custom connector or the on-premises gateway without checking the licence consequence. | Moves the whole user population from seeded to paid entitlement; T3 sources describe this as the commonest mid-project licence shock | MS + T3 | LC-03, L-10 |

## 6. Economic comparison with alternatives — **method, not price verdict**

Cross-Block V2 rejects the previous row-level “where Power Platform is favoured” claims as too weakly evidenced on the comparator side. No current, like-for-like comparator pricing was fetched, and SaaS/custom/other-low-code economics are engagement-specific. This section is therefore a **comparison method**. It may conclude that Power Platform is economically wrong, but only after the same workload and operating model are priced across options.

For every candidate (Power Platform, custom development, Azure-native, SaaS/configure-buy, existing enterprise platform, other low-code), compare the same units:

| Cost dimension | Required comparison input | Why it changes the decision |
|---|---|---|
| **Audience** | named users, active users, external/anonymous population, user×app pairs | Power Platform often scales with people/app scope; other models may not |
| **Machine workload** | calls/messages/compute time/transactions and peak shape | machine-heavy work can make per-action and connector constraints expensive even with few users |
| **Data** | DB/file/log volume, growth, audit, replicas, retention | storage/retention/DR can dominate licences |
| **Security prerequisites** | required controls and affected population | external E5/P1/P2/compliance prerequisites can dominate the Power Platform line (LC-30) |
| **Environment/lifecycle** | dev/test/UAT/prod, managed-environment fidelity, pipelines | non-production and release controls are real recurring cost |
| **External estate** | API gateway, broker, Functions/workers, gateway hosts, network | hybrid patterns import Azure/on-premises consumption and administration |
| **Observability/support** | telemetry ingestion/retention, alerts, support plan, on-call | availability and diagnosis are funded capabilities |
| **Build/change effort** | initial build, migration, test automation, release frequency, deprecations | low-code may reduce initial build and still lose on long-lived maintenance, or vice versa |
| **Existing sunk capability** | licences/platform teams already owned | the economically correct answer may be “use the incumbent”; avoid double-paying for a second platform |
| **Exit/option value** | migration/rewriting cost and lock-in constraints | future switching cost belongs in TCO where portability matters |

**Durable heuristic, retained only as a hypothesis to test:** Power Platform has important people-/scope-based cost mechanisms, while infrastructure alternatives often expose more compute/transaction-based meters. The **users-to-work ratio** can therefore be a useful crossover variable, but it is not a verdict and must be tested with current pricing and the actual customer agreement.

- **Classification:** DECISION CRITERION + TRADE-OFF
- **Origin:** INF over MS-sourced Power Platform billing units; comparator pricing intentionally not asserted
- **Confidence:** MEDIUM for the method; **UNKNOWN per engagement** for the winning option

## 14. Cross-Block V2 reconciliation and volatile-value register

### 14.1 Security ↔ Cost
LC-30 closes the previous structural omission: advanced security controls can import external Microsoft 365/Entra entitlement requirements over a broad population. `security.md` owns whether the control is required; this file owns the economic consequence. No list price is hardcoded as an architectural principle.

### 14.2 Architecture ↔ Cost
Hybrid/API/broker patterns must include the non-Power-Platform half: Azure resource consumption, telemetry/logging, network/gateway hosts, non-production, support and the personnel/team that operates it. `integration-architecture.md` §15 and `architecture-patterns.md` now expose those fields. LC-U-06 is partially closed by the gateway/VNet sizing basis; actual prices remain engagement-specific.

### 14.3 Operations ↔ Cost
Criticality changes the bill through managed environments, telemetry, recovery/DR, support and test environments. Availability targets must be costed at the **business-flow** level, including external dependencies; Dataverse's 99.9% service SLA is not a complete solution guarantee.
