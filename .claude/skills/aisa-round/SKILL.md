# aisa-round

## Usage

`/round [perspective|--close]`

- No argument: in Discovery, **one** integrated analysis applies the six perspectives (`business · operations · user · data · governance · financial`) from `library/kernel/lens-checklists.md` — one execution and one draft, not six. It records the coverage of the six (`coverage.py`, stage `lens`), has it read by an independent reviewer, and closes the passagem when the record is valid and current. In other phases → stop with: "/round is for Discovery; use /frame, /options, /decide for later phases."
- `[perspective]` (e.g., `data`): the same analyst goes deeper on **that** perspective only, inside the passagem currently open (opening one if none is). It writes a new coverage record that inherits the other five from the latest one. The passagem stays open, and the reviewer does not run (step 6c).
- `--close`: closes the open passagem without new analysis. The independent reviewer reads the latest record of this passagem, and the passagem closes if that record is valid and current (step 7).

Why one analysis: `docs/handoff-v1/F3/DESENHO.md` Q1–Q3. Six perspectives never mean six documents or six executions.

## Execution steps

1. Read `_state.json` (resolve the engagement root as in `aisa-start`). Read `phase`, `round` and `round_in_progress`.
2. If `phase != discovery` → stop with the message above.
3. **Determine the passagem** — a round in progress is not a completed round (`library/kernel/phases.md` → *Rounds*). `round` holds the last **completed** round; `round_in_progress` holds the one an open `/round` is filling (empty or absent → none open).
   a. `round_in_progress` non-empty and ahead of `round` → the round to run **is** `round_in_progress`. A `round_in_progress` equal to or behind `round` is a leftover (phase transition, hand edit): ignore it and treat it as none open.
   b. Otherwise → increment `round` by one (`R-00`→`R-01`, `R-01`→`R-02`, ...). `aisa-start` seeds `R-00` (no round run yet), so the first `/round` runs `R-01`.
   c. **Persist the open passagem** (one publication through the coordinator — a draft of `_state.json`, then `resolve.py publish`; `library/kernel/orchestration.md` → *Writing an authority*) BEFORE the analysis: `round_in_progress` = the round to run. `round` does not move here. This is what lets `/round data` and then `/round` stamp the same passagem, and what survives a session that dies mid-passagem. Nothing polices an order any more — the six are one analysis — so there is no `round_lenses` record; a leftover `round_lenses` key is removed in this same draft.
   d. `--close` → skip steps 3.5–5 and go to step 6 for the passagem in `round_in_progress` (none open → stop with: *"não há passagem em curso para fechar"*).

   The analysis stamps **this** round on its rows.
3.4. **Passagem guard** (only when a passagem is already open — 3a; runs BEFORE capture and context assembly so a *fechar* costs nothing). Read `engagement.lentes_ronda_aberta` from the motor (`python library/kernel/tools/dashboard.py --engagement <slug> --json <file>`). For a profile engagement it reads the `lens` coverage record: `corridas` (the six, or none), `fecha`, `revista`, `motivos`. Then:
   - `/round` with no argument and `corridas` non-empty (this passagem already has its six perspectives recorded) → **`AskUserQuestion`** (business language; id/kernel term in the description): *«A passagem <N> (ronda R-NN) já tem as seis perspectivas registadas<, ainda por rever>. Refazer a análise acrescenta linhas novas ao que já lá está.»* — options: *fechar a passagem com o que já tem* (→ step 6 as `--close`) / *refazer a análise completa*. Never re-run silently.
   - Otherwise → proceed. `/round <perspective>` never asks: going deeper is what it is for.
3.5. **Capture freshness check**: for every capture-supported file in `inputs/` — `.xlsx`/`.xlsm` (structured tier) and `.docx`/`.pdf`/`.vtt` (capture-lite) — compare its SHA-256 with `identity.sha256` in `_capture/<file>.extraction.json`; both tiers write that key, so one rule covers both, and formats outside the tiers are never stale. Missing artefact, mismatched hash, or missing `_capture/evidence-index.md` → invoke the `aisa-capture` skill for the stale/missing file(s) BEFORE the analysis (both extractors self-cache on SHA-256, so a fresh file costs one hash check). Comparison is hash/status only — never a semantic diff of old vs new content. Capture failure is soft: warn and name the file. What is never acceptable is an analysis reasoning over normalized evidence whose source has since changed without being told — name any source left stale in the context (step 3.6a).
3.6. **Assemble the passagem context** (once, before the analysis). Pure bookkeeping: the orchestrator resolves paths and one manifest key. It does not decide what any of it means.
   a. **Shared evidence** — `<engagement>/_capture/evidence-index.md`. Present → carry its path. Absent (no `_capture/`, or capture could not run) → carry the explicit line *"no `_capture/evidence-index.md` — raw `inputs/` is the evidence surface"*; never let the analysis assume a shared capture exists. Name likewise any source left stale by 3.5 or reported `failed`/`skipped`. Do **not** rank, assign, summarize or bundle sources, and do not build a per-perspective evidence view: the index is a source map; which of it matters is the lens's judgement — the analyst's, per perspective.
   b. **Pack attention cues** — read `_state.json.pack`, resolve `library/packs/<pack>/pack.yaml` → `lenses_config.<lens>.extra_signals` for the perspectives about to be applied (the six, or the named one), once per passagem. Missing `pack` key, missing `lenses_config.<lens>`, missing `extra_signals`, or an empty list → inject nothing for that lens and continue: cues are optional enrichment and a lens works on its universal perspective without them. A `pack.yaml` that does not parse is a visible failure — report it and stop, as `aisa-start` step 3 does for a missing manifest (no new validation machinery). Pass the configured tokens through **verbatim**: no scoring, no ranking, no filtering, no reordering, no rewriting into questions, no coverage bookkeeping.
   c. **Next free SU ids** — scan `shared-understanding.md` for the highest id per prefix (`C-`, `A-`, `U-`, `X-`, `R-`; `library/kernel/states.md` → id prefixes) and compute the next free id per section. **Recompute this scan immediately before EACH draft** (the analysis draft of step 4 and the arbiter's of step 5), never once for the passagem: a set computed before an earlier publish hands out an id that now exists. Two rows under one id make a citation ambiguous, and the motor cannot repair it — it reports `id duplicado` and keeps the first (F01, `docs/ADVERSARIAL_REVIEW_2026-09-08.md`).
   d. **Enquadramento** — `<engagement>/enquadramento.md` (written by `aisa-start` step 9b). Present with invariants → carry its path and the list of `M-n` ids (ids only, never the text). Present but *"não declarado"*, or absent (pre-P-0 engagement) → carry the explicit line *"no enquadramento — the owner has not declared the business mechanism; `Unknown` rows must declare their divergence in the to-be instead of citing an `M-n`"*. The orchestrator never writes or infers an `M-n`.
4. **The integrated analysis** — one execution, inline (it needs the whole context, and its detail is the product; README → *Regras de execução*):
   a. **Record it as a task** in the work checkpoint (`_work/checkpoint.json`, published by the coordinator — `library/kernel/handoff-contract.md` → *Checkpoint*): `python library/kernel/tools/workflow.py task plan --engagement <slug> --role analista-integrado --criteria "linhas das perspectivas <as seis | a pedida> publicadas na SU para <R-NN>" --input shared-understanding.md --input answers.md --input enquadramento.md --start --json` → `TASK-NNN`. The task starts `running` with the hashes of what the analysis is about to read; publishing its draft (4d) marks it `completed` in the same operation. A session that dies mid-analysis leaves it `running` — `/resume` reconciles it, it is never taken as still running.
   b. **Open the draft** (`library/kernel/orchestration.md` → *Writing an authority*): `python library/kernel/tools/resolve.py draft --engagement <slug> --files shared-understanding.md lens-outputs/business.md lens-outputs/operations.md lens-outputs/user.md lens-outputs/data.md lens-outputs/governance.md lens-outputs/financial.md --reads context.json enquadramento.md answers.md decisions.md '_capture/*' 'inputs/**/*' 'lens-outputs/*.md' --task <TASK-NNN> --json` (globs quoted; in `/round <perspective>` only that perspective's `lens-outputs` file). The analysis writes into these copies and nowhere else. A citation of a file the draft did not declare is refused at publish (`INCOMPLETE_READ_SET`): add it to `--reads` in a new draft, never drop the citation.
   c. **Apply** `library/kernel/lens-checklists.md` — the common rules and each perspective's section, the governance conflict scan last — with this context, as pointers rather than contents:
      ```
      Round: <R-NN> · engagement `<slug>` · engagement root `<engagement>` · perspectives: <all six | <name>>
      Draft: `<engagement>/_drafts/<id>/` — write the SU rows into `shared-understanding.md` (the `lens` column names the perspective each row answers) and, per perspective, the block **What matters** (2–4 sentences) · **Tensions / risks** · **Open evidence** (`(none)` where empty) under `## <R-NN> — <perspective>` in `lens-outputs/<perspective>.md` HERE, never in the engagement files; the orchestrator publishes them in one operation
      Shared Understanding: `<engagement>/shared-understanding.md` — next free ids: C-NNN · A-NNN · U-NNN · X-NNN · R-NNN
      Request context: `<engagement>/context.json` · funding gate: `funding_gate` = <true|false> (absent → true) — read verbatim from `context.json`; the financial perspective conditions its mandate on it (`library/kernel/lens-checklists.md` → *Financial*)
      Enquadramento: `<engagement>/enquadramento.md` — invariants M-1..M-n declared by the process owner (their hypothesis, `Confirmed` in ronda R-00; `/frame` confirms or corrects them). Every `Unknown` carries the fields of *Admission of a question* (`library/kernel/states.md`). An `M-n` is context the question may cite; it never stands in for the aspect the answer moves. (or the "no enquadramento" line from step 3.6d)
      Prior lens outputs: `<engagement>/lens-outputs/*.md` — earlier passagens (or "none — first passagem")
      Shared evidence: `<engagement>/_capture/evidence-index.md` — this engagement's source map (source · format · normalized evidence · status · cite as). Raw sources stay at `<engagement>/inputs/`, are always openable, and are authoritative on conflict. Read what bears on each perspective; nobody has decided that for you.
      Memory (optional): `.claude/agent-memory/_universal/<persona>/*.md` (incl. `diary.md` — cite a prior pattern by domain, never by client name) · `.claude/agent-memory/_tenant/<tenant>/<persona>/*.md`
      Pack attention cues (`<pack>`): <perspective>: <token>, <token>, … — cues, not a checklist. Follow only what is material to this engagement; an uncovered cue is not a gap and never becomes an `Unknown`.
      Comprehension survival: `<engagement>/_capture/process-model.md` §4 is the process synopsis (cross-source; lines marked OBSERVED / INFERRED / HYPOTHESIS / UNKNOWN, material lines labelled in backticks) and §6 the PM-U interrogation list. Within each perspective, every material synopsis line and every PM-U row you touch gets exactly ONE disposition in that perspective's `Open evidence` block — `MAP <SU id>` (already a row) · `ADOPT → <new id>` (row you created) · `DISMISS — <reason>` (not material for downstream decision reasoning). Markers are not states: OBSERVED → Confirmed only with the evidence; INFERRED → Assumed with basis; HYPOTHESIS → the Unknown that would settle it, or leave it in the synopsis; UNKNOWN → Unknown. A Critical PM-U may remain Unknown but never disappears silently. Disposition ≠ resolution.
      ```
      Omit the cue line entirely when step 3.6b resolved nothing (and say nothing in its place). Omit the comprehension-survival line when `_capture/process-model.md` does not exist. `<persona>` comes from the perspective→persona map in *Notes*.
      **Do not dump.** No evidence bodies, no `pack.yaml`, no `question-bank.md`, no domain-knowledge files, no full prior-passagem prose in the context — pointers only; the analysis opens what it needs. It is told where things are, never what to conclude, which evidence matters, which cue is relevant, or which state a finding should get.
   d. **Check and publish.** Confirm the draft SU has the rows and each perspective applied its block. Check that no id written already existed before the draft (the scan of 3.6c is what makes this a check and not a hope); a collision is fixed **now**, in the draft, by renaming the new row (`was <id>` on the renamed one). Then `python library/kernel/tools/resolve.py publish --engagement <slug> --draft <id>`. A refusal is handled by the table in *Writing an authority* — `INTEGRITY_FAILURE` (e.g. a `Confirmed` without a resolvable locator) goes back to the analysis to fix in the copy; `STALE_INPUT` means someone else published meanwhile: open a new draft on the current SU and redo the rows there.
5. **Arbiter** — after the analysis is published and BEFORE the coverage record: the arbiter edits SU rows, and a record finalized before those edits would be stale at once. Open **one arbiter draft** — `resolve.py draft --engagement <slug> --files shared-understanding.md council-log.md --json` — write 5a–5c into its copies, then publish it:
   a. Update the SU header `Última actualização` timestamp.
   b. **Disposition bookkeeping** (only when `_capture/process-model.md` exists; string presence, never judgement): list every **Critical** `PM-U` id and every backtick-labelled material synopsis line of §4 that no `Open evidence` block — this passagem or an earlier one — names with `MAP` / `ADOPT` / `DISMISS`. Report them as `undisposed`. Never dispose of one yourself and never promote a PM-U to an SU row: that is the analysis's judgement, taken in the next `/round <perspective>`. `/frame`'s soft gate reads the same list.
   c. **Round arbiter — admission** (presence of fields, never judgement). Rule and bounds: `library/kernel/states.md` → *Admission of a question*. Deterministic support: `python library/kernel/tools/dashboard.py --engagement <slug> --json <file>` → `arbiter.sem_declaracao` / `sem_impacto` / `alternativas_nao_avaliadas` / `decisivo_sem_referente`, filtered to `ronda = R-NN`. **Run the motor first; then read every row it names.** Its lists are presence checks; the judgement is yours (`falsos_negativos`, `julgamento`). `sem_colunas_handoff` counts rows written before the admission columns existed: never act on those.

      Per `Unknown` created this passagem: its `impacto` names at least one of the five aspects, and `tipo`, `âmbito`, `quem responde`, `fecho`, `bloqueio` and `referências` are filled; a `design_choice` names ≥ 2 real alternatives in `swing`; a `fact_gap` owes none. `decisivo` with no named referent → `dimensionante`.

      **What the arbiter does, on that row only:**
      1. `impacto` names no readable aspect — the answer moves nothing demonstrable → **park it**: append ` — estacionada (R-NN: sem impacto demonstrável)` to the last column (`states.md`, the sixth sanctioned edit);
      2. any other field missing → **hand the row back** to the analysis, in this same pass, naming the fields; the analysis completes them, and a question that itself changes becomes a new row `was U-nnn`. The arbiter never fills a field;
      3. `decisivo` without a named referent → class token → `dimensionante`, append ` — reclassificado P-1 (R-NN): decisivo sem referente`.

      Every mark and every hand-back completion is made in the arbiter draft's copies, never in place. One line per row in `council-log.md` (`estacionada: U-nnn (sem impacto demonstrável)` · `devolvida: U-nnn (falta fecho, bloqueio)` · `swing corrigido: U-nnn decisivo → dimensionante`). **Never**: delete a row, rewrite the question, judge materiality, fill a field, or raise a `criticidade`. Which options a question touches is `/simulate`'s judgement, not yours (emenda F10).
      **The one materiality class that is the arbiter's** (P-21, the role rule — `library/kernel/states.md` → *Question economics*). A row whose question, or whose `swing`, names as its consequence **only** a person's identity, a signature, an approval, an acceptance, or a document proving a third party's position changes no requirement, no data shape and no effort. Park it — append ` — estacionada (R-NN: pergunta de pessoa ou de papel, P-21)` — log the line in `council-log.md`, and say in the passagem output that the question must be reformulated by **role, operation and enforcement plane** or dropped. This is a **class** test, not a case-by-case opinion, and it is the only materiality judgement the arbiter makes.
      **Second reading — `Confirmed` created this passagem** (`library/kernel/states.md` → *Confirmed threshold*). For each new `C-` row ask three things: does the evidence carry a locator of the five classes; does the claim say more than that evidence says; and does the evidence **contradict** the claim? A direct extraction over the raw source counts only once it is **persisted in `_capture/`** and the evidence points at that file (states.md rule 1, fifth class) — a method declared in prose is not a locator. A missing locator never reaches the SU: the guard and `resolve.py publish` refuse it (`INTEGRITY_FAILURE`) — the arbiter's reading is the part no machine does. A claim above its evidence is **not a metadata edit**: it is a transition — new row `A-nnn was C-nnn`, basis = the locators, original marked ` — resolved → A-nnn`, one line in `council-log.md`. A claim the evidence **contradicts** is a transition as well, but the state does not drop when that evidence settles the right value: new row `C-nnn was C-nnn` with the corrected claim and the locator that fixes it (`states.md` → *Correction by evidence*). Without a locator that settles it, the row goes to `Assumed`. Never edit the claim in place. The arbiter reads only this passagem's rows, and only those it has not touched yet: a row whose `swing` already carries ` — reclassificado P-1` is skipped, as is a row already marked ` — resolved →`. A passagem that spans several `/round <perspective>` calls brings the same rows back each time; reclassifying twice would stack markers.

      **Publish the arbiter draft** now (`resolve.py publish --engagement <slug> --draft <id>`). A refusal follows *Writing an authority*.
6. **Coverage record** (`library/kernel/coverage-contract.md` §4.8) — the record is what closes the passagem, never a count of files:
   a. **Skeleton**: `python library/kernel/tools/coverage.py lens-draft --engagement <slug> --round <R-NN> > <tmp>/lens-draft.json`. It carries the base of **now** and inherits the perspectives and the conflict scan of the latest `lens` record — never its review.
   b. **Fill** (skip on `--close`): for each perspective applied in this call, `status` (`assessed` · `gap` · `not_applicable`), `refs` and `justification`, by `library/kernel/lens-checklists.md` → *Coverage evidence*. `refs` are SU ids that exist, `answers.md#…`, `enquadramento.md#…` or files under `_capture/` / `inputs/` — never a heading, never a `lens-outputs` section. A `gap` cites the open question that routes it. A `not_applicable` says why; without a reason it is invalid. The perspectives not applied in this call keep what they inherited — and when there is no earlier record to inherit from (a first passagem opened by `/round <perspective>`), the other five have nothing yet: stop here, do not finalize; the passagem has no coverage record until a full `/round` covers the six. `conflict_scan`: the `X-` rows the governance scan produced, or the note saying it found none (rewritten only when governance was applied). `lens_coverage.author` stays `{"kind": "agent", "name": "analista integrado (/round)"}`.
   c. **Independent review — only when the passagem is to close** (a full `/round`, or `--close`; never after `/round <perspective>`: a record the next one replaces is not worth reviewing — `docs/handoff-v1/F3/DESENHO.md` §0). Launch **one** subagent with the Agent tool, `subagent_type: lens-coverage-reviewer`, with fresh context. Pass only the engagement root, the path of `<tmp>/lens-draft.json`, `shared-understanding.md` and `library/kernel/lens-checklists.md` — no summary of the analysis, no opinion on what is covered: its independence is its only value. It returns the `semantic_review` block; put it in the draft as returned and never edit a verdict. A `not_treated` perspective stays visible: it becomes a gap of the record, and the passagem closes «por rever» (T19). Reviewer unavailable, or it returns `pending` → the review stays as it is, and the passagem closes «cobertura por rever» (soft gate).
   d. **Finalize**: `python library/kernel/tools/coverage.py finalize --engagement <slug> --draft <tmp>/lens-draft.json` → `_coverage/coverage_vNN.json`, published by the coordinator. A refused draft is fixed, never forced: a dead reference goes back to the analysis to cite a row that exists; never drop a perspective or invent a reference.
7. **Close test, then close.** Only a full `/round` or `--close` closes; after `/round <perspective>` go straight to the closing draft with *does not close*.
   a. `python library/kernel/tools/coverage.py round-state --engagement <slug> --round <R-NN> --json` (exit 0 closes, 4 does not). `closes: true` → the passagem closes; with `reviewed: false` it closes marked «cobertura por rever», naming the `reasons`. `closes: false` → it does not close; carry the `reasons` to step 9. *Never* close on a count of files or on "the analysis ran".
   b. Open **one closing draft** — `resolve.py draft --engagement <slug> --files _state.json council-log.md story.md --json`:
      - Closes → `round` = the round just run, `round_in_progress` = `""`. `round` therefore always holds the most recent **completed** round = the engagement's current round.
      - Does not close → `round` does **not** move and `round_in_progress` keeps the open passagem.
      - Append to `council-log.md`: what this call applied (the six, a perspective, or `--close`), the record (`_coverage/coverage_vNN.json`), and whether the passagem closed and was reviewed.
      - **On close only** (one episode per passagem) — append one narrative episode to `<engagement>/story.md` (`## Episódio <N> — <data> — ronda de Discovery (o que se descobriu, o que ficou por saber)`): 4-8 frases na voz do sponsor, sem jargão de kernel, máx. 2 ids citados. Create the file with `# Story — <slug>` if missing (pre-v2.3 engagements).

      Publish it (`resolve.py publish`). The passagem is not reported closed until this publish succeeds.
8. **Convergence** (counts from the motor only — `python library/kernel/tools/dashboard.py --engagement <slug> --json <file>`, never by hand). Read, for the round just run: `Unknown` **criadas** this round (rows with `ronda = R-NN`), **fechadas** this round (rows marked `resolved →` whose resolution happened this round, any origin — `/answer`, transition, arbiter), **abertas** total and **Critical abertas**. `criadas > fechadas` → label the round `sem convergência`. Visible, never blocking: no gate, no new state. All four come from `round_delta`: the entry of `round_delta.por_ronda` whose `ronda` is the round just run gives `criadas`, `fechadas` and `sem_convergencia`; `round_delta.abertas` and `round_delta.critical_abertas` are the engagement's current totals. When `round_delta.indeterminadas` is non-empty, say how many closures the motor could not date — never estimate them into a round. With the passagem still open the numbers are this passagem **so far** — say so; they are not a closed round's balance.
9. Output (business language — `CLAUDE.md` → *Duas línguas*; kernel labels and ids only between parentheses; the numbers are step 8's, never recounted):
   ```user-output
   Passagem <N> <concluída | a meio> (ronda R-NN) — <as seis perspectivas, numa só análise | aprofundada a perspectiva <negócio | operações | utilizador | dados | controlo | custo>>.
   Cobertura das seis perspectivas: <lida por um revisor independente, sem falhas | por rever — <razão curta> | ainda não fecha — <razão curta>> (_coverage/coverage_vNN.json).
   <só se houver> Perspectivas que o revisor achou por tratar: <perspectiva> — <o que falta, numa frase> …
   Perguntas que os ficheiros levantaram e em que ninguém ainda olhou: <nenhuma | <n> — <descrição curta> (PM-U-NNN, grave) …>.
   Perguntas reclassificadas por não dizerem o que muda: <nenhuma | <n> — <pergunta curta> (U-nnn: passou a «não muda nada», e deixou de contar como grave) …>.
   Nesta passagem: <n> perguntas novas · <n> fechadas · <n> em aberto no total (<c> graves) <· abrimos mais do que fechámos>.
   A seguir: <passo humano, se houver — ex.: reunião com o dono para as perguntas graves> → <passagem a meio: `/round` para a análise completa, `/round <perspectiva>` para aprofundar uma, ou `/round --close` para a fechar com o que tem> <passagem concluída: `/status` para ver o que falta, ou `/round` para outra passagem>.
   ```

## Notes

- `/round` with no argument analyses the six and closes the passagem in the same call (or, with a passagem already recorded, asks first — 3.4). `/round <perspective>` runs inside the passagem already open, or opens one, and never closes it. The counter only moves forward, and it moves when the passagem **closes** (step 7), not when the analysis writes. The analysis appends and never rewrites prior rows, so a re-run never corrupts — but it adds a second `## R-NN — <perspective>` block and a second batch of rows, which is why 3.4 asks.
- **A round in progress is not a completed round.** `round_in_progress` names the passagem the analysis is stamping; `/frame` reads `round`, so a passagem left open never counts as a completed round at the phase gate — close it with `/round --close` first.
- **No order to police.** The six perspectives are one analysis; the governance conflict scan runs last inside it (`library/kernel/lens-checklists.md` → *Order*). What closes a passagem is the coverage record, valid and current (`coverage.py round-state`), never a count of `lens-outputs` headers. The `pre-lens-order-check` hook and the `round_lenses` record are retired (handoff-v1 F3.3).
- **Subagents** (README → *Regras de execução*): the analysis runs inline — it needs the session's context and its detail is the product. The reviewer is the one subagent: it must **not** have the analyst's context, only its verdict comes back, and it runs once, in sequence, after the record it reads was drafted.
- **Perspective → persona** (for the memory pointer only): business → `business-analyst` · operations → `operations-lead` · user → `user-advocate` · data → `data-steward` · governance → `compliance-officer` · financial → `cfo-lens`.
- **Discovery cues stay in Discovery.** This passagem applies the six Discovery perspectives only; `lens-technology` is never invoked here and never receives Discovery `extra_signals`. It activates in Options, where it resolves the pack itself — pull-based (`library/kernel/orchestration.md` → *Pack context*).
- **The pack's question bank is not lens context.** It is not resolved here and never enters a lens invocation. Its single consumer is `aisa-status` step 6, where questions are formulated after reasoning has exposed what matters.
- **Disposition is projection, not resolution.** `MAP` / `ADOPT` / `DISMISS` make material process semantics visible in the SU before compression (`library/kernel/orchestration.md` → *Comprehension survival*). An adopted Critical PM-U may stay `Unknown` for the whole engagement; what is forbidden is the silent fourth outcome.
